# DearDay 개발 요구사항 정의서

> 상태: 기획 진행 중 / 지속 업데이트
> 목적: DearDay의 제품·기능·개발 기준을 한 곳에 관리하고, 이후 Codex 개발 및 구현 누락 점검의 기준 문서로 사용한다.

## 1. 서비스 개요

### 1.1 서비스명
- DearDay

### 1.2 서비스 정체성
- DearDay는 웨딩 전용 모바일 청첩장 서비스가 아니라 **다양한 행사를 위한 모바일 초대장 제작 플랫폼**이다.
- 결혼식은 초기 핵심 상품이지만 돌잔치, 생일, 파티, 기념일, 집들이, 졸업, 기업/단체 행사 등으로 확장한다.
- 전문적인 디자인·개발 지식 없이 템플릿을 선택하고 필요한 정보만 입력하여 고급스러운 모바일 초대장을 제작·공유할 수 있도록 한다.

### 1.3 브랜드/가격 포지셔닝
- 핵심 방향: **가격은 부담 없게, 결과물은 고급스럽게.**
- `싼 초대장`이 아니라 `합리적인 가격으로 제공하는 고급 모바일 초대장`으로 포지셔닝한다.
- 경쟁 서비스보다 조금 부담이 낮은 가격대를 지향하되 지나친 최저가 경쟁은 하지 않는다.
- 모든 일반 템플릿은 초기에는 동일가격 정책으로 운영한다.
- 실제 판매가격은 출시 전 경쟁사 가격, PG 수수료, 템플릿 완성도 등을 보고 최종 확정한다.
- 시스템은 향후 템플릿별 가격 변경이 가능하도록 확장성을 유지한다.
- 결제한 실제 초대장 URL에는 외부 광고를 노출하지 않는다.

### 1.4 무료 제작/유료 발행 원칙
- 템플릿 탐색, 초대장 제작, 임시저장, 미리보기까지 무료로 제공한다.
- 사용자가 실제 내용과 사진을 넣어 완성본을 충분히 확인한 뒤 결제한다.
- **실제 발행 및 전용 URL 활성화 시 유료**로 운영한다.
- 초기 정책에서는 무료 발행 템플릿을 별도로 운영하지 않고 모든 일반 템플릿의 발행을 유료로 한다.

### 1.5 주요 사용자/지원 행사
- 결혼식, 돌잔치, 생일 및 각종 파티를 준비하는 개인 사용자
- 기념일, 집들이, 졸업식 등 가족/개인 행사 사용자
- 기업/단체 행사 및 기타 초대장이 필요한 사용자
- 향후 반복 제작 수요가 있는 행사 주최자/사업자/단체로 확장 가능

지원 행사:
- 웨딩
- 돌잔치
- 생일
- 기념일
- 집들이
- 졸업
- 기업 행사
- 각종 파티
- 기타 행사

### 1.6 서비스 방향
- 모바일 환경을 최우선으로 설계한다.
- 새로운 행사 종류와 템플릿을 쉽게 추가할 수 있도록 한다.
- 웹 서비스를 우선 개발하되 향후 Android/iOS 앱으로 확장 가능하게 한다.
- 기능/콘텐츠와 템플릿 디자인을 분리한다.
- 메뉴와 제작 흐름은 최대한 단순하게 유지한다.

### 1.7 홈페이지 브랜드 스토리
메인 홈페이지에 광고성 팝업보다 정식 브랜드 섹션 `DearDay가 시작된 이유`를 배치한다.

브랜드 문구 방향:
> 특별한 날을 준비하는 마음에  
> 가격이 부담이 되지 않았으면 했습니다.
>
> DearDay는 좋은 디자인과 필요한 기능을 담으면서도  
> 누구나 부담 없이 사용할 수 있는  
> 모바일 초대장을 만들고자 시작되었습니다.
>
> **가격은 가볍게, 특별한 날의 품격은 그대로.**
>
> 당신의 소중한 날에 DearDay가 함께하겠습니다.

- `경쟁사보다 저렴` 같은 직접 비교 표현보다 `합리적인 가격`, `부담 없는 가격`을 사용한다.
- 메인 흐름은 Hero → 행사 종류 → 추천 템플릿 → DearDay가 시작된 이유 → 이용방법 → 제작 CTA 방향을 우선 검토한다.

## 2. 시스템 구성

- Frontend / Web Framework: Next.js
- Source Code: GitHub
- Hosting / Deployment: Vercel
- Database / Authentication / Storage: Supabase
- 외부 서비스: Kakao, Naver, 향후 PG 결제 API
- GitHub main 브랜치를 운영 기준으로 사용하고 Vercel에서 자동 배포한다.
- API Secret, Client Secret, Service Role Key 등은 환경변수로 관리한다.
- 서버 전용 Secret을 클라이언트 코드/GitHub에 직접 저장하지 않는다.
- Supabase RLS로 사용자별 데이터 접근을 제어하고 공개 데이터와 소유자 관리 데이터를 분리한다.

개발 흐름:
`요구사항 정의 → ChatGPT 설계/검토 → Codex 최소 범위 개발 → 테스트 → GitHub → Vercel → 운영환경 테스트`

- Codex에는 큰 범위의 분석/리팩터링보다 작은 작업 단위로 지시한다.
- 기존 정상 기능을 불필요하게 변경하지 않는다.
- 불필요한 라이브러리 추가, DB 변경, 대규모 리팩터링을 피한다.

## 3. 회원 및 인증

- 초대장 제작/관리는 회원 로그인이 필요하다.
- 발행된 초대장은 하객이 로그인 없이 열람할 수 있다.
- RSVP/방명록은 기본적으로 하객 로그인 없이 가능하다.
- Supabase Auth를 인증 중심으로 사용한다.
- MVP 소셜 로그인: Kakao, Naver
- 향후 Google, Apple, 이메일 확장 가능
- `카카오로 시작하기`, `네이버로 시작하기` 방식으로 제공한다.
- 동일 소셜 계정 반복 로그인으로 중복 회원이 생성되지 않도록 한다.
- 로그인 세션 유지 및 로그아웃을 제공한다.

### 3.1 회원탈퇴/데이터 처리
- 회원탈퇴 시 모든 DB 행을 무조건 즉시 삭제하는 방식으로 처리하지 않는다.
- 프로필에는 `withdrawn` 상태와 `withdrawn_at` 등 논리적 탈퇴 상태를 기록할 수 있도록 설계한다.
- Supabase Auth 계정은 탈퇴 후 로그인이 불가능하도록 비활성화/삭제 처리한다.
- 서비스 제공에 불필요해진 개인정보는 정책에 따라 삭제 또는 비식별화한다.
- 초대장/사진/RSVP/방명록은 초대장 삭제 정책과 연계한다.
- 결제/환불 등 법령상 보관이 필요한 거래기록은 필요한 기간만 별도 보관 후 삭제한다.
- 탈퇴 통계가 필요하더라도 불필요한 개인정보를 무기한 보관하지 않는다.

## 4. 템플릿과 행사 종류 구조

### 4.1 핵심 원칙
- 템플릿 = 어떻게 보이는가(Visual Design)
- 행사 종류(Event Type) = 어떤 콘텐츠/편집항목이 필요한가
- 초대장(Event Instance) = 사용자가 실제로 제작한 하나의 초대장
- 템플릿은 행사별로 별도 복제하지 않고 가능한 한 공통 디자인으로 재사용한다.
- 행사 종류에 따라 편집항목이 달라진다.

### 4.2 두 가지 제작 진입 경로
A. 디자인부터 시작: `템플릿 선택 → 행사 종류 선택 → 편집 → 미리보기 → 결제 → 최종 발행 확인 → 발행`

B. 행사부터 시작: `행사 종류 선택 → 템플릿 선택 → 편집 → 미리보기 → 결제 → 최종 발행 확인 → 발행`

- 두 경로는 동일한 초대장 편집 화면으로 합류한다.

### 4.3 템플릿 가격 정책 — 최신 확정
- **모든 일반 템플릿은 초기 동일가격으로 운영한다.**
- 템플릿에 따라 핵심 기능 등급을 나누지 않는다.
- 사용자는 가격이 아니라 마음에 드는 디자인을 중심으로 선택할 수 있게 한다.
- 실제 동일 판매가격은 출시 전 최종 결정한다.
- 시스템/DB는 향후 정책 변경에 대비해 템플릿별 가격을 설정할 수 있는 확장성을 유지한다.

### 4.4 템플릿 변경 정책 — 최신 확정
- 기존 `결제 후 템플릿 변경 불가` 정책은 폐기한다.
- 결제 전 템플릿을 자유롭게 변경할 수 있으며 입력 내용은 유지한다.
- 결제 완료 후·발행 전에도 템플릿 변경이 가능하다.
- **발행 후에도 초대장 이용기간 동안 템플릿을 자유롭게 변경할 수 있다.**
- 템플릿 변경에 추가 결제를 요구하지 않는다.
- 템플릿을 변경해도 기존 URL, 입력 내용, 사진, RSVP, 방명록 데이터를 그대로 유지한다.
- 템플릿 변경은 행사 데이터를 새로 만드는 것이 아니라 디자인만 교체하는 것으로 처리한다.
- 행사 종류 자체의 변경은 별도 정책으로 제한할 수 있다.

### 4.5 핵심 마케팅 포인트
- `발행했다고, 디자인까지 끝난 건 아니니까.`
- `마음은 그대로, 디자인은 언제든 새롭게.`
- **이용기간 동안 발행 후에도 원하는 템플릿으로 변경 가능 / 추가 결제 없음 / 내용과 URL 그대로**를 주요 혜택으로 강조한다.
- `무제한 변경`보다는 실제 정책과 일치하는 `이용기간 동안 자유롭게 변경` 표현을 사용한다.
- 템플릿 목록/결제 전 안내/홈페이지 차별점 영역 등에서 해당 혜택을 명확히 노출한다.

## 5. 메뉴 / 사이트맵

### 5.1 PC 상단
`DearDay | 템플릿 | 이용안내 | [초대장 만들기] | 프로필`
- `내 초대장`은 최상위 PC 메뉴에 별도로 두지 않고 마이페이지에서 접근한다.

### 5.2 모바일
- 상단: DearDay 로고 + 햄버거 + 프로필
- 햄버거: 템플릿, 이용안내, 내 초대장, 하객 관리, 결제/보관, 내 정보, 초대장 만들기 등

### 5.3 홈/제작 진입
- 행사 우선: 결혼식 / 돌잔치 / 생일 / 파티 / 기타
- 템플릿 우선: 추천/인기 템플릿 및 전체 템플릿 보기
- `초대장 만들기` 클릭 시 `디자인부터 시작하기`와 `행사부터 시작하기`를 선택할 수 있게 한다.

## 6. 데이터 구조 기본 원칙

- 행사별 별도 초대장 본체 테이블을 만들지 않는다.
- 핵심 초대장 데이터는 공통 `events` 구조를 사용한다.
- `event_kind`로 행사 종류를 구분한다.
- 행사별 입력 차이는 공통 이벤트 데이터 + 유연한 설정 데이터(JSONB 등)를 활용한다.
- 사진, RSVP, 방명록 등 반복/관계 데이터는 별도 테이블을 사용한다.
- 현재 events, templates, event_media, rsvps, guestbook_entries, event_locations 등을 최대한 활용한다.
- 템플릿 변경 시 이벤트/하객 데이터를 새로 생성하지 않는다.

## 7. 초대장 편집 공통 원칙

### 7.1 필드/검증
1. 항상 필수: 행사 핵심 정보
2. 조건부 필수: 해당 기능 ON일 때만 필수
3. 선택: 없어도 발행 가능

- 임시저장/미리보기는 필수항목이 없어도 가능하다.
- 최종 발행 시 항상 필수 + ON 기능의 조건부 필수만 검사한다.
- OFF 기능은 발행 검증에서 완전히 제외하고 공개 초대장에서도 숨긴다.
- 편집 중 과도한 빨간 오류를 피하고 최종 발행 시 누락 목록을 명확히 안내한다.

### 7.2 편집 UX
- 하나의 편집 화면에서 섹션별 구성 및 접기/펼치기를 활용한다.
- ON/OFF 기능은 OFF 시 상세 편집 UI를 숨긴다.
- 템플릿은 결제/발행 여부와 관계없이 이용기간 동안 변경 가능하고 콘텐츠를 유지한다.

## 8. 웨딩 편집항목 v1.0

### 8.1 기본정보
항상 필수: 신랑 이름, 신부 이름, 예식 날짜, 예식 시간, 예식장명

선택: 상세정보, 주소, 지도

### 8.2 대표사진 / Hero
- 초대장 접속 시 최상단 대표 Hero로 사용한다.
- 사진형/타이포형/일러스트형 등 템플릿 표현을 지원한다.
- 대표사진 사용 여부를 선택 가능하게 하여 사진 없는 템플릿도 발행 가능하게 한다.
- 템플릿 변경 시 대표사진 데이터를 유지한다.

### 8.3 인사말
- 제목/내용 선택 입력
- 미입력 시 섹션 숨김 가능

### 8.4 가족 / 연락처
- ON/OFF
- OFF: 입력 불필요/공개 화면 숨김
- ON: 신랑·신부측 부모, 본인/부모 연락처 등 입력 가능
- 입력된 정보만 표시

### 8.5 사진 / 갤러리
- ON/OFF
- 사진 추가/삭제/순서변경
- 현재 최대 20장 기준 우선 유지

### 8.6 마음 전하기 / 계좌
- ON/OFF
- OFF 시 계좌정보 없이 발행 가능
- ON 시 신랑/신부측 계좌 등록 가능
- 등록하는 계좌 1건마다 은행/계좌번호/예금주를 조건부 필수로 검사

### 8.7 RSVP
- ON/OFF
- ON 시 이름(필수), 참석/불참(필수), 참석 인원, 연락처(선택), 메시지(선택)
- 향후 신랑/신부측, 성인/아동, 식사 여부 확장 가능

### 8.8 방명록
- ON/OFF
- ON 시 이름 + 메시지 작성
- 초대장 소유자는 부적절한 방명록을 삭제 가능
- 향후 작성자 수정/삭제/비밀번호 확장 가능

## 9. 공개 초대장 디자인/브랜드 원칙

- 모바일 우선
- 깨끗하고 고급스러운 디자인
- 대표사진 Hero를 첫 화면에 크게 노출하는 디자인 지원
- 콘텐츠와 템플릿 디자인 분리
- 은은한 스크롤 Reveal, 이미지 Lazy Loading은 별도 고려
- 과도한 애니메이션/광고성 요소를 피한다.
- **결제한 공개 초대장에는 외부 배너/광고를 넣지 않는다.**
- DearDay 브랜딩이 필요한 경우 초대장 본연의 디자인을 해치지 않도록 최소화한다.

## 10. 결제 / 발행 / 수정

### 10.1 기본 상품 흐름
`무료 제작 → 무료 임시저장/미리보기 → 결제 → 결제완료 → 최종 발행 확인 → 초대장 발행하기 → 발행완료 → 전용 URL 활성화 → 공유`

- 결제 완료와 발행 완료를 분리한다.
- 결제 성공만으로 공개 URL을 자동 활성화하지 않는다.
- 사용자가 직접 `초대장 발행하기`를 눌러 최초 발행한다.
- 최초 발행 시점을 별도로 기록할 수 있도록 설계한다.

### 10.2 결제 완료 후 발행 전
- 결제는 완료되었지만 URL은 아직 공개되지 않은 상태이다.
- 템플릿 변경 가능.
- 환불 판단을 위해 `결제완료/미발행` 상태를 구분한다.

### 10.3 발행 후 수정/템플릿 변경
- 이용기간 내 내용과 템플릿 모두 수정 가능하다.
- 사진, 날짜, 시간, 장소, 선택 기능 등을 수정 가능하다.
- 템플릿도 자유롭게 변경 가능하다.
- 기존 URL을 유지한다.
- 수정/템플릿 변경 때문에 추가 결제하지 않는다.
- 기존 RSVP/방명록 데이터를 유지한다.
- 사용자 UI에서는 `재발행`보다 `변경사항 반영` 등 쉬운 표현을 사용한다.

## 11. 이용기간 / 만료 / 보관

- 기본 공개 이용기간: **행사일 + 14일**
- 만료 후 공개 URL 비활성화, 즉시 데이터 삭제하지 않음
- 만료 후 **30일 유예기간** 동안 데이터 유지
- 유예기간 중 유료 보관기간 연장/복구 가능
- 연장 결제 시 기존 URL과 초대장/사진/RSVP/방명록 유지
- 구체적인 연장 기간/가격은 추후 결정
- 유예기간 종료 후 초대장 관련 데이터 및 Storage 사진 최종 삭제 가능
- 사용자 계정은 초대장 만료만으로 삭제하지 않는다.

MVP 만료 알림은 마이페이지에서만 제공하고 SMS/카카오 알림톡은 사용하지 않는다.

예:
- `초대장 이용기간이 7일 남았습니다.`
- `초대장이 만료되었습니다. 데이터 삭제까지 30일 남았습니다.`
- `7일 후 초대장 데이터가 삭제됩니다.`

## 12. 마이페이지

메뉴:
- 내 초대장
- 하객 관리
- 결제/보관
- 문의내역
- 계정/내 정보
- 로그아웃
- 회원탈퇴

초대장 상태:
- 제작중(임시저장)
- 결제완료/미발행
- 발행완료
- 만료

### 12.1 발행완료 카드
주요 버튼은 단순하게 유지한다.
- 편집하기
- 초대장 보기
- 공유하기

`공유하기` 내부:
- 링크 복사
- QR 코드
- 카카오톡 공유(향후)

- 발행된 초대장에는 링크 복사가 반드시 가능해야 한다.
- 템플릿 변경은 편집 흐름 안에서 제공한다.

### 12.2 기타 상태
- 제작중: 계속 만들기 / 미리보기 / 삭제, 공개 공유 없음
- 결제완료/미발행: 발행하기 / 편집 / 환불 요청
- 만료/유예: 미리보기 / 삭제까지 남은 기간 / 유료 보관 연장
- 여러 초대장은 카드 목록으로 관리하고 `+ 새 초대장 만들기` 제공

## 13. 하객 관리

- RSVP와 방명록을 한 화면에서 탭으로 관리한다.
- 여러 초대장이 있으면 관리할 초대장을 선택한다.
- RSVP: 전체/참석/불참/미정 요약, 응답자/인원/필터
- 방명록: 이름/메시지/작성일, 소유자 삭제 기능
- 향후 RSVP Excel 다운로드 가능

Empty State:
- 초대장 없음: `아직 관리할 초대장이 없습니다.` + 초대장 만들기
- 제작중만 있음: 하객 관리는 발행 후 시작된다는 안내 + `초대장 계속 만들기`

## 14. 관리자

### 14.1 주요 메뉴
1. 대시보드: 회원/초대장/결제/환불 주요 지표
2. 회원 관리
3. 초대장 관리
4. 템플릿 관리: 등록/수정/미리보기/가격/노출/정렬
5. 결제/환불: 결제목록/자동환불/예외·수동환불
6. 보관/만료: 만료예정/유예/삭제예정/연장결제
7. 신고/문의
8. 서비스 관리: 공지/정책 등
9. 권한 관리

### 14.2 관리자 권한 — 최신 확정
- 애플리케이션 코드에 이메일을 영구 하드코딩하여 관리자 여부를 판단하지 않는다.
- DB `user_roles` 등 역할 구조를 사용한다.
- 역할 예: `user`, `admin`, `super_admin`
- 초기 개발/설정 시 서비스 소유자 계정 1개만 `super_admin`으로 DB에 1회 지정한다.
- 이후 `super_admin`이 관리자 UI에서 다른 계정(예: 운영자)을 `admin`으로 부여할 수 있게 한다.
- `super_admin`만 관리자 추가/해제/권한 변경을 수행한다.
- 일반 `admin`은 자신의 권한을 상승시킬 수 없다.
- 메뉴 숨김이 아니라 API/서버/RLS에서 실제 권한을 검증한다.
- 일반 사용자가 `/admin` 직접 접근해도 관리자 데이터에 접근할 수 없어야 한다.

## 15. 결제 / 환불

### 15.1 결제
- 초기 하나의 PG 우선 연동을 검토한다.
- 주문 → PG → 승인 → 서버 검증 → DB 결제완료 → 최종 발행 확인 → 사용자 발행 → 서비스 이용 시작
- 클라이언트 결과만 믿지 않고 서버 검증한다.
- 중복결제/실패/취소/환불/웹훅/금액변조를 고려한다.
- `paid_at`, `published_at`, `service_started_at` 등 결제와 최초 발행을 구분할 수 있는 개념을 둔다.

### 15.2 자동환불 — 최신 확정
일반적인 환불 가능 건은 자동 처리하고 예외 건은 관리자 처리한다.

자동환불 조건:
1. 결제완료 상태
2. 최초 발행 전
3. 결제일로부터 7일 이내
4. 기존 환불/취소 처리되지 않은 결제

모두 충족 시:
`사용자 환불 요청 → DearDay 서버 조건 검증 → PG 결제취소 API 호출 → PG 취소 성공 확인 → DearDay DB 환불완료`

- **PG 취소 성공 전에 DB를 환불완료로 변경하지 않는다.**
- 조건 불충족, PG 오류, 발행 후 요청, 기간 초과, 분쟁/보상 등은 관리자 검토 대상으로 보낸다.
- 자동환불 성공 후 입력한 초대장 콘텐츠는 보존하고 결제 전 상태로 되돌려 다시 템플릿 선택/결제가 가능하도록 하는 방향을 기본으로 한다.

### 15.3 환불 정책 원칙
- 결제 후 최초 발행 전 + 결제일 7일 이내: 전액 환불 가능 방향
- 최초 발행 후: 서비스 이용이 시작된 것으로 보아 단순 변심 환불은 원칙적으로 제한
- 중복 결제: 중복분 환불
- DearDay 시스템 장애: 확인 후 전액 또는 적절한 환불
- 사용자 입력 실수는 발행 후 수정 가능하므로 원칙적으로 환불 사유로 보지 않음
- 보관 연장 상품 환불기준은 추후 확정
- 관계 법령상 청약철회/환불이 필요한 경우 관계 법령 우선
- 출시 전 한국 전자상거래/디지털 콘텐츠 관련 법률 검토 후 약관 최종 확정

## 16. 사이트 내부 문의/고객지원

- 고객 문의는 DearDay 사이트 내부에서 등록/답변/조회할 수 있도록 한다.

사용자:
`이용안내 → 문의하기 → 문의 유형 + 제목 + 내용 → 등록`

문의 유형 예:

- 초대장 이용
- 오류
- 기타

`관리자 → 문의 관리 → 미답변/답변완료 → 상세 → 답변 등록`

- MVP는 사이트 내부 문의/답변으로 충분하며 실시간 채팅은 필수가 아니다.
- 향후 답변 등록 시 이메일/카카오 알림 확장 가능.

## 18. 개발/확장 원칙

- 기존 정상 기능 우선 보존
- Event Type → Field Definition → Editor 구조로 확장
- 행사 종류 추가 시 `if wedding` 하드코딩을 무분별하게 늘리지 않는다.
- 템플릿 변경은 콘텐츠/URL/RSVP/방명록 데이터를 파괴하지 않는다.
- 템플릿은 시각 디자인, 이벤트는 콘텐츠라는 분리를 유지한다.
- 외부 API를 독립적으로 관리한다.
- 향후 Android/iOS에서도 동일한 Supabase 데이터/백엔드 활용을 우선한다.
- 관리자/가격/템플릿/보관기간 등 운영정책은 가능한 코드 하드코딩보다 DB/관리자 설정으로 확장 가능하게 한다.
