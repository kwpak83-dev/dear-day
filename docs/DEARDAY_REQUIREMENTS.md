# DearDay 개발 요구사항 정의서

> 상태: 기획 진행 중 / 지속 업데이트
> 목적: DearDay의 제품·기능·개발 기준을 한 곳에 관리하고, 이후 Codex 개발 및 구현 누락 점검의 기준 문서로 사용한다.

## 1. 서비스 개요

### 1.1 서비스명
- DearDay

### 1.2 서비스 정체성
- DearDay는 웨딩 전용 모바일 청첩장 서비스가 아니라 **다양한 행사를 위한 모바일 초대장 제작 플랫폼**이다.
- 결혼식은 초기 핵심 상품이지만 돌잔치, 생일, 파티, 기념일, 집들이, 졸업, 기업/단체 행사 등으로 확장한다.
- 전문적인 디자인·개발 지식 없이 템플릿을 선택하고 필요한 정보만 입력하여 고급스러운 모바일 초대장을 제작·공유할 수 있도록 한다.
- 향후 학원, 교회, 모임, 행사기획자, 웨딩플래너, 기업 등 반복 제작 수요로 확장할 수 있으나 MVP에서는 B2B 전용 기능을 우선 구현하지 않는다.

### 1.3 브랜드/가격 포지셔닝
- 핵심 방향: **가격은 부담 없게, 결과물은 고급스럽게.**
- `싼 초대장`이 아니라 `합리적인 가격으로 제공하는 고급 모바일 초대장`으로 포지셔닝한다.
- 경쟁 서비스보다 조금 부담이 낮은 가격대를 지향하되 지나친 최저가 경쟁은 하지 않는다.
- 모든 일반 템플릿은 초기 동일가격 정책으로 운영한다.
- 실제 판매가격은 출시 전 최종 확정한다.
- 결제한 실제 초대장 URL에는 외부 광고를 노출하지 않는다. 단, 고객 FAQ/마케팅에서는 광고 여부를 별도 핵심 문구로 강조하지 않는다.

### 1.4 무료 제작/유료 발행 원칙
- 템플릿 탐색, 초대장 제작, 임시저장, 미리보기까지 무료로 제공한다.
- 사용자가 완성본을 충분히 확인한 뒤 결제한다.
- **실제 발행 및 전용 URL 활성화 시 유료**로 운영한다.
- 초기에는 무료 발행 템플릿/무료 플랜을 핵심 전략으로 운영하지 않는다.

### 1.5 지원 행사
- 웨딩
- 돌잔치
- 생일
- 기념일
- 집들이
- 졸업
- 기업 행사
- 각종 파티
- 기타 행사

### 1.6 서비스 방향
- 모바일 환경 최우선.
- 새로운 행사 종류와 템플릿을 쉽게 추가할 수 있게 한다.
- 웹 우선 개발 후 Android/iOS 확장 가능하게 한다.
- 기능/콘텐츠와 템플릿 디자인을 분리한다.
- 메뉴와 제작 흐름은 최대한 단순하게 유지한다.

### 1.7 홈페이지 브랜드 스토리
메인 홈페이지에 정식 브랜드 섹션 `DearDay가 시작된 이유`를 배치한다.

> **특별한 날을 준비하는 마음에  
> 가격이 부담이 되지 않았으면 했습니다.**
>
> DearDay는 좋은 디자인과 필요한 기능을 담으면서도  
> 누구나 부담 없이 사용할 수 있는  
> 모바일 초대장을 만들고자 시작되었습니다.
>
> **가격은 가볍게, 특별한 날의 품격은 그대로.**
>
> 당신의 소중한 날에 DearDay가 함께하겠습니다.

- 메인 흐름: Hero → 행사 종류 → 추천 템플릿 → DearDay가 시작된 이유 → 이용방법 → 제작 CTA.
- 브랜드 스토리를 첫 방문 강제 팝업으로 띄우지 않는다. 팝업은 향후 프로모션 등에 제한적으로 사용한다.

## 2. 시스템 구성 / 개발 원칙

- Frontend / Web Framework: Next.js
- Source Code: GitHub
- Hosting / Deployment: Vercel
- Database / Authentication / Storage: Supabase
- 외부 서비스: Kakao, Naver, 향후 PG 결제 API
- GitHub `main` 브랜치를 운영 기준으로 사용하고 Vercel 자동 배포.
- Secret/Service Role Key 등은 환경변수로 관리하고 클라이언트/GitHub에 직접 저장하지 않는다.
- Supabase RLS로 사용자별 데이터 접근을 제어한다.

개발 흐름:
`요구사항 정의 → ChatGPT 설계/검토 → Codex 최소 범위 개발 → 테스트 → GitHub → Vercel → 운영환경 테스트`

- Codex에는 큰 범위의 분석/리팩터링보다 작은 작업 단위로 지시한다.
- 기존 정상 기능을 불필요하게 변경하지 않는다.
- 불필요한 라이브러리 추가, DB 변경, 대규모 리팩터링을 피한다.
- Codex 작업 전 `docs/DEARDAY_REQUIREMENTS.md`를 먼저 확인하도록 한다.

## 3. 회원 및 인증

- 초대장 제작/관리는 회원 로그인이 필요하다.
- 발행 초대장은 하객이 로그인 없이 열람할 수 있다.
- RSVP/방명록은 기본적으로 하객 로그인 없이 가능하다.
- MVP 소셜 로그인: Kakao, Naver.
- 향후 Google, Apple, 이메일 확장 가능.
- `카카오로 시작하기`, `네이버로 시작하기` 방식.
- 동일 소셜 계정 반복 로그인으로 중복 회원이 생성되지 않도록 한다.
- 로그인 세션 유지 및 로그아웃 제공.

### 3.1 회원탈퇴 — 최신 확정
- **활성화된 발행완료 초대장이 있으면 즉시 회원탈퇴 불가.**
- 해당 초대장의 이용기간 종료 후 사용자가 직접 탈퇴할 수 있다.
- 탈퇴 예약/자동탈퇴 스케줄링 기능은 구현하지 않는다.
- 활성 초대장이 없으면 일반 회원탈퇴 가능.
- 탈퇴 후 동일 카카오/네이버 계정으로 재가입 가능.
- 재가입은 신규 회원처럼 시작하며 이전 초대장/서비스 데이터는 자동 복구하지 않는다.
- Supabase Auth 계정은 탈퇴 후 기존 계정으로 로그인할 수 없도록 처리한다.
- 불필요한 개인정보는 삭제 또는 비식별화하고, 결제/환불 등 법령상 보관이 필요한 거래기록은 필요한 기간만 별도 보관한다.

## 4. 템플릿과 행사 종류 구조

### 4.1 핵심 원칙
- 템플릿 = 어떻게 보이는가(Visual Design)
- 행사 종류(Event Type) = 어떤 콘텐츠/편집항목이 필요한가
- 초대장(Event Instance) = 사용자가 실제로 제작한 하나의 초대장
- 템플릿은 행사별로 별도 복제하지 않고 가능한 한 공통 디자인으로 재사용한다.
- 행사 종류에 따라 편집항목이 달라진다.

### 4.2 두 가지 제작 진입 경로
A. 디자인부터 시작: `템플릿 선택 → 행사 종류 선택 → 편집 → 미리보기 → 결제 → 최종 발행 확인 → 발행`

B. 행사부터 시작: `행사 종류 선택 → 템플릿 선택 → 편집 → 미리보기 → 결제 → 최종 발행 확인 → 발행`

- 두 경로는 동일한 초대장 편집 화면으로 합류한다.

### 4.3 가격 구조 — 최신 확정
- 초기에는 서비스 공통 기본 발행가격 하나를 사용하고 모든 일반 템플릿에 동일 적용한다.
- 관리자가 동일 가격을 템플릿마다 반복 입력하지 않게 한다.
- 정확한 판매가격은 출시 전 최종 결정한다.
- 향후 프리미엄/시즌 템플릿 등에 대비해 템플릿별 개별가격 Override가 가능하도록 설계한다.
- 관리자 템플릿 가격 방식: `기본가격 사용 / 개별가격 사용`.
- 초기 모든 일반 템플릿은 `기본가격 사용`.
- 향후 실제 차등가격 도입 시 업그레이드 차액결제/다운그레이드 환불 정책을 별도 정의한다.

### 4.4 템플릿 변경 정책 — 최신 확정
- 결제 전 자유롭게 변경 가능, 입력 내용 유지.
- 결제 완료 후·발행 전에도 변경 가능.
- **발행 후에도 초대장 이용기간 동안 자유롭게 변경 가능.**
- 초기 동일가격 정책에서는 추가 결제 없음.
- 기존 URL, 입력 내용, 사진, RSVP, 방명록 유지.
- 템플릿 변경은 행사 데이터를 새로 만드는 것이 아니라 디자인만 교체한다.
- 출시 템플릿은 공통 핵심 섹션을 지원하여 변경 시 콘텐츠가 갑자기 사라지는 문제를 최소화한다.

### 4.5 핵심 마케팅 포인트
- `발행했다고, 디자인까지 끝난 건 아니니까.`
- `마음은 그대로, 디자인은 언제든 새롭게.`
- `이용기간 동안 발행 후에도 원하는 템플릿으로 변경 가능 / 추가 결제 없음 / 내용과 URL 그대로`를 주요 혜택으로 사용한다.
- `무제한 변경`보다는 `이용기간 동안 자유롭게 변경`을 사용한다.

### 4.6 관리자 템플릿 관리 — 최신 확정
- MVP에서 템플릿의 실제 시각 디자인은 **코드 컴포넌트**로 개발한다.
- 관리자 페이지는 Canva 같은 비주얼 템플릿 빌더를 MVP에 구현하지 않는다.
- 관리자에서 관리할 항목: 템플릿명, 내부 관리코드, 스타일 카테고리, 썸네일, 미리보기, 노출 ON/OFF, 가격 방식, 개별가격(선택), 지원 섹션, 추천/신규 표시, 정렬순서.
- 지원 섹션 예: Hero, 인사말, 가족/연락처, 캘린더, 갤러리, 지도, 마음 전하기, RSVP, 방명록.
- 관리 기능: 수정, 복제, 미리보기, 숨김.
- 향후 필요 시 관리자용 시각적 템플릿 빌더로 확장 가능하게 한다.

## 5. 메뉴 / 사이트맵

### 5.1 PC 상단
`DearDay | 템플릿 | 이용안내 | [초대장 만들기] | 프로필`
- `내 초대장`은 PC 최상위 메뉴에 별도로 두지 않고 마이페이지에서 접근한다.

### 5.2 모바일
- 상단: `DearDay | 햄버거 | 프로필`
- 햄버거: 템플릿, 이용안내, 내 초대장, 하객 관리, 결제/보관, 내 정보, 초대장 만들기.

### 5.3 제작 진입
`초대장 만들기` 선택 시:
- 디자인부터 시작하기 → 템플릿 선택 → 행사 선택
- 행사부터 시작하기 → 행사 선택 → 템플릿 선택

## 6. 데이터 구조 기본 원칙

- 행사별 별도 초대장 본체 테이블을 만들지 않는다.
- 핵심 초대장 데이터는 공통 `events` 구조를 사용한다.
- `event_kind`로 행사 종류를 구분한다.
- 행사별 입력 차이는 공통 이벤트 데이터 + 유연한 설정 데이터(JSONB 등)를 활용한다.
- 사진, RSVP, 방명록, 장소 등 반복/관계 데이터는 별도 테이블을 사용한다.
- 현재 `events`, `templates`, `event_media`, `rsvps`, `guestbook_entries`, `event_locations` 등을 최대한 활용한다.
- 템플릿 변경 시 이벤트/하객 데이터를 새로 생성하지 않는다.

## 7. 초대장 편집 공통 원칙

### 7.1 필드/검증
1. 항상 필수: 행사 핵심 정보
2. 조건부 필수: 해당 기능 ON일 때만 필수
3. 선택: 없어도 발행 가능

- 임시저장/미리보기는 필수항목이 없어도 가능.
- 최종 발행 시 항상 필수 + ON 기능의 조건부 필수만 검사.
- OFF 기능은 검증/공개 화면에서 제외.
- 편집 중 과도한 오류 표시를 피하고 최종 발행 시 누락 목록을 명확히 안내한다.

### 7.2 편집 UX
- 하나의 편집 화면에서 섹션별 구성 및 접기/펼치기를 활용한다.
- ON/OFF 기능은 OFF 시 상세 편집 UI를 숨긴다.
- Event Type → Field Definition → Editor 구조로 확장한다.

## 8. 웨딩 편집항목 v1.0

### 8.1 기본정보
항상 필수: 신랑 이름, 신부 이름, 예식 날짜, 예식 시간, 예식장명.
선택: 상세정보, 주소, 지도.

### 8.2 대표사진 / Hero
- 최상단 대표 Hero.
- 사진형/타이포형/일러스트형 지원.
- 대표사진 ON/OFF 가능하여 사진 없는 템플릿도 지원.
- 템플릿 변경 시 대표사진 데이터 유지.

### 8.3 인사말
- 제목/내용 선택 입력, 미입력 시 숨김 가능.

### 8.4 가족 / 연락처
- ON/OFF.
- ON 시 신랑·신부측 부모, 본인/부모 연락처 등 입력 가능.
- 입력된 정보만 표시.

### 8.5 사진 / 갤러리
- ON/OFF.
- 사진 추가/삭제/순서변경.
- 현재 최대 20장 기준 우선 유지.

### 8.6 마음 전하기 / 계좌
- ON/OFF.
- OFF 시 계좌정보 없이 발행 가능.
- ON 시 등록 계좌마다 은행/계좌번호/예금주 조건부 필수.

### 8.7 RSVP
- ON/OFF.
- ON 시 이름(필수), 참석/불참(필수), 참석 인원, 연락처(선택), 메시지(선택).
- 향후 신랑/신부측, 성인/아동, 식사 여부 확장 가능.

### 8.8 방명록
- ON/OFF.
- 이름 + 메시지 작성.
- 초대장 소유자는 부적절한 방명록 삭제 가능.
- 향후 작성자 수정/삭제/비밀번호 확장 가능.

## 9. 공개 초대장 디자인/브랜드 원칙

- 모바일 우선, 깨끗하고 고급스러운 디자인.
- 대표사진 Hero를 첫 화면에 크게 노출하는 디자인 지원.
- 콘텐츠와 템플릿 디자인 분리.
- 과도한 애니메이션/광고성 요소를 피한다.
- 결제한 공개 초대장에는 외부 배너 광고를 넣지 않는다.
- DearDay 브랜딩은 초대장 본연의 디자인을 해치지 않도록 최소화한다.

## 10. 결제 / 발행 / 수정

### 10.1 기본 흐름
`무료 제작 → 임시저장/미리보기 → 결제 → 결제완료 → 최종 발행 확인 → 초대장 발행하기 → 발행완료 → 전용 URL 활성화 → 공유`

- 결제 완료와 발행 완료를 분리한다.
- 결제 성공만으로 URL을 자동 활성화하지 않는다.
- 사용자가 직접 `초대장 발행하기`를 눌러 최초 발행한다.
- `paid_at`, `published_at`, `service_started_at` 등을 구분할 수 있게 한다.

### 10.2 결제 완료 후 발행 전
- URL 미공개.
- 편집/템플릿 변경 가능.
- 환불 판단을 위해 `결제완료/미발행` 상태를 구분한다.

### 10.3 발행 후
- 이용기간 내 내용과 템플릿 수정 가능.
- 기존 URL 유지.
- 초기 동일가격 정책에서는 템플릿 변경 추가 결제 없음.
- 기존 RSVP/방명록 유지.

### 10.4 행사 취소 / 복원 — 최신 확정
- 발행된 초대장에서 사용자가 `행사 취소하기`를 선택할 수 있다.
- 잘못 누르는 것을 방지하기 위해 실제 상태 변경 전 **확인 팝업을 한 번 더 표시**한다.
- 취소는 삭제가 아니라 상태 전환으로 처리한다.
- 기존 초대장 URL은 유지한다.
- 취소 상태에서는 기존 사진 갤러리, 지도, 계좌, RSVP 등 일반 초대장 본문을 하객에게 숨기고 DearDay가 준비한 **자동 행사 취소 안내문**을 표시한다.
- 기존 초대장 내용/사진/RSVP/방명록 데이터는 삭제하지 않는다.
- 소유자는 `초대장 다시 활성화` 기능으로 기존 초대장을 복원할 수 있다.
- 복원 역시 확인 팝업을 거친다.
- 복원 시 기존 URL, 내용, 사진, RSVP, 방명록을 그대로 유지한다.
- 행사 연기는 별도 복잡한 기능보다 기존 날짜/시간 수정 기능을 우선 활용한다.

자동 취소 안내문 기본 방향:
> **행사 취소 안내**
>
> 부득이한 사정으로 예정되어 있던 행사가 취소되었습니다.  
> 참석을 예정해 주셨던 분들께 감사드리며, 너른 양해 부탁드립니다.

## 11. 이용기간 / 만료 / 보관 / 자동삭제

- 기본 공개 이용기간: **행사일 + 14일**.
- 이후 공개 URL 비활성화, 즉시 데이터 삭제하지 않음.
- 만료 후 **30일 유예기간** 동안 데이터/사진 유지.
- 유예기간 중 유료 보관기간 연장/복구 가능.
- 연장 결제 시 기존 URL과 초대장/사진/RSVP/방명록 유지.
- 구체적인 연장 기간/가격은 추후 결정.
- 사용자 계정은 초대장 만료만으로 삭제하지 않는다.

### 11.1 유예기간 종료 자동삭제 — 최신 확정
- **30일 유예기간 종료 시 관리자 승인 없이 시스템이 자동삭제한다.**
- 초대장 본체 및 관련 DB 데이터와 Supabase Storage 사진/파일을 함께 정리한다.
- 삭제 대상: 초대장 내용, 대표사진, 갤러리, 장소정보, 계좌정보, RSVP, 방명록 등 해당 초대장 관련 서비스 데이터.
- 법령상 별도 보관이 필요한 결제/환불 기록은 초대장 삭제와 분리한다.
- 처리 상태 예: `삭제예정 → 삭제처리중 → 삭제완료 / 삭제실패`.
- 정상 삭제 건은 관리자 승인/확인 불필요.
- **삭제 실패 건만 관리자 확인 필요 목록에 표시하고 재처리한다.**
- 삭제 시도 시각, 대상, 성공/실패, 오류 원인 등 삭제 처리 로그를 남긴다.

MVP 만료 알림은 마이페이지에서만 제공하며 SMS/카카오 알림톡은 사용하지 않는다.

### 12.1 발행완료 카드
주요 버튼은 3개로 단순화한다.
- 편집하기
- 초대장 보기
- 공유하기

공유하기 내부: 링크 복사, QR 코드, 카카오톡 공유(향후), 닫기.

### 12.2 기타 상태
- 제작중: 계속 만들기 / 미리보기 / 삭제, 공개 공유 없음.
- 결제완료/미발행: 발행하기 / 편집 / 환불 요청.
- 만료/유예: 미리보기 / 삭제까지 남은 기간 / 유료 보관 연장.
- 여러 초대장은 카드 목록으로 관리하고 `+ 새 초대장 만들기` 제공.

### 12.3 결제/보관 화면 — 최신 확정
- 결제와 보관을 별도 메뉴로 나누지 않고 **하나의 `결제/보관` 화면**에서 초대장별 카드로 관리한다.
- 제작중: 미결제, `계속 만들기`.
- 결제완료/미발행: 결제 정보 + `초대장 발행하기` + 조건 충족 시 `환불 요청`.
- 발행완료: 결제금액/결제일, 행사일, 이용 종료일 표시.
- 만료/유예: URL 비활성, 삭제 예정일/남은 기간 + `보관기간 연장`.
- 최종 삭제 완료된 초대장은 서비스 관리 목록에서 제거한다.

### 14.2 관리자 권한 — 최신 확정
- 이메일 하드코딩으로 관리자 여부를 판단하지 않는다.
- DB `user_roles` 등 역할 구조 사용: `user`, `admin`, `super_admin`.
- 초기 서비스 소유자 계정 1개만 DB에서 1회 `super_admin` 지정.
- 이후 `super_admin`이 관리자 UI에서 다른 운영자를 `admin`으로 지정 가능.
- `super_admin`만 관리자 추가/해제/권한 변경 가능.
- 일반 admin은 자신의 권한 상승 불가.
- 메뉴 숨김이 아니라 API/서버/RLS에서 실제 권한 검증.
- 일반 사용자의 `/admin` 직접 접근 차단.

### 14.3 관리자 대시보드 방문/전환 통계 — 최신 확정
- 비회원 포함 방문자 수(UV), 페이지 조회수(PV).
- 오늘/어제/이번 달 방문자.
- 신규 회원가입 수.
- 초대장 제작 시작 수.
- 초대장 저장/완성 수.
- 결제 건수/금액.
- 발행완료 수.
- 환불 건수.
- 미답변 문의 수.

전환 퍼널:
`사이트 방문 → 초대장 만들기 시작 → 로그인/회원가입 → 초대장 제작 → 결제 → 발행완료`

- 각 단계별 인원과 전환율을 볼 수 있게 한다.
- 분석 솔루션은 요구사항 단계에서 Vercel Analytics 등에 고정하지 않고 구현 시 비용/개인정보/복잡도를 비교해 결정한다.

### 14.4 관리자 초대장 관리 권한 — 최신 확정
- 전체 초대장 목록/상태/행사종류/소유자/템플릿/행사일/결제상태/미리보기 확인 가능.
- 신고/약관 위반 등 운영상 필요한 경우 초대장 숨김/해제 가능.
- 운영 조치 시 사유를 기록한다.
- **관리자는 고객 초대장의 이름, 사진, 날짜/장소, 계좌, RSVP 내용, 템플릿 등 실제 콘텐츠를 직접 수정하지 않는다.**
- 고객 콘텐츠 수정은 원칙적으로 고객 본인이 수행하고 관리자는 안내한다.
- 관리자 운영행위는 Audit Log에 관리자, 시각, 대상, 작업, 사유를 기록한다.

### 14.5 관리자 결제/환불
- 결제완료, 자동환불, 환불실패, 관리자 확인 필요 등을 조회/필터한다.
- 결제 상세에 PG 거래번호, 결제금액, 결제수단, 결제일, 최초 발행 여부, 환불일/사유/처리결과 등을 확인할 수 있게 한다.
- 정상 자동환불은 관리자가 일일이 승인하지 않는다.
- PG 오류/예외 건은 관리자 확인 대상으로 표시한다.
- 수동 환불 권한은 권한 정책으로 제한한다.

### 14.6 관리자 보관/만료
- 만료예정, 현재 유예기간, 삭제예정, 보관연장, 삭제실패 현황을 조회한다.
- 정상 자동삭제 건은 별도 승인 불필요.
- 삭제 실패 건만 확인/재처리한다.

## 15. 결제 / 환불

### 15.1 결제
- 초기 하나의 PG를 우선 연동한다.
- `주문 → PG → 승인 → 서버 검증 → DB 결제완료 → 최종 발행 확인 → 사용자 발행 → 서비스 이용 시작`.
- 클라이언트 결과만 믿지 않고 서버 검증한다.
- 중복결제/실패/취소/환불/웹훅/금액변조를 고려한다.

### 15.2 자동환불 — 최신 확정
자동환불 조건:
1. 결제완료 상태
2. 최초 발행 전
3. 결제일로부터 7일 이내
4. 기존 환불/취소 처리되지 않은 결제

모두 충족 시:
`사용자 환불 요청 → DearDay 서버 조건 검증 → PG 결제취소 API 호출 → PG 취소 성공 확인 → DearDay DB 환불완료`

- **PG 취소 성공 전에 DB를 환불완료로 변경하지 않는다.**
- 조건 불충족, PG 오류, 발행 후 요청, 기간 초과, 분쟁/보상 등은 관리자 검토.
- 자동환불 성공 후 초대장 콘텐츠는 보존하고 결제 전 상태로 되돌린다.

### 15.3 환불 원칙
- 결제 후 최초 발행 전 + 결제일 7일 이내: 전액 환불 가능 방향.
- 최초 발행 후 단순 변심 환불은 원칙적으로 제한.
- 중복 결제: 중복분 환불.
- 시스템 장애: 확인 후 적절한 환불.
- 사용자 입력 실수는 수정 가능하므로 원칙적으로 환불 사유로 보지 않음.
- 보관 연장 상품 환불기준은 추후 확정.
- 관계 법령이 우선하며 출시 전 법률/약관 검토.

### 15.4 외부 판매채널 결제 확장 — 최신 확정
- DearDay 자체 PG 결제를 기본 결제 경로로 유지하되, 향후 **네이버 스마트스토어 등 외부 판매채널에서 결제한 고객도 동일한 DearDay 초대장 제작/발행 시스템을 이용할 수 있도록 확장 가능한 구조**로 설계한다.
- 외부 판매채널 결제 고객도 DearDay에서 로그인/회원가입 후 기존 제작 흐름을 사용한다.
- 외부 채널에서 결제되었다는 이유만으로 별도의 초대장 데이터 구조나 별도 제작 시스템을 만들지 않는다.
- DearDay 내부 결제 상태는 결제 출처와 무관하게 공통 결제 상태로 통합하되, 결제 출처를 구분할 수 있어야 한다.
- 예: `payment_source = dearday | naver_smartstore | future_external_channel`.
- 외부 주문과 DearDay 회원/초대장을 안전하게 연결하기 위한 구매 인증 절차를 둔다. 후보 방식은 주문번호, 구매자 정보, 휴대폰 정보, 인증코드 또는 외부 주문 API 연동이며 실제 방식은 연동 시 최종 결정한다.
- 외부 주문을 자동 연동할 경우 외부 판매채널의 공식 주문 API를 서버에서 사용하고, 클라이언트 입력만으로 결제완료 권한을 부여하지 않는다.
- 자동 연동 전 단계에서는 관리자가 외부 주문을 확인하여 구매 인증/결제완료 상태를 승인하는 수동 운영 방식도 허용한다.
- 외부 판매채널 구매 인증이 완료되면 해당 초대장을 DearDay 내부의 `결제완료/미발행` 상태와 동일하게 처리하고, 사용자가 최종 `초대장 발행하기`를 눌러 발행하도록 한다.
- 외부 판매채널 결제도 기존의 `결제 완료`와 `최초 발행` 상태를 분리하는 원칙을 유지한다.
- 외부 채널별 주문번호/거래 식별자/결제금액/결제일/구매 인증 상태 등을 추적할 수 있도록 확장 가능하게 한다.
- 외부 판매채널의 환불/취소는 해당 채널의 정책 및 API 처리 결과와 DearDay 내부 상태가 불일치하지 않도록 별도 연동 규칙을 적용한다.
- MVP에서 네이버 스마트스토어 연동을 반드시 구현하는 것은 아니며, **현재 단계에서는 향후 외부 판매채널을 추가하기 쉬운 결제 구조를 확보하는 것을 요구사항으로 한다.**

## 16. 사이트 내부 문의/고객지원

사용자:
`이용안내 → 문의하기 → 문의 유형 + 제목 + 내용 → 등록`

문의 유형:
- 결제/환불
- 초대장 이용
- 오류
- 기타

관리자:
`관리자 → 문의 관리 → 미답변/답변완료 → 상세 → 답변 등록`

- 사용자는 `마이페이지 → 문의내역`에서 답변 확인.
- MVP는 사이트 내부 문의/답변, 실시간 채팅은 필수 아님.
- 향후 이메일/카카오 알림 확장 가능.

## 17. 이용안내 / FAQ

기본 구성:
1. DearDay 이용방법: 디자인/행사 선택 → 편집 → 미리보기 → 결제 → 최종 확인 → 발행 → 공유
2. FAQ
3. 가격 안내
4. 문의하기
5. 이용약관 / 개인정보처리방침 / 환불정책

FAQ 핵심:
- 제작/저장/미리보기는 무료, 발행 시 결제.
- 결제/발행 후에도 이용기간 동안 내용 수정 가능.
- 발행 후에도 이용기간 동안 템플릿 변경 가능.
- 초기 동일가격 정책에서 템플릿 변경 추가 결제 없음, 기존 URL/데이터 유지.
- 기본 이용기간 행사일 +14일.
- 만료 후 30일 유예기간.
- 환불은 최초 발행 전/결제 후 7일 이내 등 조건에 따라 처리.
- 고객 FAQ에는 광고 관련 문항을 별도로 넣지 않는다.

## 18. 개발/확장 원칙

- 기존 정상 기능 우선 보존.
- Event Type → Field Definition → Editor 구조로 확장.
- 행사 종류 추가 시 `if wedding` 하드코딩을 무분별하게 늘리지 않는다.
- 템플릿 변경은 콘텐츠/URL/RSVP/방명록 데이터를 파괴하지 않는다.
- 템플릿=시각 디자인, 이벤트=콘텐츠 분리를 유지한다.
- 외부 API 독립 관리.
- 향후 Android/iOS에서도 동일 Supabase 데이터/백엔드 활용 우선.
- 관리자/가격/템플릿/보관기간 등 운영정책은 가능한 코드 하드코딩보다 DB/관리자 설정으로 확장 가능하게 한다.
