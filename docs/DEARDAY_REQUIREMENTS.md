# DearDay 개발 요구사항 정의서

> 상태: 기획 진행 중 / 지속 업데이트
> 목적: DearDay의 제품·기능·개발 기준을 한 곳에 관리하고, 이후 Codex 개발 및 구현 누락 점검의 기준 문서로 사용한다.

## 1. 서비스 개요

### 1.1 서비스명
- DearDay

### 1.2 서비스 목적
- 사용자가 모바일 환경에서 쉽고 빠르게 디지털 초대장을 제작하고 공유할 수 있는 서비스
- 전문적인 디자인·개발 지식 없이 템플릿을 선택하고 필요한 정보만 입력하여 초대장을 제작할 수 있도록 한다.

### 1.3 주요 사용자
- 결혼식을 준비하는 예비 신랑·신부
- 돌잔치를 준비하는 부모
- 생일 및 각종 파티를 준비하는 개인 사용자
- 기념일, 집들이, 졸업식, 기업 행사 등 각종 행사의 초대장이 필요한 사용자

### 1.4 지원 행사
- 웨딩
- 돌잔치
- 생일
- 기념일
- 집들이
- 졸업
- 기업 행사
- 각종 파티
- 기타 행사

### 1.5 서비스 방향
- 모바일 환경을 최우선으로 설계한다.
- 웨딩 전용 서비스로 제한하지 않고 다양한 행사로 확장 가능한 구조로 개발한다.
- 새로운 행사 종류와 템플릿을 쉽게 추가할 수 있도록 한다.
- 웹 서비스를 우선 개발하되 향후 Android/iOS 앱으로 확장할 수 있도록 한다.
- 기능/콘텐츠와 템플릿 디자인을 분리한다.
- 메뉴와 제작 흐름은 최대한 단순하게 유지한다.

## 2. 시스템 구성

### 2.1 기본 기술 구성
- Frontend / Web Framework: Next.js
- Source Code: GitHub
- Hosting / Deployment: Vercel
- Database / Authentication / Storage: Supabase
- 외부 서비스: Kakao, Naver, 향후 PG 결제 API

### 2.2 역할
- GitHub: 전체 소스코드 및 버전 관리, main 브랜치를 운영 기준으로 사용
- Vercel: main 브랜치 자동 배포 및 환경변수 관리
- Supabase: 인증, 프로필, 초대장 데이터, 템플릿, Storage, RSVP, 방명록 등
- 외부 API: 카카오 로그인/공유, 네이버 로그인/장소검색/지도, PG 결제

### 2.3 보안 기본 원칙
- API Secret, Client Secret, Service Role Key 등은 환경변수로 관리한다.
- 서버 전용 Secret을 클라이언트 코드나 GitHub에 직접 저장하지 않는다.
- Supabase RLS를 이용하여 사용자별 데이터 접근을 제어한다.
- 공개 초대장 데이터와 소유자 전용 관리 데이터를 구분한다.

### 2.4 개발 흐름
요구사항 정의 → ChatGPT와 설계/검토 → Codex 최소 범위 개발 → 테스트 → GitHub Commit/Push → Vercel 자동 배포 → 운영환경 테스트

- Codex에는 큰 범위의 분석/리팩터링을 맡기지 않고 작은 작업 단위로 지시한다.
- 기존 정상 기능을 불필요하게 변경하지 않는다.
- 불필요한 라이브러리 추가, DB 변경, 대규모 리팩터링을 피한다.

## 3. 회원 및 인증

- 초대장 제작/관리는 회원 로그인이 필요하다.
- 발행된 초대장은 하객이 로그인 없이 열람할 수 있다.
- RSVP/방명록 작성은 기본적으로 하객 로그인 없이 가능하게 한다.
- Supabase Auth를 인증의 중심으로 사용한다.
- MVP 소셜 로그인: Kakao, Naver
- 향후 Google, Apple, 이메일 로그인 확장 가능
- 별도 회원가입/로그인 구분보다 `카카오로 시작하기`, `네이버로 시작하기` 방식으로 제공한다.
- 동일 소셜 계정의 반복 로그인으로 중복 회원이 생성되지 않도록 한다.
- 로그인 세션은 유지 가능하며 로그아웃을 제공한다.
- 역할은 일반 사용자 / 관리자 구조를 고려한다.
- 사용자가 자신의 권한을 관리자 권한으로 변경할 수 없어야 한다.
- 관리자 권한은 서버/RLS 기준으로 보호한다.

## 4. 템플릿과 행사 종류 구조

### 4.1 핵심 원칙
- 템플릿 = 어떻게 보이는가(Visual Design)
- 행사 종류(Event Type) = 어떤 콘텐츠/편집항목이 필요한가
- 초대장(Event Instance) = 사용자가 실제로 제작한 하나의 초대장
- 템플릿은 웨딩/돌잔치/생일별로 별도 복제하지 않고 가능한 한 공통 디자인으로 재사용한다.
- 행사 종류에 따라 편집항목만 달라진다.

### 4.2 두 가지 제작 진입 경로

#### A. 디자인부터 시작
템플릿 선택 → 행사 종류 선택 → 행사에 맞는 편집항목 구성 → 내용 편집 → 미리보기 → 결제 → 발행

#### B. 행사부터 시작
행사 종류 선택 → 행사에 맞는 편집항목 결정 → 템플릿 선택 → 내용 편집 → 미리보기 → 결제 → 발행

- 두 경로는 최종적으로 동일한 초대장 편집 화면으로 합류한다.
- 템플릿을 변경해도 사용자가 입력한 행사 데이터는 유지되어야 한다.

## 5. 메뉴 / 사이트맵

### 5.1 PC 상단 메뉴
`DearDay | 템플릿 | 이용안내 | [초대장 만들기] | 프로필`

- `내 초대장`은 PC 최상위 메뉴에 별도로 두지 않고 프로필/마이페이지에서 접근한다.

### 5.2 모바일
- 상단: DearDay 로고 + 햄버거 메뉴 + 프로필
- 햄버거에서 템플릿, 이용안내, 내 초대장, 하객 관리, 결제/보관, 내 정보 등에 접근한다.

### 5.3 홈 진입
- 행사 우선 진입을 홈에서 명확히 제공한다.
  - 결혼식 / 돌잔치 / 생일 / 파티 / 기타
- 템플릿 우선 진입도 홈에서 제공한다.
  - 추천/인기 템플릿 및 전체 템플릿 보기

### 5.4 `초대장 만들기` 버튼
클릭 시 단순한 시작 선택 UI를 제공한다.
- 디자인부터 시작하기 → 템플릿 선택 → 행사 선택
- 행사부터 시작하기 → 행사 선택 → 템플릿 선택

## 6. 데이터 구조 기본 원칙

- 행사 종류별로 별도의 초대장 본체 테이블을 만들지 않는다.
- 핵심 초대장 데이터는 공통 `events` 구조를 사용한다.
- `event_kind`로 행사 종류를 구분한다.
- 행사별로 달라지는 입력 내용은 공통 이벤트 데이터 및 유연한 설정 데이터(JSONB 등)를 활용한다.
- 사진, RSVP, 방명록처럼 반복/관계 데이터는 별도 테이블을 사용한다.
- 현재 존재하는 events, templates, event_media, rsvps, guestbook_entries, event_locations 등의 구조를 최대한 활용한다.
- 행사 종류 추가를 이유로 wedding_events, birthday_events 등 행사별 테이블을 무분별하게 만들지 않는다.

## 7. 초대장 편집 공통 원칙

### 7.1 필드 구분
1. 항상 필수: 행사 자체를 성립시키는 핵심 정보
2. 조건부 필수: 해당 기능을 ON 했을 때만 필수
3. 선택: 없어도 발행 가능

### 7.2 검증
- 임시저장은 필수항목이 없어도 가능하다.
- 미리보기도 필수항목이 없어도 가능하다.
- 최종 발행 시에만 항상 필수 + ON 기능의 조건부 필수를 검사한다.
- OFF 상태의 기능은 필수항목 검사에서 완전히 제외한다.
- 선택 기능을 OFF하면 공개 초대장에서도 해당 섹션을 표시하지 않는다.
- 편집 중에는 과도한 오류 경고를 표시하지 않고 발행 시 누락 항목을 명확히 안내한다.

### 7.3 편집 UX
- 하나의 편집 화면에서 섹션별로 구성하고 필요한 경우 접기/펼치기를 사용한다.
- ON/OFF 기능은 OFF 시 상세 편집 UI도 접거나 숨긴다.
- 현재 디자인을 확인하고 `디자인 변경`이 가능해야 한다.
- 디자인 변경 시 입력 콘텐츠는 유지한다.

## 8. 웨딩 편집항목 v1.0

### 8.1 기본정보
항상 필수:
- 신랑 이름
- 신부 이름
- 예식 날짜
- 예식 시간
- 예식장명

선택:
- 상세정보
- 주소
- 지도

### 8.2 대표사진 / Hero
- 초대장 접속 시 최상단의 대표 Hero 영역으로 사용한다.
- 대표사진 사용 여부 또는 템플릿 특성에 따라 사진형/타이포형 Hero를 지원한다.
- 사진형에서는 대표사진 1장을 등록한다.
- 템플릿에 따라 이름, 날짜, 문구 등을 오버레이할 수 있다.
- 사진이 없는 템플릿은 타이포그래피/일러스트/배경으로 첫 화면을 구성할 수 있다.
- 템플릿을 변경해도 대표사진 데이터는 유지한다.

### 8.3 인사말
선택:
- 인사말 제목
- 인사말 내용
- 미입력 시 섹션 숨김 가능

### 8.4 가족 / 연락처
ON/OFF 선택 기능.
- OFF: 입력 불필요, 발행 가능, 공개 초대장에서 숨김
- ON: 신랑측 부모, 신부측 부모, 신랑/신부 연락처, 부모 연락처 등을 입력 가능
- 입력된 정보만 표시한다.

### 8.5 사진 / 갤러리
ON/OFF 선택 기능.
- 사진 추가/삭제/순서변경
- 현재 구현된 최대 20장 기준을 우선 유지
- OFF 시 갤러리 없이 발행 가능

### 8.6 마음 전하기 / 계좌
ON/OFF 선택 기능.
- OFF: 계좌정보가 없어도 발행 가능하고 섹션 숨김
- ON: 신랑측/신부측 계좌 등록 가능
- 계좌 1건을 등록하려는 경우 은행, 계좌번호, 예금주를 조건부 필수로 검사
- 불완전한 계좌만 발행 전 안내

### 8.7 RSVP
ON/OFF 선택 기능.
- OFF: RSVP 없이 발행 가능
- ON: 공개 초대장에 참석 응답 폼 표시
- 기본 하객 입력: 이름(필수), 참석/불참(필수), 참석 인원, 연락처(선택), 메시지(선택)
- 향후 신랑측/신부측, 성인/아동, 식사 여부 확장 가능

### 8.8 방명록
ON/OFF 선택 기능.
- OFF: 방명록 없이 발행 가능
- ON: 하객이 이름 + 메시지를 작성 가능
- 향후 작성자 수정/삭제, 비밀번호 등의 확장 가능

## 9. 공개 초대장 디자인 방향

- 모바일 우선
- 대표사진 Hero를 첫 화면에 크게 노출하는 디자인 지원
- 깨끗하고 고급스러운 모바일 초대장 스타일
- 콘텐츠와 템플릿 디자인은 분리
- 갤러리, 날짜/장소, 인사말, 가족/연락처, 지도, 마음 전하기, RSVP, 방명록 등을 섹션 단위로 구성
- 스크롤 Reveal과 이미지 Lazy Loading은 별개 기능으로 고려
- 과도한 애니메이션보다 은은한 등장 효과를 선호

## 10. 결제 / 발행 / 수정

### 10.1 기본 흐름
제작중 → 미리보기 → 결제 → 최초 발행 → 전용 URL 활성화

- 결제 완료와 발행 완료는 별개의 상태/행위로 취급한다.
- 결제 후 최종 발행이 이루어지면 URL을 공개한다.

### 10.2 발행 후 수정
- 발행 후에도 이용기간 내 초대장 내용을 수정할 수 있다.
- 수정 시 기존 URL을 유지한다.
- 새 URL을 만들거나 재결제하지 않는다.
- 변경 내용은 기존 공개 초대장에 반영한다.
- RSVP/방명록 등 기존 하객 데이터는 유지한다.
- 사용자 UI에서는 복잡한 `재발행` 표현보다 `변경사항 반영` 등 이해하기 쉬운 표현을 우선한다.
- 행사 종류처럼 초대장 구조 자체를 크게 변경하는 항목은 발행 후 변경을 제한할 수 있다.

## 11. 이용기간 / 만료 / 보관

### 11.1 기본 이용기간
- 행사일 + 14일까지 공개
- 이 기간에는 URL 접속, 수정, 공유, RSVP/방명록 등을 정상 이용

### 11.2 만료
- 행사일 + 14일이 지나면 초대장을 만료 처리한다.
- 공개 URL은 비활성화한다.
- 즉시 데이터를 삭제하지 않는다.

### 11.3 유예기간
- 만료 후 30일간 데이터를 유지한다.
- 마이페이지에서 만료 상태 및 최종 삭제까지 남은 기간을 보여준다.
- 유예기간 중 유료 보관기간 연장/복구가 가능하도록 한다.

### 11.4 유료 연장
- 보관기간 연장은 유료 정책으로 한다.
- 구체적인 연장기간과 가격은 추후 PG 선정/수수료 및 상품정책 확정 시 결정한다.
- 연장 결제 완료 시 기존 URL을 다시 활성화하고 기존 초대장/사진/RSVP/방명록을 유지한다.
- DB는 특정 연장 상품 기간에 고정되지 않도록 설계한다.

### 11.5 최종 삭제
- 유예기간 종료 후 해당 초대장의 데이터 및 Storage 사진을 최종 삭제할 수 있다.
- 사용자 계정 자체는 초대장 만료만으로 삭제하지 않는다.
- 관련 데이터 삭제는 안전하게 처리하고 Storage 정리도 포함한다.

### 11.6 만료 알림
MVP에서는 외부 유료 알림을 사용하지 않는다.
- 카카오 알림톡 사용하지 않음
- SMS 사용하지 않음
- 마이페이지에서만 안내

예:
- 이용기간 7일 이하: `초대장 이용기간이 7일 남았습니다.`
- 만료: `초대장이 만료되었습니다.`
- 삭제 임박: `7일 후 초대장 데이터가 삭제됩니다.`

향후 필요 시 이메일/카카오 알림 확장 가능.

## 12. 마이페이지

### 12.1 메뉴
- 내 초대장
- 하객 관리
- 결제/보관
- 내 정보
- 로그아웃
- 회원탈퇴

### 12.2 내 초대장 상태
- 제작중(임시저장)
- 발행완료
- 만료

`발행중`보다 `발행완료`라는 사용자 표현을 사용한다.

### 12.3 제작중 카드
- 계속 만들기
- 미리보기
- 삭제
- 아직 공개 URL 공유 기능은 제공하지 않음

### 12.4 발행완료 카드
카드 UI는 버튼을 과도하게 늘리지 않고 깔끔하게 유지한다.

주요 버튼:
- 편집하기
- 초대장 보기
- 공유하기

`공유하기` 내부:
- 링크 복사
- QR 코드
- 카카오톡 공유(향후 연동)

- 이미 발행된 초대장에는 링크 복사 기능이 반드시 제공되어야 한다.
- PC/모바일 공통 원칙으로 적용한다.
- 카드에 만료 예정일/남은 기간 안내를 표시할 수 있다.

### 12.5 만료 카드
- 상태: 만료
- 공개 URL 비활성화 안내
- 데이터 삭제까지 남은 기간 표시
- 미리보기
- 보관기간 연장

### 12.6 여러 초대장
- 한 계정에서 여러 개의 초대장을 만들 수 있다.
- 카드 목록 방식으로 관리한다.
- 웨딩, 돌잔치, 생일, 파티 등 서로 다른 행사 초대장을 함께 관리 가능해야 한다.

## 13. 하객 관리

### 13.1 기본 구조
- RSVP와 방명록을 `하객 관리` 한 화면에서 탭으로 제공한다.
- 여러 초대장이 있으면 상단에서 관리할 초대장을 선택한다.
- 기본적으로 발행된 초대장을 대상으로 한다.

### 13.2 RSVP 관리
- 전체 / 참석 / 불참 / 미정 요약
- 응답자 목록
- 참석 인원 표시
- 전체/참석/불참/미정 필터
- 최신 응답을 확인할 수 있도록 한다.
- 초대장 소유자만 해당 RSVP 데이터를 조회할 수 있다.

향후 기능:
- 신랑측/신부측 필터
- 성인/아동
- 식사 여부
- RSVP Excel 다운로드

### 13.3 방명록 관리
- 작성자 이름
- 메시지
- 작성일
- 초대장 소유자가 부적절한 방명록을 삭제할 수 있도록 한다.

### 13.4 기능 OFF 상태
- RSVP OFF: 해당 기능을 사용하지 않는다는 안내
- 방명록 OFF: 해당 기능을 사용하지 않는다는 안내

### 13.5 Empty State
발행된 초대장이 없는 경우:
- `아직 관리할 초대장이 없습니다.`
- `초대장을 발행하면 참석 여부와 방명록을 여기서 확인할 수 있어요.`
- 초대장 만들기 버튼 제공

제작중 초대장만 있는 경우:
- 제작중 초대장을 보여주고 하객 관리는 발행 후 시작된다는 안내
- `초대장 계속 만들기` 제공

## 14. 관리자

향후 관리자 영역에서 다음을 관리할 수 있도록 한다.
- 회원
- 전체 초대장
- 템플릿
- 결제/환불
- 신고/문의
- 통계
- 보관/만료/삭제
- 공지

- 관리자 메뉴를 숨기는 것만으로 보안을 처리하지 않는다.
- 서버 권한 및 RLS에서 관리자 여부를 검증한다.

## 15. 결제 기본 원칙

- 초기에는 하나의 PG를 우선 연동하는 방향을 검토한다.
- 주문 → PG 결제 → 승인 → 서버 검증 → DB 결제완료 → 서비스 권한 부여 흐름을 사용한다.
- 클라이언트 결과만 믿지 않고 서버에서 결제를 검증한다.
- 중복 결제, 실패, 취소, 환불, 웹훅, 금액 변조 등을 고려한다.
- 결제/환불 세부 정책과 PG는 추후 확정한다.
- 보관기간 연장 역시 결제 상품으로 확장 가능하게 한다.

## 16. 개발/확장 원칙

- 기존 정상 기능을 우선 보존한다.
- 행사 종류를 추가할 때 코드 곳곳에 무분별한 `if wedding` 하드코딩을 늘리지 않는다.
- Event Type → Field Definition → Editor 구조로 확장 가능한 방향을 우선한다.
- 템플릿 변경은 콘텐츠 데이터를 파괴하지 않는다.
- 외부 API 코드는 가능한 독립적으로 관리한다.
- PG, 로그인 방식, 지도 서비스 변경/추가가 기존 기능에 미치는 영향을 최소화한다.
- 향후 Android/iOS 앱에서도 가능한 한 동일한 Supabase 데이터/백엔드 구조를 활용한다.
