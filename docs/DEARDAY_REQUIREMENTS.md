# DearDay 개발 요구사항 정의서

> 상태: 핵심 기획 확정 / 세부 구현 전 지속 업데이트
> 목적: DearDay의 제품·기능·개발 기준을 한 곳에 관리하고, 이후 Codex 개발 및 구현 누락 점검의 기준 문서로 사용한다.

## 1. 서비스 개요

### 1.1 서비스명 / 정체성
- 서비스명: **DearDay**.
- 웨딩 전용이 아니라 다양한 행사를 위한 **모바일 초대장 제작 플랫폼**이다.
- 결혼식을 초기 핵심 상품으로 시작하되 돌잔치, 생일, 기념일, 집들이, 졸업, 기업/단체 행사, 파티, 기타 행사로 확장한다.
- 전문 디자인/개발 지식 없이 템플릿을 선택하고 필요한 정보만 입력해 고급스러운 모바일 초대장을 제작·공유할 수 있게 한다.
- 모바일 환경 최우선, 웹 우선 개발 후 Android/iOS 확장 가능하게 한다.
- 메뉴와 제작 흐름은 최대한 단순하게 유지한다.

### 1.2 브랜드 / 가격 포지셔닝
- 핵심 방향: **가격은 부담 없게, 결과물은 고급스럽게.**
- `싼 초대장`보다 `합리적인 가격으로 제공하는 고급 모바일 초대장`으로 포지셔닝한다.
- 모든 일반 템플릿은 초기 동일가격 정책.
- 정확한 판매가격은 출시 전 최종 확정한다.
- 결제한 실제 초대장 URL에는 외부 광고를 노출하지 않는다.

### 1.3 무료 제작 / 유료 발행
- 템플릿 탐색, 제작, 임시저장, 미리보기까지 무료.
- 실제 발행 및 전용 URL 활성화 시 유료.
- 결제 전 미리보기에는 화면을 방해하지 않는 수준의 `DearDay Preview` 워터마크를 표시하고 결제 완료 후 제거한다.
- 초기에는 무료 발행 플랜을 핵심 전략으로 운영하지 않는다.

### 1.4 브랜드 스토리
메인 홈페이지에 `DearDay가 시작된 이유` 섹션을 배치한다.

> **특별한 날을 준비하는 마음에  
> 가격이 부담이 되지 않았으면 했습니다.**
>
> DearDay는 좋은 디자인과 필요한 기능을 담으면서도  
> 누구나 부담 없이 사용할 수 있는  
> 모바일 초대장을 만들고자 시작되었습니다.
>
> **가격은 가볍게, 특별한 날의 품격은 그대로.**
>
> 당신의 소중한 날에 DearDay가 함께하겠습니다.

## 2. 시스템 구성 / 개발 원칙

- Frontend / Web Framework: Next.js.
- Source Code: GitHub.
- Hosting / Deployment: Vercel.
- Database / Authentication / Storage: Supabase.
- 외부 서비스: Kakao, Naver, 향후 PG 결제 API.
- GitHub `main`을 운영 기준으로 사용하고 Vercel 자동 배포.
- Secret/Service Role Key 등은 환경변수로 관리하고 클라이언트/GitHub에 직접 저장하지 않는다.
- Supabase RLS로 사용자별 데이터 접근을 제어한다.
- 기존 정상 기능을 불필요하게 변경하지 않고 Codex에는 작은 작업 단위로 지시한다.
- Codex 작업 전 항상 `docs/DEARDAY_REQUIREMENTS.md`를 먼저 확인한다.

개발 흐름:
`요구사항 정의 → ChatGPT 설계/검토 → Codex 최소 범위 개발 → 테스트 → GitHub → Vercel → 운영환경 테스트`

## 3. 회원 / 인증 / 계정

- 제작/관리는 회원 로그인이 필요하며 발행 초대장은 하객이 로그인 없이 열람한다.
- RSVP/방명록은 하객 회원가입 없이 이용 가능.
- MVP 소셜 로그인: Kakao, Naver. 향후 Google/Apple/이메일 확장 가능.
- 동일 소셜 계정 반복 로그인으로 중복 회원이 생성되지 않게 한다.
- 로그인 세션 유지 및 로그아웃 제공.

### 3.1 회원탈퇴
- 활성화된 발행완료 초대장이 있으면 즉시 탈퇴 불가.
- 해당 초대장 이용기간 종료 후 사용자가 직접 탈퇴 가능하며 탈퇴 예약은 구현하지 않는다.
- 탈퇴 후 동일 소셜 계정 재가입 가능하나 신규 회원으로 처리하고 이전 데이터는 복구하지 않는다.
- 불필요한 개인정보는 삭제/비식별화하고 법령상 보관이 필요한 거래기록만 필요한 기간 별도 보관한다.

### 3.2 세션 만료
- 편집 중 세션 만료 시 작성 화면을 즉시 버리지 않는다.
- 저장 시 로그인이 만료되었다면 재로그인을 안내하고 현재 작성 내용을 최대한 유지한다.
- 재로그인 성공 후 원래 작업으로 돌아와 저장할 수 있게 한다.

## 4. 템플릿 / 행사 종류

### 4.1 핵심 구조
- 템플릿 = 어떻게 보이는가(Visual Design).
- 행사 종류(Event Type) = 어떤 콘텐츠/편집항목이 필요한가.
- 초대장(Event Instance) = 사용자가 실제 제작한 하나의 초대장.
- 템플릿은 가능한 한 행사 종류와 분리해 공통 디자인으로 재사용한다.
- 템플릿 변경은 행사 데이터를 새로 만드는 것이 아니라 디자인만 교체한다.

### 4.2 제작 진입
- 디자인부터: `템플릿 → 행사 종류 → 편집 → 미리보기 → 결제 → 최종 확인 → 발행`.
- 행사부터: `행사 종류 → 템플릿 → 편집 → 미리보기 → 결제 → 최종 확인 → 발행`.
- 두 경로는 동일 편집기로 합류한다.

### 4.3 가격
- 공통 기본 발행가격을 사용한다.
- **정상가 + 실제 판매가**를 분리 관리하여 할인/프로모션 표현이 가능하게 한다.
- 가격은 코드 하드코딩 대신 운영 설정값으로 관리한다.
- 향후 프리미엄 템플릿에 대비해 개별가격 Override가 가능하게 설계한다.

### 4.4 템플릿 변경
- 결제 전, 결제 후 발행 전, 발행 후 이용기간 중 모두 변경 가능.
- 초기 동일가격 정책에서는 추가 결제 없음.
- 기존 URL, 입력내용, 사진, RSVP, 방명록 유지.
- 마케팅 표현은 `무제한 변경`보다 `이용기간 동안 자유롭게 변경`을 사용한다.

### 4.5 관리자 템플릿 운영
- 기존 공통 `InvitationRenderer`를 유지하고, 일반적인 신규 시각 디자인은 가능한 한 DB Config + Storage Asset + 관리자 페이지에서 등록·수정한다.
- 공통 규격으로 표현할 수 없는 새로운 기능, 완전히 새로운 레이아웃/인터랙션, 새로운 Renderer 능력만 코드 개발 대상으로 분리한다.
- 관리자 관리항목: 템플릿명, stable template key, 스타일 카테고리, 썸네일, 긴 판매 미리보기, Asset, 배경/Hero, 장식, typography/색상, 섹션 구성, 연출 설정, 노출/판매 상태, 추천, NEW, 정렬순서, 가격 방식.
- 템플릿은 stable `template_id`와 version을 가지며 실질적 디자인 변경은 Draft/새 버전 기반으로 관리한다. 기존 발행본은 사용한 버전에 고정한다.
- 판매용 Asset은 기본 7종 체계를 출발점으로 하되 개수를 하드코딩하지 않는다. 전체 Background와 Hero Background는 같은 Asset을 재사용하거나 필요 시 서로 다른 Background Asset을 사용할 수 있다.
- 템플릿 삭제 대신 **숨김/판매중지**를 기본으로 하며 기존 제작·발행 초대장과 참조 중인 버전/Asset을 보호한다.
- 심각한 보안/장애 상황은 별도 긴급조치 가능.
- 스타일 카테고리 예: 심플, 모던, 로맨틱, 포토, 클래식.
- 세부 템플릿 규격과 현재 Config 구현 단계는 `docs/DEARDAY_TEMPLATE_SPEC.md`를 기준으로 한다.

## 6. 데이터 구조 기본 원칙

- 행사별 별도 본체 테이블을 만들지 않고 공통 `events` 구조와 `event_kind`를 사용한다.
- 행사별 입력 차이는 공통 데이터 + 유연한 설정 데이터(JSONB 등)를 활용한다.
- 사진, RSVP, 방명록, 장소 등 반복/관계 데이터는 별도 테이블을 사용한다.
- 템플릿 변경 시 이벤트/하객 데이터를 새로 생성하지 않는다.
- 결제 상태는 최소 `미결제 → 결제완료/미발행 → 발행완료`, 환불/만료 등 확장 상태를 명확히 구분한다.

## 7. 초대장 편집 공통 원칙

- 한 페이지 편집 + 섹션별 접기/펼치기.
- 항상 필수 / 기능 ON 시 조건부 필수 / 선택 항목을 구분한다.
- 임시저장/미리보기는 필수항목 누락 상태에서도 가능.
- 최종 발행 시에만 필수값을 검사하고 누락 목록을 명확히 안내한다.
- OFF 기능은 검증과 공개 화면에서 제외한다.
- Event Type → Field Definition → Editor 구조로 확장한다.
- 상단/하단에서 `저장하기`, `미리보기`를 명확히 제공한다.
- 제작 화면에 결제 버튼을 계속 노출하지 않고 미리보기의 `발행 준비하기`에서 결제로 진입한다.

### 7.1 저장 / 네트워크 오류
- 저장 성공/실패를 명확히 표시하며 실패를 성공처럼 표시하지 않는다.
- 저장되지 않은 변경사항이 있을 때 페이지 이탈 경고.
- MVP는 명시적 저장을 기본으로 하고 자동저장은 추후 확장 가능.

### 7.2 동시 편집 충돌
- 실시간 공동편집은 구현하지 않는다.
- 다른 기기/탭에서 먼저 저장되어 버전이 바뀐 경우 오래된 화면의 저장을 무조건 덮어쓰지 않고 충돌을 감지해 최신 내용을 다시 불러오도록 한다.

### 7.3 사진 업로드 실패
- 여러 사진 중 일부 실패 시 성공한 사진은 유지하고 실패한 사진만 재시도한다.
- 업로드 중/실패 사진이 남아 있으면 최종 발행을 차단한다.

## 8. 행사별 편집항목 / 웨딩 v1.0

- 기본정보: 신랑/신부 이름, 예식 날짜/시간, 예식장명 필수. 상세정보/주소/지도 선택.
- 대표사진/Hero: ON/OFF, 사진형/타이포형/일러스트형 지원 가능.
- 인사말: 제목/내용 선택 입력.
- 가족/연락처: ON/OFF, 입력된 정보만 표시.
- 갤러리: ON/OFF, 사진 추가/삭제/순서변경, 현재 최대 20장 기준.
- 마음 전하기: ON/OFF, ON 시 계좌별 은행/계좌번호/예금주 필수.
- RSVP: ON/OFF.
- 방명록: ON/OFF.

## 9. 공개 초대장 / 미리보기

- 모바일 우선, 깨끗하고 고급스러운 디자인.
- 콘텐츠와 템플릿 디자인 분리.
- 미리보기는 실제 하객 화면과 최대한 동일하게 표시한다.
- 결제 전 미리보기에는 `DearDay Preview` 워터마크.
- 미리보기 단계에서는 공개 URL 미활성.
- 선택항목 미입력 시 자연스럽게 숨긴다.
- 공개 초대장은 모바일 가로 overflow가 발생하지 않도록 모든 사용자 입력 텍스트/URL/이미지를 반응형으로 처리한다.
- 갤러리 썸네일 클릭 시 한 장 전체보기, 이전/다음, 닫기 제공. 추가 확대/핀치줌은 제공하지 않는다.

## 10. 결제 / 발행 / 수정

### 10.1 기본 흐름
`무료 제작 → 저장/미리보기 → 발행 준비하기 → 필수값 검사 → 결제 → 결제완료/미발행 → 최종 미리보기 → 초대장 발행하기 → URL 활성화 → 공유`

- 결제완료와 발행완료를 분리한다.
- 결제 성공만으로 URL을 자동 활성화하지 않는다.
- 사용자가 최종 `초대장 발행하기`를 직접 누른다.
- 최초 발행 이후 초대장 URL은 변경하지 않는다.
- 발행 후에도 이용기간 내 내용/템플릿 수정 가능.

### 10.2 행사 취소 / 복원
- 발행 초대장에서 `행사 취소하기` 제공.
- 확인 팝업 후 취소 상태로 전환하며 삭제하지 않는다.
- 기존 URL 유지, 일반 본문은 숨기고 행사 취소 안내를 표시한다.
- 기존 내용/사진/RSVP/방명록은 보존.
- `초대장 다시 활성화`로 동일 URL/데이터 복원 가능.

### 10.3 행사일 변경
- 행사 연기는 기존 날짜/시간 수정으로 처리한다.
- 변경된 행사일 기준으로 이용 종료일을 다시 계산하되 이미 결제/발행으로 확보한 이용 종료일보다 짧아지지 않게 한다.
- 악용 방지를 위해 행사일은 최초 발행일 기준 최대 1년 범위 내에서만 변경 가능하게 한다.

## 11. 이용기간 / 보관 / 자동삭제

- 기본 공개기간: 행사일 +14일.
- 이후 URL 비활성, 즉시 삭제하지 않는다.
- 만료 후 30일 유예기간 동안 데이터/사진 유지.
- 유예기간 중 유료 보관 연장/복구 가능.
- 연장 시 기존 URL/내용/사진/RSVP/방명록 유지.
- 보관 연장은 30일 단위이며 반복 구매 가능.
- 정확한 연장 가격은 출시 전 결정.
- 30일 유예 종료 후 관리자 승인 없이 자동삭제.
- 삭제 실패 건만 관리자 확인/재처리.
- 법령상 거래기록은 별도 보관.

### 11.1 만료 / 삭제 알림
- MVP는 사이트 내부 알림만 사용한다.
- 만료 7일 전, 1일 전 알림.
- 최종삭제 7일 전, 1일 전 알림.
- 같은 초대장/같은 알림유형 중복 발송 방지.
- 이미 연장/삭제/상태변경된 경우 불필요한 예약 알림은 취소/무효화한다.

## 12. 마이페이지

메뉴: 내 초대장 / 하객 관리 / 결제·보관 / 문의내역 / 계정·내 정보.

### 12.1 내 초대장
- 제작중 / 결제완료·미발행 / 발행완료 / 만료 상태로 관리.
- **초대장 제작본 단위**로 카드 표시한다. 하나의 제작본에서 템플릿만 변경하는 것은 새 카드가 아니다.
- 새 초대장을 각각 만들고 저장하면 제작중 카드가 각각 생성된다.
- 제작중: 계속 만들기 / 미리보기 / 삭제.
- 결제완료·미발행: 편집 / 미리보기 / 발행 / 조건 충족 시 환불 요청.
- 발행완료: 편집하기 / 초대장 보기 / 공유하기.
- 만료: 미리보기 / 삭제예정일 / 보관기간 연장.
- `+ 새 초대장 만들기` 제공.
- 초대장이 없으면 빈 상태 안내 + 제작 CTA.

### 12.2 하객 관리
- 초대장 선택 + RSVP / 방명록 탭.
- RSVP: 전체/참석/불참 등 필터, 응답자/참석인원 요약.
- RSVP 목록: 이름, 측 구분(사용 시), 참석여부, 참석인원, 연락처(수집 시), 전달사항, 제출일.
- **MVP부터 RSVP 엑셀 다운로드 제공**, 현재 필터 결과도 다운로드 가능하게 한다.
- 방명록: 작성자/메시지/작성일/소유자 삭제. MVP 방명록 엑셀 다운로드는 제공하지 않는다.
- 신규 RSVP/방명록 표시 가능.

### 12.3 결제 / 보관
- 초대장별 카드로 관리.
- 제작중: 미결제 + 계속 만들기.
- 결제완료·미발행: 결제일/금액/상태 + 발행 + 조건 충족 시 환불 요청.
- 발행완료: 결제금액/최초 발행일/행사일/이용 종료일.
- 만료/유예: URL 비활성/삭제예정일/남은 기간 + 30일 연장.
- MVP부터 PG가 제공하는 **결제내역/영수증 확인** 기능을 제공한다.

### 12.4 문의내역
- 목록: 문의유형/제목/등록일/답변상태(답변대기/답변완료).
- 상세: 문의 원문/등록일/관리자 답변/답변일.
- `새 문의하기` 제공.
- 문의 등록 후 고객/관리자 모두 원문 수정·삭제 불가.

### 12.5 계정 / 내 정보
- 이름/닉네임, 로그인 방식, 가입일, DearDay에서 별도 수집한 정보가 있으면 해당 정보 표시.
- 로그아웃 / 회원탈퇴.
- 소셜 로그인 중심이므로 DearDay 자체 비밀번호 변경 메뉴는 MVP에 두지 않는다.

## 13. RSVP

- 하객 로그인 없이 제출 가능.
- 이름 + 참석/불참 필수.
- 참석인원 선택 가능.
- 연락처/메시지는 선택.
- 제출 완료 후 **개인 수정 링크**를 발급해 같은 링크에서 응답 수정 가능.
- 회원가입/비밀번호는 요구하지 않는다.
- MVP에서 동일인 자동판단/중복 병합은 하지 않고 별도 응답으로 저장한다.
- 소유자가 하객관리에서 필요 시 정리한다.
- RSVP는 행사 시작 시각에 자동 마감한다.
- 마감 후 기존 응답은 보존/조회 가능하나 신규 제출/수정 불가.
- 소유자가 RSVP ON/OFF 가능.

## 14. 방명록

- 초대장 소유자가 방명록 기능을 ON/OFF 할 수 있으며 기본값은 ON이다.
- OFF 시 공개 초대장에서 방명록 작성폼과 목록을 숨기고 신규 작성을 차단하지만 기존 데이터는 삭제하지 않는다. 다시 ON 하면 기존 글을 복원한다.
- 하객 로그인 없이 작성 가능하다.
- 작성 항목은 이름(필수, 최대 20자), 메시지(필수, 최대 200자), 삭제 비밀번호(필수, 숫자 4자리)다.
- 텍스트만 허용한다.
- 삭제 비밀번호 원문은 저장하지 않고 안전한 해시 방식으로 저장한다.
- 작성자는 자신이 설정한 4자리 비밀번호를 입력해 본인 글을 삭제할 수 있다. 비밀번호가 틀리면 삭제하지 않는다.
- 작성자 본인의 글 수정 기능은 MVP에서 제외한다.
- 초대장 소유자는 자신의 초대장에 작성된 방명록 글을 비밀번호 없이 삭제할 수 있다.
- 삭제는 확인 절차 후 처리한다.
- 방명록 작성은 공개 초대장 URL이 활성 상태인 동안 가능하며 기본 행사일 +14일 또는 유료 연장기간을 따른다. URL 비활성 상태에서는 신규 작성을 차단한다.
- MVP 기본 도배 방지로 공개 작성/삭제 요청에 간단한 rate limit을 적용한다.
- CAPTCHA는 기본 적용하지 않고 필요 시 추후 추가한다.

## 15. 공유

- MVP부터 링크 복사 + QR 코드 + 모바일 기본 공유(Web Share API 가능 환경) 제공.
- 카카오톡 전용 공유 API는 향후 기능으로 두되 구조 확장 가능하게 한다.
- 공유는 초대장 자체 기능으로 제공하며 공유 수단이 바뀌어도 URL은 동일하게 유지한다.

## 16. 결제 / 환불 / 외부 판매채널

### 16.1 결제 구조
- 초기 하나의 PG를 우선 연동하되 **실제 PG 연동은 개발 후반부**에 진행한다.
- 그 전에는 개발용 가결제로 결제완료/미발행 → 발행 전체 흐름을 검증한다.
- 실제 PG로 교체하기 쉽도록 결제 상태/서버 인터페이스를 분리한다.
- 실제 연동 시 주문 → PG → 승인 → 서버검증 → DB 결제완료 순서를 지킨다.
- 클라이언트 결제 성공만 신뢰하지 않는다.

### 16.2 자동환불
조건: 결제완료 + 최초발행 전 + 결제일 7일 이내 + 기존 환불/취소 아님.

`사용자 요청 → 서버 조건검증 → PG 취소 API → PG 성공확인 → DB 환불완료`

- PG 성공 전 DB를 환불완료로 변경하지 않는다.
- 조건 불충족/PG 오류/발행 후/기간초과/분쟁은 관리자 검토.
- 성공 후 초대장 콘텐츠는 보존하고 결제 전 상태로 복귀.

### 16.3 외부 판매채널 확장
- DearDay 자체 PG가 기본.
- 향후 네이버 스마트스토어 등 외부 채널 결제도 같은 제작/발행 시스템 사용.
- `payment_source` 등으로 결제 출처 구분.
- 외부 주문 인증 후 내부 `결제완료/미발행` 상태로 통합.
- 외부 주문번호/거래식별자 중복 사용을 방지한다.
- 공식 주문 API 사용 시 서버에서 검증하며 클라이언트 입력만으로 결제완료 권한을 주지 않는다.
- MVP에서 실제 네이버 연동은 필수 아님.

## 17. 사이트 내부 문의 / 고객지원

- 이용안내 → 문의하기 → 문의유형(결제/환불, 초대장 이용, 오류/장애, 기타) + 제목 + 내용 → 등록.
- 마이페이지 문의내역에서 확인.
- 관리자: 전체/답변대기/답변완료 → 상세 → 답변 등록.
- 문의 원문은 등록 후 수정/삭제 불가.
- **관리자 답변도 등록 후 수정/삭제 불가**. 잘못된 답변은 추가 답변으로 정정하고 기존 이력 유지.
- 답변 등록 시 고객 사이트 내부 알림 생성.
- MVP 실시간 채팅은 필수 아님.

## 18. 관리자

### 18.1 권한 구조
- `user / admin / super_admin`.
- MVP `super_admin`은 **1명만 유지**.
- 초기 1명을 DB에서 지정하고 이후 super_admin만 admin 추가/해제 가능.
- admin은 자기 권한 상승 불가.
- API/서버/RLS에서 실제 권한 검증.
- 권한 변경 Audit Log 기록.

### 18.2 대시보드
- 오늘 방문자/가입/제작시작/결제금액/발행/환불/미답변 문의.
- 전환 퍼널: 방문 → 제작시작 → 로그인/가입 → 제작 → 결제 → 발행.
- 환불실패/확인필요 결제/삭제실패/미답변 문의/숨김 관련 등 운영 확인 필요 영역.
- 숫자 클릭 시 해당 메뉴의 필터된 목록으로 이동.

### 18.3 회원 관리
- 목록: 이름/닉네임, 가입방식, 가입일, 초대장 수, 결제 수, 상태.
- 상세: 기본정보, 초대장, 결제/환불, 문의, 계정상태.
- 관리자는 이용정지/정지해제 가능하며 정지 사유 필수.
- 회원 이용정지와 초대장 숨김은 별도 상태로 관리한다.
- 회원 정지만으로 이미 발행된 초대장을 자동 숨김하지 않는다.
- 인증토큰 등 민감한 내부정보는 노출하지 않는다.

### 18.4 초대장 관리
- 전체 목록/상태/행사종류/소유자/템플릿/행사일/발행일/이용종료일/결제상태/미리보기.
- 관리자는 고객 콘텐츠를 직접 수정하지 않는다.
- 신고/약관 위반 등은 `숨김/숨김해제`로 조치하고 사유 필수.
- 관리자 강제삭제 기능은 두지 않는다.
- 숨김 해제 시 같은 URL/기존 데이터 유지.
- 조치 Audit Log 기록.

### 18.5 템플릿 관리
- 템플릿명/내부코드/카테고리/썸네일/미리보기/노출/추천/NEW/정렬/지원섹션/가격방식 관리.
- 내부코드는 자동생성 또는 개발자 지정, 관리자 조회 위주.
- 디자인 자체는 코드에서 개발.
- 삭제 대신 숨김.
- MVP 복제 기능 제외.

### 18.6 결제 / 환불 관리
- 오늘/월 결제금액, 환불금액, 관리자 확인 필요 요약.
- 결제번호/회원/초대장/금액/수단/결제일/최초발행 여부/상태 조회.
- 정상 자동환불은 시스템 처리.
- 예외/실패 건 관리자 확인.
- **수동 환불 실행은 super_admin만 가능**.
- 수동 환불의 관리자/시간/금액/사유 Audit Log 기록.

### 18.7 보관 / 만료 관리
- 이용중/만료·유예/삭제예정/처리중/완료/실패 조회.
- 정상 자동처리는 관리자 승인 불필요.
- 삭제 실패만 관리자 확인.
- 장애 등 보상 목적 무료 연장은 **super_admin만 가능**, 연장일수+사유 필수, Audit Log 기록.

### 18.8 문의 관리
- 전체/답변대기/답변완료 필터.
- 원문 수정/삭제 불가.
- 관리자 답변도 수정/삭제 불가, 추가답변으로 정정.

### 18.9 서비스 설정
- 정상가/판매가/보관연장 가격 등 가격 설정은 super_admin 수정 가능.
- 공개기간 +14일, 유예기간 30일, 자동삭제 같은 핵심 운영정책은 MVP에서 조회만 가능.

## 19. 보안 / 운영 예외처리

- 권한은 UI 숨김이 아니라 서버/API/RLS에서 검증한다.
- 결제/환불/권한변경/초대장 숨김/보상연장 등 중요 조치는 Audit Log.
- 과도한 요청/도배에는 기본 rate limit 적용.
- 결제 상태가 불명확하면 PG 결과를 재확인하며 임의 성공처리하지 않는다.
- 발행 상태가 불명확하면 서버의 실제 상태를 재확인한다.
- 상태 확인 전 중복결제/중복발행을 차단한다.
- 자동복구 불가능한 건만 관리자 확인 필요로 전환한다.
- 계획 점검 중에는 가능하면 결제/발행을 비활성화하고 안내한다.
- 제작/관리 기능 장애와 이미 발행된 공개 초대장 열람을 최대한 분리해 공개 초대장의 가용성을 우선한다.

## 20. 화면별 최종 기능정의

### 20.1 홈페이지
`상단 메뉴 → Hero → 행사 종류 선택 → 추천 템플릿 → DearDay가 시작된 이유 → 이용방법 → 최종 CTA → Footer`
- Hero: `[초대장 만들기] [템플릿 보기]`.
- 최종 CTA에서 다시 제작 진입 유도.
- Footer: 사업자정보, 고객센터, 이용약관, 개인정보처리방침 등.
- 비회원도 홈/템플릿/이용안내 탐색 가능.

### 20.2 템플릿 목록 / 미리보기
- 카테고리 필터: 전체/심플/모던/로맨틱/포토/클래식 등.
- 카드: 미리보기 이미지 + 템플릿명 + NEW/추천.
- 상세는 실제 모바일 초대장 형태의 긴 미리보기 + `[이 템플릿으로 만들기]`.
- 비회원도 목록/미리보기 가능.
- 동일가격이므로 카드마다 가격을 과도하게 반복하지 않고 공통 가격 안내 영역 사용.

### 20.3 제작 화면
- 한 페이지 + 섹션 접기/펼치기.
- 기본정보, 대표사진, 인사말, 가족/연락처, 갤러리, 마음 전하기, RSVP, 방명록 등 행사 종류에 맞게 구성.
- 저장/미리보기 중심, 결제는 미리보기의 `발행 준비하기`에서 진입.

### 20.4 미리보기
- 실제 하객 화면과 최대한 동일하게 표시.
- 결제 전에는 `DearDay Preview` 워터마크.
- 공개 URL은 아직 활성화하지 않는다.
- `[계속 수정하기] [발행 준비하기]`.
- 미리보기는 결제 전 횟수 제한 없이 무료.

### 20.5 결제 → 최종 발행
- 결제 안내: 정상가, 판매가, 이용기간, 환불정책, 결제하기.
- 결제 성공 후 `아직 공개되지 않았습니다` 안내 + `[최종 미리보기] [초대장 발행하기]`.
- 최종 발행 확인 후 URL 활성화 → `[초대장 보기] [공유하기]`.

## 21. 개발 우선순위 — 최종 확정

실제 PG 연동은 핵심 기능이 안정된 뒤로 미룬다. 단, 결제 상태/인터페이스는 처음부터 실제 PG로 교체 가능한 구조로 설계한다.

### 1단계 — 공통 UI 뼈대 + 핵심 제작 기반
- 홈, 상단 메뉴, 버튼, 카드, 폰트, 여백, 모바일 기본 레이아웃 등 DearDay 공통 디자인 시스템을 먼저 잡는다.
- 이 단계의 화면 디자인은 출시 수준의 완성본이 아니라 약 70~80% 수준의 기본 UI를 목표로 한다.
- 로그인 → 행사종류 → 템플릿 → 제작/저장 → 미리보기 → 수정의 핵심 흐름을 구축한다.

### 2단계 — 실제 판매용 템플릿 2~3개 + 핵심 제작 기능 검증
- 임시 샘플만으로 개발하지 않고 실제 판매에 사용할 웨딩 템플릿 2~3개를 먼저 코드 컴포넌트로 구현한다.
- 실제 템플릿으로 사진 비율, 섹션 ON/OFF, 편집 데이터 연결, 미리보기, 모바일 반응형을 검증한다.
- 템플릿 변경 시 기존 입력 내용/사진/RSVP/방명록 데이터가 유지되는 구조를 검증한다.
- 결제 전 미리보기 `DearDay Preview` 워터마크를 적용한다.

### 3단계 — 발행/공유 흐름을 가결제로 구현
- 실제 PG 없이 개발용 결제완료 처리.
- `결제완료/미발행 → 최종 발행 → URL 활성화 → 공유/QR` 전체 흐름 먼저 완성.
- 나중에 실제 PG만 교체/연결할 수 있도록 결제 상태와 서버 인터페이스를 분리.

### 4단계 — 하객 기능
`RSVP → 수정 링크 → 하객관리 → 엑셀 다운로드 → 방명록`

### 5단계 — 마이페이지 / 보관 / 알림 + 관리자
- `내 초대장 → 결제/보관 → 만료 → 30일 유예 → 연장 → 자동삭제 → 내부 알림`.
- 관리자: 대시보드 → 회원 → 초대장 → 템플릿 → 문의 → 결제관리 → 보관/만료 → 권한/Audit Log.
- 관리자 화면은 기능성과 운영 효율을 우선하고 과도한 시각 디자인 작업은 하지 않는다.

### 6단계 — 판매용 템플릿 확대 + 전체 고객 UI 최종 마감
- 실제 판매용 템플릿 수를 확대한다.
- 홈/템플릿 목록/제작/미리보기/공개 초대장/마이페이지 등 고객이 보는 주요 화면을 출시 수준으로 최종 디자인한다.
- PC/모바일 반응형, 폰트, 간격, 이미지 품질, 세부 인터랙션/애니메이션 등을 최종 조정한다.
- 디자인 리소스는 관리자 화면보다 고객이 직접 보는 화면에 우선 배분한다.

### 7단계 — 실제 PG 결제 연동
`실제 결제 → 서버 검증 → 환불 API → 중복결제 방지 → DB 반영 실패 복구 → 보관 연장결제`

### 8단계 — 안정화 / 출시 준비
`전체 시나리오 테스트 → 모바일/PC → RLS/보안 → 개인정보/약관 → 성능 → 실제 PG 운영환경 테스트 → 출시`

## 22. 구현 점검 / 테스트 기준

현재 GitHub 구현을 이 문서와 비교하여 `구현완료 / 수정필요 / 미구현 / 향후기능`으로 GAP 분석한다.

핵심 테스트:
- 비회원 홈/템플릿 탐색.
- 디자인 우선/행사 우선 제작 진입 후 동일 편집기로 합류.
- 여러 초대장 제작본 저장/목록 표시.
- 임시저장/미리보기/워터마크.
- 실제 판매용 템플릿 2~3개에서 사진 비율/섹션/반응형/데이터 연결 검증.
- 템플릿 변경 시 콘텐츠 유지.
- 최종 발행 필수값 검증 및 과거 행사일 차단.
- 가결제 및 향후 실제결제 → 결제완료/미발행 → 최종 발행.
- 최초 발행 후 URL 고정, 같은 URL로 내용/템플릿 변경.
- 행사일 변경/1년 제한/유료 확보기간 보호.
- RSVP 제출/수정링크/자동마감/엑셀.
- 방명록 작성/삭제/ON-OFF/도배 방지.
- 공유 링크/QR/기본 공유.
- 행사 취소/복원.
- 행사일 +14일 → 30일 유예 → 반복 연장 → 자동삭제.
- 만료/삭제 사전 알림.
- 중복결제, PG 성공-DB 실패, 장애 복구.
- 회원 이용정지와 초대장 숨김 분리.
- 관리자 권한/RLS/Audit Log.
- 문의 등록/답변/추가 정정 이력.
- 외부 판매채널 구매 인증 확장성.

## 23. 현재 작업 원칙

- 이 문서를 DearDay 개발의 최신 기준으로 사용한다.
- 기능 개발 전 필요한 요구사항을 먼저 확정한다.
- 요구사항이 변경되면 충돌하는 이전 정책을 함께 수정하여 최신 확정 정책만 남긴다.
- Codex에는 전체 요구사항을 한 번에 구현시키지 않고 작은 작업 단위로 나눈다.
- 각 단계 구현 후 테스트하고 다음 단계로 진행한다.
- 다음 개발 단계는 **현재 GitHub 코드와 본 요구사항의 GAP 분석** 후 작업목록을 만드는 것이다.
