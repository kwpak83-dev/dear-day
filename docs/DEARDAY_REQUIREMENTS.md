# DearDay 개발 요구사항 정의서

> 상태: 핵심 기획 확정 / 세부 구현 전 지속 업데이트
> 목적: DearDay의 제품·기능·개발 기준을 한 곳에 관리하고, 이후 Codex 개발 및 구현 누락 점검의 기준 문서로 사용한다.

## 1. 서비스 개요

### 1.1 서비스명 / 정체성
- 서비스명: **DearDay**.
- 웨딩 전용이 아니라 다양한 행사를 위한 **모바일 초대장 제작 플랫폼**이다.
- 결혼식을 초기 핵심 상품으로 시작하되 돌잔치, 생일, 기념일, 집들이, 졸업, 기업/단체 행사, 파티, 기타 행사로 확장한다.
- 전문 디자인/개발 지식 없이 템플릿을 선택하고 필요한 정보만 입력해 고급스러운 모바일 초대장을 제작·공유할 수 있게 한다.
- 모바일 환경 최우선, 웹 우선 개발 후 Android/iOS 확장 가능하게 한다.
- 메뉴와 제작 흐름은 최대한 단순하게 유지한다.

### 1.2 브랜드 / 가격 포지셔닝
- 핵심 방향: **가격은 부담 없게, 결과물은 고급스럽게.**
- `싼 초대장`보다 `합리적인 가격으로 제공하는 고급 모바일 초대장`으로 포지셔닝한다.
- 모든 일반 템플릿은 초기 동일가격 정책.
- 정확한 판매가격은 출시 전 최종 확정한다.
- 결제한 실제 초대장 URL에는 외부 광고를 노출하지 않는다.

### 1.3 무료 제작 / 유료 발행
- 템플릿 탐색, 제작, 임시저장, 미리보기까지 무료.
- 실제 발행 및 전용 URL 활성화 시 유료.
- 결제 전 미리보기에는 화면을 방해하지 않는 수준의 `DearDay Preview` 워터마크를 표시하고 결제 완료 후 제거한다.
- 초기에는 무료 발행 플랜을 핵심 전략으로 운영하지 않는다.

### 1.4 브랜드 스토리
메인 홈페이지에 `DearDay가 시작된 이유` 섹션을 배치한다.

> **특별한 날을 준비하는 마음에  
> 가격이 부담이 되지 않았으면 했습니다.**
>
> DearDay는 좋은 디자인과 필요한 기능을 담으면서도  
> 누구나 부담 없이 사용할 수 있는  
> 모바일 초대장을 만들고자 시작되었습니다.
>
> **가격은 가볍게, 특별한 날의 품격은 그대로.**
>
> 당신의 소중한 날에 DearDay가 함께하겠습니다.

## 2. 시스템 구성 / 개발 원칙

- Frontend / Web Framework: Next.js.
- Source Code: GitHub.
- Hosting / Deployment: Vercel.
- Database / Authentication / Storage: Supabase.
- 외부 서비스: Kakao, Naver, 향후 PG 결제 API.
- GitHub `main`을 운영 기준으로 사용하고 Vercel 자동 배포.
- Secret/Service Role Key 등은 환경변수로 관리하고 클라이언트/GitHub에 직접 저장하지 않는다.
- Supabase RLS로 사용자별 데이터 접근을 제어한다.
- 기존 정상 기능을 불필요하게 변경하지 않고 Codex에는 작은 작업 단위로 지시한다.
- Codex 작업 전 항상 `docs/DEARDAY_REQUIREMENTS.md`를 먼저 확인한다.

개발 흐름:
`요구사항 정의 → ChatGPT 설계/검토 → Codex 최소 범위 개발 → 테스트 → GitHub → Vercel → 운영환경 테스트`

## 3. 회원 / 인증 / 계정

- 제작/관리는 회원 로그인이 필요하며 발행 초대장은 하객이 로그인 없이 열람한다.
- RSVP/방명록은 하객 회원가입 없이 이용 가능.
- MVP 소셜 로그인: Kakao, Naver. 향후 Google/Apple/이메일 확장 가능.
- 동일 소셜 계정 반복 로그인으로 중복 회원이 생성되지 않게 한다.
- 로그인 세션 유지 및 로그아웃 제공.

### 3.1 회원탈퇴
- 활성화된 발행완료 초대장이 있으면 즉시 탈퇴 불가.
- 해당 초대장 이용기간 종료 후 사용자가 직접 탈퇴 가능하며 탈퇴 예약은 구현하지 않는다.
- 탈퇴 후 동일 소셜 계정 재가입 가능하나 신규 회원으로 처리하고 이전 데이터는 복구하지 않는다.
- 불필요한 개인정보는 삭제/비식별화하고 법령상 보관이 필요한 거래기록만 필요한 기간 별도 보관한다.

### 3.2 세션 만료
- 편집 중 세션 만료 시 작성 화면을 즉시 버리지 않는다.
- 저장 시 로그인이 만료되었다면 재로그인을 안내하고 현재 작성 내용을 최대한 유지한다.
- 재로그인 성공 후 원래 작업으로 돌아와 저장할 수 있게 한다.

## 4. 템플릿 / 행사 종류

### 4.1 핵심 구조
- 템플릿 = 어떻게 보이는가(Visual Design).
- 행사 종류(Event Type) = 어떤 콘텐츠/편집항목이 필요한가.
- 초대장(Event Instance) = 사용자가 실제 제작한 하나의 초대장.
- 템플릿은 가능한 한 행사 종류와 분리해 공통 디자인으로 재사용한다.
- 템플릿 변경은 행사 데이터를 새로 만드는 것이 아니라 디자인만 교체한다.

### 4.2 제작 진입
- 디자인부터: `템플릿 → 행사 종류 → 편집 → 미리보기 → 결제 → 최종 확인 → 발행`.
- 행사부터: `행사 종류 → 템플릿 → 편집 → 미리보기 → 결제 → 최종 확인 → 발행`.
- 두 경로는 동일 편집기로 합류한다.

### 4.3 가격
- 공통 기본 발행가격을 사용한다.
- **정상가 + 실제 판매가**를 분리 관리하여 할인/프로모션 표현이 가능하게 한다.
- 가격은 코드 하드코딩 대신 운영 설정값으로 관리한다.
- 향후 프리미엄 템플릿에 대비해 개별가격 Override가 가능하게 설계한다.

### 4.4 템플릿 변경
- 결제 전, 결제 후 발행 전, 발행 후 이용기간 중 모두 변경 가능.
- 초기 동일가격 정책에서는 추가 결제 없음.
- 기존 URL, 입력내용, 사진, RSVP, 방명록 유지.
- 마케팅 표현은 `무제한 변경`보다 `이용기간 동안 자유롭게 변경`을 사용한다.

### 4.5 관리자 템플릿 운영
- 실제 시각 디자인은 MVP에서 코드 컴포넌트로 개발한다.
- 관리자 관리항목: 템플릿명, 내부 관리코드, 스타일 카테고리, 썸네일, 미리보기, 노출 ON/OFF, 추천, NEW, 정렬순서, 지원 섹션, 가격 방식.
- 내부 관리코드는 시스템용 고유값으로 자동 생성 또는 개발자가 지정하고 관리자에게는 조회 위주로 제공한다.
- 템플릿 삭제 대신 **숨김(노출 OFF)**을 기본으로 한다.
- 숨김 시 신규 선택만 막고 이미 사용 중인 초대장에는 계속 정상 적용한다.
- 심각한 보안/장애 상황은 별도 긴급조치 가능.
- MVP 관리자 템플릿 복제 기능은 제외한다.
- 스타일 카테고리 예: 심플, 모던, 로맨틱, 포토, 클래식.

## 6. 데이터 구조 기본 원칙

- 행사별 별도 본체 테이블을 만들지 않고 공통 `events` 구조와 `event_kind`를 사용한다.
- 행사별 입력 차이는 공통 데이터 + 유연한 설정 데이터(JSONB 등)를 활용한다.
- 사진, RSVP, 방명록, 장소 등 반복/관계 데이터는 별도 테이블을 사용한다.
- 템플릿 변경 시 이벤트/하객 데이터를 새로 생성하지 않는다.
- 결제 상태는 최소 `미결제 → 결제완료/미발행 → 발행완료`, 환불/만료 등 확장 상태를 명확히 구분한다.

## 7. 초대장 편집 공통 원칙

- 한 페이지 편집 + 섹션별 접기/펼치기.
- 항상 필수 / 기능 ON 시 조건부 필수 / 선택 항목을 구분한다.
- 임시저장/미리보기는 필수항목 누락 상태에서도 가능.
- 최종 발행 시에만 필수값을 검사하고 누락 목록을 명확히 안내한다.
- OFF 기능은 검증과 공개 화면에서 제외한다.
- Event Type → Field Definition → Editor 구조로 확장한다.
- 상단/하단에서 `저장하기`, `미리보기`를 명확히 제공한다.
- 제작 화면에 결제 버튼을 계속 노출하지 않고 미리보기의 `발행 준비하기`에서 결제로 진입한다.

### 7.1 저장 / 네트워크 오류
- 저장 성공/실패를 명확히 표시하며 실패를 성공처럼 표시하지 않는다.
- 저장되지 않은 변경사항이 있을 때 페이지 이탈 경고.
- MVP는 명시적 저장을 기본으로 하고 자동저장은 추후 확장 가능.

### 7.2 동시 편집 충돌
- 실시간 공동편집은 구현하지 않는다.
- 다른 기기/탭에서 먼저 저장되어 버전이 바뀐 경우 오래된 화면의 저장을 무조건 덮어쓰지 않고 충돌을 감지해 최신 내용을 다시 불러오도록 한다.

### 7.3 사진 업로드 실패
- 여러 사진 중 일부 실패 시 성공한 사진은 유지하고 실패한 사진만 재시도한다.
- 업로드 중/실패 사진이 남아 있으면 최종 발행을 차단한다.

## 8. 행사별 편집항목 / 웨딩 v1.0

- 기본정보: 신랑/신부 이름, 예식 날짜/시간, 예식장명 필수. 상세정보/주소/지도 등 선택.
- 대표사진/Hero: ON/OFF 가능, 사진형/타이포형/일러스트형 지원.
- 인사말: 선택 입력, 미입력 시 숨김 가능.
- 가족/연락처: ON/OFF, 입력된 정보만 표시.
- 갤러리: ON/OFF, 사진 추가/삭제/순서변경, 현재 최대 20장 기준.
- 마음 전하기/계좌: ON/OFF, ON 시 등록 계좌의 필수값 검증.
- RSVP: ON/OFF, 세부 정책은 13장 기준.
- 방명록: ON/OFF, 세부 정책은 13장 기준.
- 돌잔치/생일/파티 등은 행사 종류별 필드 정의로 확장한다.

## 9. 공개 초대장 디자인 / 브랜드

- 모바일 우선, 깨끗하고 고급스럽게.
- 콘텐츠와 템플릿 디자인 분리.
- 과도한 애니메이션/광고성 요소를 피한다.
- 결제한 공개 초대장에는 외부 배너 광고를 넣지 않는다.
- DearDay 브랜딩은 초대장 본연의 디자인을 해치지 않도록 최소화한다.

## 10. 결제 / 발행 / 수정

### 10.1 기본 흐름
`무료 제작 → 저장/미리보기 → 발행 준비하기 → 필수값 검사 → 결제 → 결제완료/미발행 → 최종 미리보기 → 초대장 발행하기 → URL 활성화 → 공유`

- 결제 완료와 발행 완료를 분리한다.
- 결제 성공만으로 URL을 자동 활성화하지 않는다.
- `paid_at`, `published_at`, `service_started_at` 등을 구분할 수 있게 한다.
- 결제 후 발행기한은 두지 않는다.
- 결제완료/미발행 상태로 보관하며 원하는 시점에 수정 후 발행 가능.
- 최초 발행 후에도 이용기간 중 내용/템플릿 수정 가능.

### 10.2 최종 발행
- 발행 직전 최종 확인 팝업에서 발행 후에도 내용/템플릿 수정은 가능하지만 URL은 변경할 수 없음을 안내한다.
- 설정된 행사일이 이미 과거이면 신규 발행을 차단하고 행사일 수정 안내.
- 최초 발행 이후 URL은 고정한다. 제작중/결제완료·미발행 단계에서는 변경 가능.

### 10.3 행사일 변경
- 발행 후 행사일 변경 가능.
- 기본 만료일은 변경된 행사일 +14일로 재계산한다.
- 이미 유료로 확보한 이용기간은 행사일 변경으로 줄어들지 않는다.
- 발행 후 행사일 변경은 최초 행사일 기준 최대 1년 범위까지 허용하고 그 이상은 고객센터 문의로 처리한다.

### 10.4 행사 취소 / 복원
- `행사 취소하기`는 확인 팝업 후 상태 전환으로 처리하며 데이터 삭제가 아니다.
- 같은 URL에서 일반 본문을 숨기고 자동 행사 취소 안내문을 표시한다.
- 기존 내용/사진/RSVP/방명록은 보존한다.
- `초대장 다시 활성화`로 같은 URL과 데이터를 복원한다.
- 행사 연기는 날짜/시간 수정으로 처리한다.

## 11. 이용기간 / 만료 / 보관 / 자동삭제

- 기본 공개 이용기간: **행사일 +14일**.
- 이후 URL 비활성화, 즉시 삭제하지 않는다.
- 만료 후 **30일 유예기간** 동안 데이터/사진 유지.
- 유예기간 중 유료 연장/복구 가능.
- 사용자 계정은 초대장 만료만으로 삭제하지 않는다.

### 11.1 30일 연장 상품
- MVP는 **30일 연장 상품 하나**만 제공한다.
- 향후 90일/1년 등 추가 상품을 쉽게 넣을 수 있게 구조화한다.
- 연장 가격은 출시 전 결정하고 관리자 설정값으로 관리한다.
- 만료/유예 상태에서 연장하면 **결제 완료 시점부터 30일** 활성화.
- 아직 이용기간이 남아 있을 때 추가 연장하면 **기존 만료일 +30일**.
- 30일 연장은 횟수 제한 없이 반복 구매 가능.
- 기존 URL, 내용, 사진, RSVP, 방명록 유지.
- 연장 결제 완료 즉시 기간이 적용되므로 단순변심 환불은 원칙적으로 제한하되 중복결제/시스템·PG 오류/법적 환불사유는 예외 처리한다.

### 11.2 자동삭제
- 30일 유예 종료 시 관리자 승인 없이 시스템 자동삭제.
- 초대장 본체 및 관련 DB/Storage 데이터 정리.
- 법령상 보관 필요한 거래기록은 분리 보관.
- 상태: `삭제예정 → 삭제처리중 → 삭제완료 / 삭제실패`.
- 정상 건은 관리자 승인 불필요, 삭제 실패만 관리자 확인/재처리.
- 삭제 로그를 남긴다.

## 12. 마이페이지 / 고객 화면

메뉴: 내 초대장 / 하객 관리 / 결제·보관 / 문의내역 / 계정·내 정보 / 로그아웃 / 회원탈퇴.

### 12.1 내 초대장
- 상태: 제작중 / 결제완료·미발행 / 발행완료 / 만료·유예.
- **템플릿 단위가 아니라 초대장 제작본(Event Instance) 단위로 카드 표시**한다.
- 새 초대장을 3개 저장하면 제작중 카드 3개, 하나의 제작본에서 템플릿만 여러 번 변경하면 카드 1개.
- 제작중: 계속 만들기 / 미리보기 / 삭제.
- 결제완료·미발행: 편집 / 미리보기 / 발행 / 조건 충족 시 환불 요청.
- 발행완료: 편집하기 / 초대장 보기 / 공유하기.
- 만료·유예: 미리보기 / 삭제 예정일 / 보관기간 연장.
- 상단 `+ 새 초대장 만들기`, 빈 상태 CTA 제공.

### 12.2 결제 / 보관
- 초대장별 카드로 한 화면에서 관리.
- 제작중: 미결제 + 계속 만들기.
- 결제완료·미발행: 결제일/금액/상태 + 발행 + 환불 요청(조건 충족 시).
- 발행완료: 결제정보, 최초 발행일, 행사일, 이용 종료일, 보관기간 연장.
- 만료·유예: URL 비활성, 삭제예정일/남은일수, 30일 연장.
- MVP부터 PG가 제공하는 **결제내역/영수증 확인** 기능을 연결한다.

### 12.3 계정 / 내 정보
- 이름/닉네임, 로그인 방식, 가입일, 서비스에서 별도 수집한 연락정보가 있으면 표시.
- 소셜 로그인 기반이므로 DearDay 자체 비밀번호 변경 메뉴는 두지 않는다.
- 로그아웃/회원탈퇴 제공.

## 13. 하객 기능 / 관리

### 13.1 RSVP
- RSVP 기능 ON/OFF.
- 기본 필수: 이름, 참석 여부.
- 결혼식의 `신랑측/신부측`은 기본 ON이며 주최자가 OFF 가능. 다른 행사 종류에서는 자동 제외/행사에 맞게 처리.
- 참석 인원 항목은 ON/OFF 가능하며 참석 선택 시 `1명 / 2명 / 3명 / 4명 / 5명 이상`, 불참 시 숨김.
- 연락처는 **기본 OFF**, 주최자가 필요할 때 ON. 개인정보 이용 안내를 표시한다.
- 전달사항은 **기본 OFF / 최대 200자 / 주최자만 확인하는 비공개 정보**.
- 행사 시작 시각에 신규 RSVP와 수정 모두 자동 마감.
- 제출 후 하객은 회원가입 없이 **고유 수정 링크/토큰**으로 자신의 RSVP만 수정 가능.
- MVP는 RSVP 제출마다 카카오/문자 실시간 알림을 보내지 않고 하객관리에서 전체/신규 건수를 표시한다.

### 13.2 방명록
- 기본 ON, 주최자가 ON/OFF 가능.
- OFF해도 기존 글을 삭제하지 않고 다시 ON하면 복원 표시.
- 비회원 작성.
- 이름 필수 최대 20자, 메시지 필수 최대 200자, 삭제용 숫자 비밀번호 4자리.
- **텍스트 전용**, 사진/파일 첨부 없음.
- 작성 즉시 공개, 별도 승인 없음.
- 작성자는 비밀번호로 자기 글 삭제, 초대장 소유자는 부적절한 글 삭제 가능.
- 기본적인 도배/연속 등록 방지 적용.
- 초대장이 활성화되어 있는 동안 작성 가능. URL 비활성 시 작성 중지, 유료 연장으로 재활성화되면 다시 작성 가능.

### 13.3 하객 관리 화면
- 초대장 선택 + RSVP / 방명록 탭.
- RSVP 필터: 전체/참석/불참 등.
- RSVP 요약: 총 응답, 참석/불참, 예상 참석인원.
- 목록: 이름, 측 구분(해당 시), 참석여부, 참석인원, 연락처(수집 시), 전달사항, 제출일.
- 신규 응답/방명록은 `신규 N건` 형태로 표시.
- **MVP부터 RSVP 엑셀 다운로드 제공**, 현재 필터 결과도 다운로드 가능.
- 방명록 엑셀 다운로드는 MVP에서 제외.

## 14. 공유 기능

- 발행완료 초대장에서 Bottom Sheet 형태의 공유 UI 제공.
- MVP: **링크 복사 + QR코드 + 기기 기본 공유**.
- 카카오 전용 공유 API는 추후 확장.
- 공유 문구는 행사 종류, 주인공 이름, 행사일시, URL을 이용해 **자동 생성**하며 MVP에서 직접 편집 기능은 제외.
- QR은 발행된 고정 URL을 사용한다.
- QR 보기 + **QR 이미지 저장** 제공. 내용/템플릿 수정 후에도 같은 QR 사용.

## 15. 결제 / 환불 / 외부 판매채널

### 15.1 결제 안전 원칙
- 같은 초대장/같은 결제 건의 중복 처리를 서버에서 차단한다.
- 클라이언트 화면 결과가 아니라 PG 서버 결과를 기준으로 확정한다.
- PG 결제 성공 후 DB 반영 실패 시 PG 결과 재확인 후 자동 복구하고 실패 건만 관리자 확인으로 보낸다.
- 결제/발행 상태가 불명확할 때 중복 실행을 막고 서버에서 실제 상태를 재확인한다.

### 15.2 최초 발행 결제 환불
자동환불 조건:
1. 결제완료.
2. 최초 발행 전.
3. 결제일로부터 7일 이내.
4. 기존 환불/취소되지 않음.

- 조건 충족 시 서버 검증 → PG 취소 API → PG 성공 확인 → DB 환불완료.
- PG 성공 전에 DB를 환불완료로 변경하지 않는다.
- 최초 발행 후 단순변심 환불은 원칙적으로 제한.
- 중복결제는 중복분 환불, 시스템 장애는 확인 후 적절히 처리.
- 관계 법령이 우선하며 출시 전 약관/법률 검토.

### 15.3 외부 판매채널
- DearDay 자체 PG를 기본으로 유지하되 네이버 스마트스토어 등 외부 판매채널 확장 가능하게 한다.
- `payment_source` 등으로 결제 출처를 구분한다.
- 외부 주문은 주문번호/구매정보/인증코드/공식 API 등 안전한 구매 인증 후 DearDay의 `결제완료/미발행` 상태로 통합한다.
- 외부 주문 식별자는 중복 사용을 방지한다.
- 외부 결제도 사용자가 최종 `초대장 발행하기`를 눌러 발행한다.
- MVP에서 실제 외부채널 연동은 필수 아님.

## 16. 사이트 내부 문의 / 고객지원

- 이용안내 → 문의하기 → 문의유형 + 제목 + 내용 → 등록.
- 유형: 결제/환불, 초대장 이용, 오류/장애, 기타.
- 마이페이지 문의내역: 유형, 제목, 등록일, `답변대기/답변완료`.
- 문의 원문은 등록 후 고객/관리자가 수정·삭제하지 않는다.
- 관리자는 답변/상태만 관리.
- 관리자 답변도 등록 후 수정·삭제하지 않고 잘못된 답변은 **추가 답변으로 정정**해 이력을 보존한다.
- 답변 등록 시 사이트 내부 알림 생성, 해당 문의 상세로 이동.
- MVP는 실시간 채팅 필수 아님. 향후 이메일/카카오/AI 고객지원 확장 가능.

## 17. 알림 정책

MVP는 사이트 내부 알림 중심으로 운영한다.
- 이용기간 종료 **7일 전 + 1일 전**.
- 유예기간 최종 데이터 삭제 **7일 전 + 1일 전**, `보관기간 연장` 바로가기 제공.
- 결제완료: 결제 완료 + 발행 안내.
- 환불완료.
- 환불실패/관리자 확인 필요 + 문의하기.
- 보관연장 완료 + 새 만료일.
- 문의 답변 등록/추가 답변 등록.
- RSVP/방명록은 별도 실시간 알림 대신 하객관리의 신규 건수로 표시.
- 향후 이메일/카카오 알림톡/앱 푸시 확장 가능.

## 18. 관리자

### 18.1 메뉴
1. 대시보드
2. 회원 관리
3. 초대장 관리
4. 템플릿 관리
5. 결제/환불
6. 보관/만료
7. 문의 관리
8. 서비스 설정
9. 관리자 권한

### 18.2 권한
- 역할: `user / admin / super_admin`.
- MVP는 **super_admin 1명 + 필요한 만큼 admin**.
- 최초 소유자 1명을 DB에서 1회 super_admin 지정하며 이메일 하드코딩 금지.
- super_admin만 admin 부여/해제 및 중요 권한 변경 가능.
- admin은 자신의 권한 상승 불가.
- API/서버/RLS에서 실제 권한 검증하고 일반 사용자의 `/admin` 직접 접근 차단.
- 권한 변경은 Audit Log 기록.

### 18.3 대시보드
- 오늘 방문자, 오늘 가입, 제작 시작, 오늘 결제금액, 오늘 발행, 환불, 미답변 문의.
- 전환 퍼널: `방문 → 제작 시작 → 로그인/가입 → 제작 → 결제 → 발행`.
- 운영 확인 필요: 환불 실패, 관리자 확인 결제, 삭제 실패, 미답변 문의, 숨김/신고 관련.
- 숫자 클릭 시 해당 메뉴의 필터된 목록으로 이동.

### 18.4 회원 관리
- 목록: 이름/닉네임, 가입방식, 가입일, 초대장 수, 결제 수, 상태.
- 상세: 운영에 필요한 최소 기본정보, 초대장/결제·환불/문의 내역, 계정상태.
- 소셜 토큰/인증정보 등 민감한 인증정보는 관리자에게도 노출하지 않는다.
- 회원 상태는 MVP에서 `정상 ↔ 이용정지` 두 상태만 사용.
- 정지 시 사유 필수, 정지/해제 Audit Log 기록.
- 정지 회원도 로그인, 마이페이지 열람, 문의하기 가능. 신규 제작/편집/결제/발행 등 주요 기능은 제한.
- **회원 이용정지와 초대장 공개 상태는 분리**한다. 회원 정지만으로 기존 발행 초대장을 자동 비공개하지 않는다.

### 18.5 초대장 관리
- 목록/상세에서 초대장명, 회원, 행사종류, 템플릿, 상태, 행사일, 발행일, 이용 종료일, 결제상태, 미리보기 확인.
- 관리자는 고객의 실제 콘텐츠를 직접 수정하지 않는다.
- 신고/약관위반 등 운영상 필요한 경우 `숨김/숨김해제` 가능, 사유 필수.
- 관리자 강제삭제 기능은 두지 않는다. 실제 삭제는 만료/유예/탈퇴 등 정해진 정책을 따른다.
- 숨김 해제 시 같은 URL과 기존 데이터를 유지.
- 모든 운영조치는 Audit Log 기록.

### 18.6 결제 / 환불 관리
- 결제완료, 환불완료, 환불실패, 관리자확인 등을 조회/필터.
- 결제번호, 회원, 초대장, 금액, 수단, 결제일, 최초발행 여부, 상태 등 확인.
- 정상 자동환불은 관리자 승인 불필요.
- 일반 admin은 조회/확인 중심, **수동 환불 실행은 super_admin만 가능**.
- 수동 환불은 관리자/시간/금액/사유 Audit Log 기록.

### 18.7 보관 / 만료 관리
- 이용중, 만료·유예중, 삭제예정, 삭제처리중, 삭제완료, 삭제실패 조회.
- 정상 자동삭제는 승인 불필요, 삭제실패만 관리자 확인.
- 서비스 장애 등 보상 필요 시 **super_admin만 무료 보상 연장** 가능.
- 보상 연장 시 연장 일수 + 사유 필수, Audit Log 기록.

### 18.8 서비스 설정
- 가격 관련 설정은 super_admin이 변경 가능.
- 기본 공개기간 +14일, 유예기간 30일, 삭제정책 등 핵심 운영정책은 MVP 관리자 화면에서 조회만 가능하고 임의 변경하지 않는다.

## 19. 운영 / 장애 / 보안 예외처리

- 계획된 점검 중에는 가능하면 결제/발행 버튼을 비활성화하고 안내한다.
- 결제/발행 성공 여부가 불명확하면 임의 성공 처리하지 않고 서버 상태를 재확인한다.
- 자동 복구 불가 건만 관리자 확인 필요로 보낸다.
- 제작/관리 기능 장애가 발생해도 이미 발행된 하객용 초대장은 가능한 한 계속 열람되도록 운영 구조를 분리한다.
- API 권한, RLS, 입력 검증, rate limit 등 기술 보안은 구현 단계 체크리스트로 관리한다.

## 20. 화면별 최종 기능 정의

### 20.1 홈페이지
`상단 메뉴 → Hero → 행사 종류 선택 → 추천 템플릿 → DearDay가 시작된 이유 → 이용방법 → 최종 CTA → Footer`
- Hero: `[초대장 만들기] [템플릿 보기]`.
- 최종 CTA에서 다시 제작 진입 유도.
- Footer: 사업자정보, 고객센터, 이용약관, 개인정보처리방침 등.
- 비회원도 홈/템플릿/이용안내 탐색 가능.

### 20.2 템플릿 목록 / 미리보기
- 카테고리 필터: 전체/심플/모던/로맨틱/포토/클래식 등.
- 카드: 미리보기 이미지 + 템플릿명 + NEW/추천.
- 상세는 실제 모바일 초대장 형태의 긴 미리보기 + `[이 템플릿으로 만들기]`.
- 비회원도 목록/미리보기 가능.
- 동일가격이므로 카드마다 가격을 과도하게 반복하지 않고 공통 가격 안내 영역 사용.

### 20.3 제작 화면
- 한 페이지 + 섹션 접기/펼치기.
- 기본정보, 대표사진, 인사말, 가족/연락처, 갤러리, 마음 전하기, RSVP, 방명록 등 행사 종류에 맞게 구성.
- 저장/미리보기 중심, 결제는 미리보기의 `발행 준비하기`에서 진입.

### 20.4 미리보기
- 실제 하객 화면과 최대한 동일하게 표시.
- 결제 전에는 `DearDay Preview` 워터마크.
- 공개 URL은 아직 활성화하지 않는다.
- `[계속 수정하기] [발행 준비하기]`.
- 미리보기는 결제 전 횟수 제한 없이 무료.

### 20.5 결제 → 최종 발행
- 결제 안내: 정상가, 판매가, 이용기간, 환불정책, 결제하기.
- 결제 성공 후 `아직 공개되지 않았습니다` 안내 + `[최종 미리보기] [초대장 발행하기]`.
- 최종 발행 확인 후 URL 활성화 → `[초대장 보기] [공유하기]`.

## 21. 개발 우선순위 — 최종 확정

실제 PG 연동은 핵심 기능이 안정된 뒤로 미룬다. 단, 결제 상태/인터페이스는 처음부터 실제 PG로 교체 가능한 구조로 설계한다.

### 1단계 — 핵심 제작 기능
`로그인 → 행사종류 → 템플릿 → 제작/저장 → 미리보기 → 수정`

### 2단계 — 발행/공유 흐름을 가결제로 구현
- 실제 PG 없이 개발용 결제완료 처리.
- `결제완료/미발행 → 최종 발행 → URL 활성화 → 공유/QR` 전체 흐름 먼저 완성.
- 나중에 실제 PG만 교체/연결할 수 있도록 결제 상태와 서버 인터페이스를 분리.

### 3단계 — 하객 기능
`RSVP → 수정 링크 → 하객관리 → 엑셀 다운로드 → 방명록`

### 4단계 — 마이페이지 / 보관 / 알림
`내 초대장 → 결제/보관 → 만료 → 30일 유예 → 연장 → 자동삭제 → 내부 알림`

### 5단계 — 관리자
`대시보드 → 회원 → 초대장 → 템플릿 → 문의 → 결제관리 → 보관/만료 → 권한/Audit Log`

### 6단계 — 실제 PG 결제 연동
`실제 결제 → 서버 검증 → 환불 API → 중복결제 방지 → DB 반영 실패 복구 → 보관 연장결제`

### 7단계 — 안정화 / 출시 준비
`전체 시나리오 테스트 → 모바일/PC → RLS/보안 → 개인정보/약관 → 성능 → 실제 PG 운영환경 테스트 → 출시`

## 22. 구현 점검 / 테스트 기준

현재 GitHub 구현을 이 문서와 비교하여 `구현완료 / 수정필요 / 미구현 / 향후기능`으로 GAP 분석한다.

핵심 테스트:
- 비회원 홈/템플릿 탐색.
- 디자인 우선/행사 우선 제작 진입 후 동일 편집기로 합류.
- 여러 초대장 제작본 저장/목록 표시.
- 임시저장/미리보기/워터마크.
- 템플릿 변경 시 콘텐츠 유지.
- 최종 발행 필수값 검증 및 과거 행사일 차단.
- 가결제 및 향후 실제결제 → 결제완료/미발행 → 최종 발행.
- 최초 발행 후 URL 고정, 같은 URL로 내용/템플릿 변경.
- 행사일 변경/1년 제한/유료 확보기간 보호.
- RSVP 제출/수정링크/자동마감/엑셀.
- 방명록 작성/삭제/ON-OFF/도배 방지.
- 공유 링크/QR/기본 공유.
- 행사 취소/복원.
- 행사일 +14일 → 30일 유예 → 반복 연장 → 자동삭제.
- 만료/삭제 사전 알림.
- 중복결제, PG 성공-DB 실패, 장애 복구.
- 회원 이용정지와 초대장 숨김 분리.
- 관리자 권한/RLS/Audit Log.
- 문의 등록/답변/추가 정정 이력.
- 외부 판매채널 구매 인증 확장성.

## 23. 현재 작업 원칙

- 이 문서를 DearDay 개발의 최신 기준으로 사용한다.
- 기능 개발 전 필요한 요구사항을 먼저 확정한다.
- 요구사항이 변경되면 충돌하는 이전 정책을 함께 수정하여 최신 확정 정책만 남긴다.
- Codex에는 전체 요구사항을 한 번에 구현시키지 않고 작은 작업 단위로 나눈다.
- 각 단계 구현 후 테스트하고 다음 단계로 진행한다.
- 다음 개발 단계는 **현재 GitHub 코드와 본 요구사항의 GAP 분석** 후 작업목록을 만드는 것이다.
