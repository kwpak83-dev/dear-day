# DearDay 상품·요금제 운영 규격 초안

> 목적: ⑫-A 요금제 구조 및 ⑬ 관리자 페이지 구현 시 상품/이용권을 코드에 고정하지 않고 운영자가 관리자 페이지에서 유연하게 관리하기 위한 기준을 정의한다.

## 1. 기본 원칙

- DearDay의 상품은 `B2C 단건`과 `B2B 전용`으로 시스템에서 경직되게 구분하지 않는다.
- `Partner 50`, `Partner 100` 등의 명칭은 마케팅/판매를 위한 상품명일 뿐, 특정 구매자 유형만 구매할 수 있는 하드코딩된 상품 유형으로 취급하지 않는다.
- 예식장, 행사대행사 등 사업자가 다건 이용권을 구매할 수 있고 일반 개인 사용자도 필요하면 동일한 다건 상품을 구매할 수 있는 구조를 기본으로 한다.
- 향후 정말 특정 회원군 전용 상품이 필요해질 경우를 대비해 `구매 대상: 전체 / 파트너 전용` 등의 접근 정책을 확장할 수 있도록 설계하되, 현재 기본값은 전체 구매 가능으로 본다.

## 2. 관리자 상품 관리

운영자는 노트북이나 코드 수정 없이 모바일 관리자 페이지에서도 다음 항목을 관리할 수 있어야 한다.

- 상품 신규 추가
- 상품명 수정
- 상품 설명 수정
- 정상가 설정/수정
- 판매가 설정/수정
- 포함 초대장 발행 건수 설정/수정
- 이용권 유효기간 설정/수정
- 상품 노출/숨김
- 판매 ON/OFF
- 노출 순서 변경
- `NEW` / 추천 / 인기 등 배지 설정
- 필요 시 구매 대상 정책 설정

예를 들어 `Starter 10`, `Partner 50`, `Partner 100`, `Business 200` 등 상품명과 제공 건수는 코드에 고정하지 않으며 운영자가 자유롭게 추가·변경할 수 있어야 한다.

## 3. 하드코딩 금지 원칙

- 상품명, 가격, 정상가, 판매가, 제공 건수, 유효기간, 노출 여부, 판매 여부, 노출 순서 등 운영 중 변경될 수 있는 값은 코드 상수에 하드코딩하지 않는다.
- 가능한 운영 설정은 DB 기반으로 저장하고 관리자 페이지에서 변경 가능하게 한다.
- 일상적인 상품 변경 때문에 Codex 수정 → GitHub commit/push → Vercel 재배포 → Supabase SQL 직접 실행이 필요하지 않도록 한다.
- 인증, 권한 검증, 결제 금액 서버 검증, 이용권 차감 무결성 등 보안/핵심 시스템 로직은 코드에서 보호한다.

## 4. 기존 구매자 보호 및 상품 삭제

- 상품을 관리 화면에서 제거할 때는 실제 물리 삭제보다 `판매 종료/비활성화/숨김`을 기본으로 한다.
- 이미 구매된 주문은 구매 당시의 상품명, 실제 결제 가격, 제공 건수, 유효기간 등 상품 조건을 주문 스냅샷으로 보존한다.
- 관리자가 이후 상품명·가격·건수·유효기간을 변경하거나 판매를 종료해도 과거 주문의 구매 조건과 이력이 변경되어서는 안 된다.
- 관리자 UI에서 삭제 기능을 제공하더라도 과거 주문과 연결된 상품/이력 보존 정책을 우선한다.

## 5. 결제 및 이용권 원칙

- 실제 결제 시 브라우저에 표시된 가격이나 상품 조건을 신뢰하지 않고 서버에서 현재 활성 상품과 판매 가격/조건을 다시 조회해 검증한다.
- 다건 상품 구매 시 구매자 계정에 사용 가능한 이용권/크레딧을 부여하는 구조로 확장한다.
- 이용권은 제작 시작이 아니라 최종 발행 시 차감하는 방향을 기본으로 하며 세부 처리는 ⑫-B에서 구현한다.
- 사업자/개인 여부와 무관하게 동일한 구매·잔여수량·사용량 구조를 재사용할 수 있도록 한다.

## 6. 모바일 운영 원칙

- 관리자 페이지는 모바일 우선으로 설계해 노트북을 사용할 수 없는 환경에서도 상품 추가·수정·판매중지·가격/건수/유효기간 변경 등 주요 운영이 가능해야 한다.
- 가격, 제공 건수, 이용권 조정 등 중요한 변경은 저장 전 확인 절차와 변경 전/후 값을 보여주는 UX를 고려한다.
- 주요 변경은 변경 시각, 관리자, 변경 전/후 값을 감사 로그에 남길 수 있도록 설계한다.

## 7. 구현 시 참고 문서

⑫-A, ⑫-B, ⑬ 관리자 및 결제 관련 Codex 작업 전 다음 문서를 함께 확인한다.

- `docs/DEARDAY_GAP.md`
- `docs/DEARDAY_REQUIREMENTS.md`
- `docs/DEARDAY_PRODUCT_PLAN_SPEC.md`
- 템플릿 관련 작업이 포함되면 `docs/DEARDAY_TEMPLATE_SPEC.md`

본 문서의 핵심은 **상품 이름이나 B2B/B2C 마케팅 분류가 시스템의 고정 제약이 되지 않게 하고, 운영 중 바뀌는 상품 조건은 가능한 한 관리자 페이지에서 수정 가능하게 만드는 것**이다.
