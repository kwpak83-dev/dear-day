# DearDay 개발 요구사항 정의서

> 상태: 핵심 기획 확정 / 2026-10-23 정책 업데이트 / 구현 및 법적 검증은 별도
> 목적: DearDay의 제품·기능·개발 기준을 한 곳에 관리하고, 이후 Codex 개발 및 구현 누락 점검의 기준 문서로 사용한다.
> **정책 우선순위:** 27장(2026-10-23 확정 정책) → 26장(스마트스토어 이용권) → 3.4/16.5(네이버 단일 로그인·판매) → 이전 역사적 설계. 과거 PG·유예·연장 관련 표현은 출시 구현 기준으로 사용하지 않는다.

## 1. 서비스 개요

### 1.1 서비스명 / 정체성
- 서비스명: **DearDay**.
- 웨딩 전용이 아니라 다양한 행사를 위한 **모바일 초대장 제작 플랫폼**이다.
- 결혼식을 초기 핵심 상품으로 시작하되 돌잔치, 생일, 기념일, 집들이, 졸업, 기업/단체 행사, 파티, 기타 행사로 확장한다.
- 전문 디자인/개발 지식 없이 템플릿을 선택하고 필요한 정보만 입력해 고급스러운 모바일 초대장을 제작·공유할 수 있게 한다.
- 모바일 환경 최우선, 웹 우선 개발 후 Android/iOS 확장 가능하게 한다.
- 메뉴와 제작 흐름은 최대한 단순하게 유지한다.

### 1.2 브랜드 / 가격 포지셔닝
- 핵심 방향: **가격은 부담 없게, 결과물은 고급스럽게.**
- `싼 초대장`보다 `합리적인 가격으로 제공하는 고급 모바일 초대장`으로 포지셔닝한다.
- 모든 일반 템플릿은 초기 동일가격 정책.
- 정확한 판매가격은 출시 전 최종 확정한다.
- 결제한 실제 초대장 URL에는 외부 광고를 노출하지 않는다.

### 1.3 무료 제작 / 유료 발행
- 템플릿 탐색, 제작, 임시저장, 미리보기까지 무료.
- 실제 발행 및 전용 URL 활성화 시 유료.
- 결제 전 미리보기에는 화면을 방해하지 않는 수준의 `DearDay Preview` 워터마크를 표시하고 결제 완료 후 제거한다.
- 초기에는 무료 발행 플랜을 핵심 전략으로 운영하지 않는다.

### 1.4 브랜드 스토리
메인 홈페이지에 `DearDay가 시작된 이유` 섹션을 배치한다.

> **특별한 날을 준비하는 마음에  
> 가격이 부담이 되지 않았으면 했습니다.**
>
> DearDay는 좋은 디자인과 필요한 기능을 담으면서도  
> 누구나 부담 없이 사용할 수 있는  
> 모바일 초대장을 만들고자 시작되었습니다.
>
> **가격은 가볍게, 특별한 날의 품격은 그대로.**
>
> 당신의 소중한 날에 DearDay가 함께하겠습니다.

## 2. 시스템 구성 / 개발 원칙

- Frontend / Web Framework: Next.js.
- Source Code: GitHub.
- Hosting / Deployment: Vercel.
- Database / Authentication / Storage: Supabase.
- 외부 서비스: 네이버 로그인·스마트스토어, 카카오톡 공유, 향후 PG 결제 API(초기 제외).
- GitHub `main`을 운영 기준으로 사용하고 Vercel 자동 배포.
- Secret/Service Role Key 등은 환경변수로 관리하고 클라이언트/GitHub에 직접 저장하지 않는다.
- Supabase RLS로 사용자별 데이터 접근을 제어한다.
- 기존 정상 기능을 불필요하게 변경하지 않고 Codex에는 작은 작업 단위로 지시한다.
- Codex 작업 전 항상 `docs/DEARDAY_REQUIREMENTS.md`를 먼저 확인한다.

개발 흐름:
`요구사항 정의 → ChatGPT 설계/검토 → Codex 최소 범위 개발 → 테스트 → GitHub → Vercel → 운영환경 테스트`

## 3. 회원 / 인증 / 계정

- 제작/관리는 회원 로그인이 필요하며 발행 초대장은 하객이 로그인 없이 열람한다.
- RSVP/방명록은 하객 회원가입 없이 이용 가능.
- 초기 상용화 로그인은 네이버 단일(3.4절). 카카오 로그인은 신규 고객에게 노출하지 않으며 기존 계정/데이터 전환 검증 후 정리한다. 향후 Google/Apple/이메일 확장 가능.
- 동일 소셜 계정 반복 로그인으로 중복 회원이 생성되지 않게 한다.
- 로그인 세션 유지 및 로그아웃 제공.

### 3.1 회원탈퇴 (2026-10-23 확정)
- 회원은 발행·공개 중인 초대장이나 미사용 이용권 보유 여부와 관계없이 언제든 탈퇴를 신청할 수 있다. 탈퇴 예약 및 활성 초대장으로 인한 탈퇴 제한은 두지 않는다.
- 탈퇴 전 발행 초대장 공개 중단, 사진·RSVP·방명록 등 데이터 삭제, 복구 불가, 미사용 이용권 사용 권한 종료 및 환불 신청 경로를 명확히 안내하고 최종 확인을 받는다.
- 탈퇴 확정 시 초대장 공개 URL을 즉시 비활성화하고 관련 데이터·저장소 파일을 삭제한 다음 계정 삭제를 완료한다. 실패 시 재처리 및 운영 점검을 남기며 삭제가 끝나지 않은 상태를 완료로 표시하지 않는다.
- 미사용 묶음상품의 일부 사용 후 단순 변심에 따른 잔여 이용권 부분 환불은 제공하지 않는 것을 원칙으로 하되, 법령상 환불 권리와 스마트스토어 정책을 우선한다. 전부 미사용 주문은 스마트스토어 환불 신청을 안내하며, 환불 신청 여부와 별개로 탈퇴를 허용한다.
- 탈퇴 완료 시 잔여 이용권의 서비스 사용 권한은 종료되지만 법정 환불 권리는 소멸하지 않는다. 환불 정산을 위해 필요한 거래 정보는 법정 보존 범위에서 분리 관리한다.
- 동일 네이버 계정 재가입은 신규 회원으로 처리하고 이전 초대장·RSVP·방명록 등은 복구하지 않는다.
- 법령상 보존이 필요한 거래기록 등은 목적·기간·접근권한을 제한해 별도 보관한다.
- 회원이 탈퇴하지 않은 동안 기본 회원정보(네이버 식별자, 이름, 휴대전화번호, 이메일)는 유지한다. 초대장 데이터는 회원 유지 여부와 관계없이 별도 보관기준에 따라 삭제한다.

### 3.2 세션 만료
- 편집 중 세션 만료 시 작성 화면을 즉시 버리지 않는다.
- 저장 시 로그인이 만료되었다면 재로그인을 안내하고 현재 작성 내용을 최대한 유지한다.
- 재로그인 성공 후 원래 작업으로 돌아와 저장할 수 있게 한다.

### 3.3 상용화 시 소셜 로그인 개인정보 제공항목
- 네이버 로그인 기준으로 서비스 운영 및 외부 구매 인증에 필요한 최소 정보만 요청한다.
- 상용화 목표 필수 항목: **소셜 사용자 식별자, 이름, 휴대전화번호, 이메일 주소**.
- 별명/프로필사진 등 서비스 제공에 불필요한 정보는 기본 필수 수집항목에서 제외한다.
- Kakao/Naver 등 공급자별 식별자는 회원 본체에 하드코딩하기보다 소셜 계정 연결 구조로 관리하여 향후 복수 로그인 공급자 연결에 대비한다.
- 실제 필수 제공항목과 동의 문구는 출시 전 각 소셜 로그인 사업자의 최신 심사정책 및 개인정보처리방침에 맞춰 최종 확정한다.
- 이름/휴대전화번호는 향후 네이버 스마트스토어 등 외부 판매채널의 구매자 정보와 DearDay 회원을 1차 확인하는 데 사용할 수 있으나, 이 정보 일치만으로 결제완료 권한을 부여하지 않는다.


### 3.4 초기 상용화 네이버 단일 로그인 정책 (2026-10-08 확정)
- 초기 신규 가입·로그인 수단은 **네이버 로그인 단일**로 운영한다. 카카오 로그인은 신규 고객에게 제공하지 않는다. 기존 카카오 회원/제작 데이터는 삭제하지 않으며, 전환·계정연결·접근 보존 방안을 검증한 뒤 비노출/중단한다.
- 회원 필수 프로필은 **이름, 휴대전화번호, 이메일**이다. **기본 가입 흐름에서는 별도의 회원정보 입력 폼을 표시하지 않는다.** 네이버 OAuth의 제공정보 동의 화면에서 사용자가 동의하면 네이버 프로필 API로 세 항목을 받아 자동 저장하고 가입을 완료한다. 누락·거부·미제공 등 예외 시에만 해당 항목의 추가 입력·확인을 안내한다. 네이버 제공정보 항목의 필수/선택 설정 및 실제 제공 가능 여부는 네이버 개발자센터 심사·정책을 확인한다. 로그인용 네이버 고유 식별자(id)는 별도로 보관한다.
- 필수 프로필의 이용 목적, 보관·삭제 및 동의 문구는 개인정보처리방침과 네이버 로그인 검수 정책에 맞춘다. 네이버 제공 정보가 곧 실명/휴대전화 소유 인증 또는 주문 결제 증빙이라는 뜻은 아니다.
- 이름/전화번호/이메일은 외부 구매 매칭의 보조 단서이며, 네이버 스마트스토어 주문과 자동으로 동일 계정이라고 단정하지 않는다. 주문 API 및 고유 거래식별자 검증을 필수로 한다.

## 4. 템플릿 / 행사 종류

### 4.1 핵심 구조
- 템플릿 = 어떻게 보이는가(Visual Design).
- 행사 종류(Event Type) = 어떤 콘텐츠/편집항목이 필요한가.
- 초대장(Event Instance) = 사용자가 실제 제작한 하나의 초대장.
- 템플릿은 가능한 한 행사 종류와 분리해 공통 디자인으로 재사용한다.
- 템플릿 변경은 행사 데이터를 새로 만드는 것이 아니라 디자인만 교체한다.

### 4.2 제작 진입
- 디자인부터: `템플릿 → 행사 종류 → 편집 → 미리보기 → 결제 → 최종 확인 → 발행`.
- 행사부터: `행사 종류 → 템플릿 → 편집 → 미리보기 → 결제 → 최종 확인 → 발행`.
- 두 경로는 동일 편집기로 합류한다.

### 4.3 가격
- 공통 기본 발행가격을 사용한다.
- **정상가 + 실제 판매가**를 분리 관리하여 할인/프로모션 표현이 가능하게 한다.
- 가격은 코드 하드코딩 대신 운영 설정값으로 관리한다.
- 향후 프리미엄 템플릿에 대비해 개별가격 Override가 가능하게 설계한다.

### 4.4 템플릿 변경
- 결제 전, 결제 후 발행 전, 발행 후 이용기간 중 모두 변경 가능.
- 초기 동일가격 정책에서는 추가 결제 없음.
- 기존 URL, 입력내용, 사진, RSVP, 방명록 유지.
- 마케팅 표현은 `무제한 변경`보다 `이용기간 동안 자유롭게 변경`을 사용한다.

### 4.5 관리자 템플릿 운영
- 기존 공통 `InvitationRenderer`를 유지하고, 일반적인 신규 시각 디자인은 가능한 한 DB Config + Storage Asset + 관리자 페이지에서 등록·수정한다.
- 공통 규격으로 표현할 수 없는 새로운 기능, 완전히 새로운 레이아웃/인터랙션, 새로운 Renderer 능력만 코드 개발 대상으로 분리한다.
- 관리자 관리항목: 템플릿명, stable template key, 스타일 카테고리, 썸네일, 긴 판매 미리보기, Asset, 배경/Hero, 장식, typography/색상, 섹션 구성, 연출 설정, 노출/판매 상태, 추천, NEW, 정렬순서, 가격 방식.
- 템플릿은 stable `template_id`와 version을 가지며 실질적 디자인 변경은 Draft/새 버전 기반으로 관리한다. 기존 발행본은 사용한 버전에 고정한다.
- 판매용 Asset은 기본 7종 체계를 출발점으로 하되 개수를 하드코딩하지 않는다. 전체 Background와 Hero Background는 같은 Asset을 재사용하거나 필요 시 서로 다른 Background Asset을 사용할 수 있다.
- 템플릿 삭제 대신 **숨김/판매중지**를 기본으로 하며 기존 제작·발행 초대장과 참조 중인 버전/Asset을 보호한다.
- 심각한 보안/장애 상황은 별도 긴급조치 가능.
- 스타일 카테고리 예: 심플, 모던, 로맨틱, 포토, 클래식.
- 세부 템플릿 규격과 현재 Config 구현 단계는 `docs/DEARDAY_TEMPLATE_SPEC.md`를 기준으로 한다.

## 5. 메뉴 / 사이트맵

### 5.1 PC
`DearDay | 템플릿 | 이용안내 | [초대장 만들기] | 프로필`
- `내 초대장`은 최상위 메뉴에 별도로 두지 않고 마이페이지에서 접근한다.

### 5.2 모바일
- 상단: `DearDay | 햄버거 | 프로필`.
- 햄버거: 템플릿, 이용안내, 내 초대장, 하객 관리, 결제/보관, 내 정보, 초대장 만들기.

### 5.3 제작 진입
- 디자인부터 시작하기 → 템플릿 선택 → 행사 선택.
- 행사부터 시작하기 → 행사 선택 → 템플릿 선택.

![DearDay 모바일 메뉴 구성 최종안](./images/메뉴구성도(모바일).png)

> 참고 이미지는 시각적 참고용이며 텍스트 요구사항과 충돌할 경우 본 문서의 최신 텍스트 요구사항을 우선한다.

## 6. 데이터 구조 기본 원칙

- 행사별 별도 본체 테이블을 만들지 않고 공통 `events` 구조와 `event_kind`를 사용한다.
- 행사별 입력 차이는 공통 데이터 + 유연한 설정 데이터(JSONB 등)를 활용한다.
- 사진, RSVP, 방명록, 장소 등 반복/관계 데이터는 별도 테이블을 사용한다.
- 템플릿 변경 시 이벤트/하객 데이터를 새로 생성하지 않는다.
- 주문 결제 상태·이용권 지급/사용/회수/만료 상태·초대장 제작/발행/삭제 상태를 각각 분리하여 관리한다.

## 7. 초대장 편집 공통 원칙

- 한 페이지 편집 + 섹션별 접기/펼치기.
- 항상 필수 / 기능 ON 시 조건부 필수 / 선택 항목을 구분한다.
- 임시저장/미리보기는 필수항목 누락 상태에서도 가능.
- 최종 발행 시에만 필수값을 검사하고 누락 목록을 명확히 안내한다.
- OFF 기능은 검증과 공개 화면에서 제외한다.
- Event Type → Field Definition → Editor 구조로 확장한다.
- 상단/하단에서 `저장하기`, `미리보기`를 명확히 제공한다.
- 제작 화면에 결제 버튼을 계속 노출하지 않고 미리보기의 `발행 준비하기`에서 결제로 진입한다.

### 7.1 저장 / 네트워크 오류
- 저장 성공/실패를 명확히 표시하며 실패를 성공처럼 표시하지 않는다.
- 저장되지 않은 변경사항이 있을 때 페이지 이탈 경고.
- MVP는 명시적 저장을 기본으로 하고 자동저장은 추후 확장 가능.

### 7.2 동시 편집 충돌
- 실시간 공동편집은 구현하지 않는다.
- 다른 기기/탭에서 먼저 저장되어 버전이 바뀐 경우 오래된 화면의 저장을 무조건 덮어쓰지 않고 충돌을 감지해 최신 내용을 다시 불러오도록 한다.

### 7.3 사진 업로드 실패
- 여러 사진 중 일부 실패 시 성공한 사진은 유지하고 실패한 사진만 재시도한다.
- 업로드 중/실패 사진이 남아 있으면 최종 발행을 차단한다.

## 8. 행사별 편집항목 / 웨딩 v1.0

- 기본정보: 신랑/신부 이름, 예식 날짜/시간, 예식장명 필수. 상세정보/주소/지도 선택.
- 대표사진/Hero: ON/OFF, 사진형/타이포형/일러스트형 지원 가능.
- 인사말: 제목/내용 선택 입력.
- 가족/연락처: ON/OFF, 입력된 정보만 표시.
- 갤러리: ON/OFF, 사진 추가/삭제/순서변경, 현재 최대 20장 기준.
- 마음 전하기: ON/OFF, ON 시 계좌별 은행/계좌번호/예금주 필수.
- RSVP: ON/OFF.
- 방명록: ON/OFF.

## 9. 공개 초대장 / 미리보기

- 모바일 우선, 깨끗하고 고급스러운 디자인.
- 콘텐츠와 템플릿 디자인 분리.
- 미리보기는 실제 하객 화면과 최대한 동일하게 표시한다.
- 결제 전 미리보기에는 `DearDay Preview` 워터마크.
- 미리보기 단계에서는 공개 URL 미활성.
- 선택항목 미입력 시 자연스럽게 숨긴다.
- 공개 초대장은 모바일 가로 overflow가 발생하지 않도록 모든 사용자 입력 텍스트/URL/이미지를 반응형으로 처리한다.
- 갤러리 썸네일 클릭 시 한 장 전체보기, 이전/다음, 닫기 제공. 추가 확대/핀치줌은 제공하지 않는다.

## 10. 결제 / 발행 / 수정

### 10.1 기본 흐름 (이용권 기반 최신 정책)
`무료 제작 → 저장/워터마크 미리보기 → 발행하기 → 필수값 검사 → 이용권 잔액 확인 → (부족 시 스마트스토어 구매·공식 주문 검증) → 발행 동의 → 최초 발행 성공 시 이용권 1개 원자적 차감 및 URL 활성화 → 공유`
- 결제 완료만으로 공개 URL을 자동 활성화하지 않는다. 사용자가 `초대장 발행하기`를 직접 누른다.
- 이용권 구매·지급과 개별 초대장 발행은 별개다. 최초 발행에만 1개 차감하며 이후 같은 초대장 편집/템플릿 변경에 추가 차감하지 않는다.
- 최초 발행 이후 초대장 URL은 변경하지 않는다.
- 행사 시작 전까지만 일반 편집/템플릿 변경/행사일 변경을 허용한다. 행사 시작 이후 초대장은 읽기 전용이며 삭제·하객관리 기능은 별도 유지한다.
- 발행 전 디지털 서비스 제공 개시 및 법정 환불 안내를 표시하고 필요한 동의 이력을 저장한다. 세부 내용은 26장 기준.

### 10.2 행사 취소 / 복원
- 발행 초대장에서 `행사 취소하기` 제공.
- 확인 팝업 후 취소 상태로 전환하며 삭제하지 않는다.
- 기존 URL 유지, 일반 본문은 숨기고 행사 취소 안내를 표시한다.
- 기존 내용/사진/RSVP/방명록은 보존.
- `초대장 다시 활성화`로 동일 URL/데이터 복원 가능.

### 10.3 행사일 변경 (2026-10-23 확정)
- 초대장 발행 후에도 **기존 행사 시작 시각 전까지만** 행사 날짜·시간 변경을 허용한다. 행사 시작 이후에는 서버/API에서도 변경 요청을 거부한다.
- 변경하려는 행사 시작 시각은 과거 시점일 수 없다.
- 변경된 행사일을 기준으로 자동삭제 예정일을 `행사일 +30일`로 다시 계산하고 RSVP·방명록 작성 마감 시각도 새 행사 시작 시각으로 갱신한다.
- 행사일 변경으로 추가 이용권을 차감하지 않으며 기존 URL·QR코드는 유지한다.
- 이전의 '최초 발행일 기준 1년 제한' 및 '기존 유료 확보기간 보호' 규칙은 폐기한다. 유료 보관 연장 상품을 운영하지 않는다.

## 11. 이용기간 / 보관 / 자동삭제 (2026-10-23 확정)
- 발행된 초대장의 공개 및 보관 종료 기준은 **행사일 +30일**이다. 삭제 예정일에 URL 공개를 종료하고 초대장 본문, 갤러리·사진, RSVP, 방명록 등 관련 데이터를 자동삭제한다.
- **종전 행사일 +14일 공개, 만료 후 30일 유예, 유료 30일 단위 보관 연장/복원, 반복 연장 정책은 전부 폐기한다.**
- 자동삭제 시점까지 주최자는 초대장을 열람·공유하고 RSVP 조회/엑셀 다운로드 및 방명록 삭제 등 관리 기능을 사용할 수 있다. 단 행사 시작 이후 초대장 내용 편집, 신규 RSVP·수정 및 신규 방명록 작성은 불가하다.
- 주최자는 행사 전후 언제든 초대장을 직접 조기 삭제할 수 있다. 최종 확인 후 즉시 URL 공개를 중단하고 관련 데이터를 삭제한다. 사용된 이용권은 조기 삭제를 이유로 복구하지 않는다(법정 환불 사유 별도).
- 회원탈퇴 시에는 초대장 공개를 즉시 중단하고 관련 데이터를 삭제한다. 삭제된 초대장 복구 기능은 제공하지 않는다.
- 삭제 실패 건은 재시도 및 관리자 확인 대상으로 관리한다. 법정 보존 거래기록은 서비스 데이터와 분리해 보관한다.
- 삭제 날짜·마감 시각은 한국시간(KST) 기준으로 일관 처리한다. 정확한 날짜 경계 및 배치 실행 시각은 구현 전 기술 규칙으로 명시한다.

### 11.1 자동삭제 사전 안내 (2026-10-23 확정)
- 마이페이지/초대장 관리 화면에 **삭제 예정일을 상시 표시**한다.
- **삭제 7일 전(D-7), 1일 전(D-1)** 서비스 내 알림을 제공한다. 로그인하지 않았던 회원도 이후 로그인 시 미확인 알림을 볼 수 있도록 한다.
- 알림에는 삭제 예정일, 삭제 후 복구 불가, RSVP 엑셀 다운로드 권고를 포함한다.
- 초기에는 이메일·문자·카카오 알림톡 등 외부 발송을 제공하지 않는다.
- 같은 초대장/같은 알림 유형의 중복 생성을 방지하며 이미 삭제된 초대장에 대한 알림은 무효화한다.

## 12. 마이페이지

메뉴: 내 초대장 / 하객 관리 / 결제·보관 / 문의내역 / 계정·내 정보.

### 12.1 내 초대장
- 제작중 / 발행완료(행사 전) / 행사 시작 후 읽기 전용 / 삭제 예정 상태로 관리한다. 기존 결제완료·미발행은 이용권 잔액 및 발행 가능 여부로 구분한다.
- **초대장 제작본 단위**로 카드 표시하며 템플릿 변경은 새 카드를 만들지 않는다. 여러 초대장 제작본은 각각 저장·표시한다.
- 제작중: 계속 만들기 / 미리보기 / 삭제.
- 발행 전: 이용권 잔액 확인 / 발행 / 부족 시 스마트스토어 구매 안내.
- 발행완료·행사 전: 편집 / 초대장 보기 / 공유 / 삭제.
- 행사 시작 후: 초대장 보기 / 공유 / 하객 관리 / 삭제(편집 불가).
- 모든 발행본에 자동삭제 예정일 표시. 유예·유료 연장·복구 버튼은 제공하지 않는다.
- `+ 새 초대장 만들기`, 빈 상태 안내 및 제작 CTA 제공.

### 12.2 하객 관리
- 초대장 선택 + RSVP / 방명록 탭.
- RSVP: 전체/참석/불참 등 필터, 응답자/참석인원 요약.
- RSVP 목록: 이름, 측 구분(사용 시), 참석여부, 참석인원, 연락처(수집 시), 전달사항, 제출일.
- **MVP부터 RSVP 엑셀 다운로드 제공**, 현재 필터 결과도 다운로드 가능하게 한다.
- 방명록: 작성자/메시지/작성일/소유자 삭제. MVP 방명록 엑셀 다운로드는 제공하지 않는다.
- 신규 RSVP/방명록 표시 가능.

### 12.3 내 이용권 / 주문 / 보관
- 초대장별 직접 PG 결제 카드 대신 **내 이용권**(잔액·지급·사용·회수·만료 내역)과 스마트스토어 주문 안내를 제공한다(26.4절).
- 제작중: 무료 저장/미리보기. 최초 발행에 이용권 1개 필요.
- 발행완료: 최초 발행일, 행사일, 자동삭제 예정일, 사용 이용권 내역을 표시한다.
- 삭제 예정: 남은 기간 및 RSVP 엑셀 다운로드 안내. 유예기간·유료 연장·복구 없음.
- 결제·환불·영수증 상세는 네이버 스마트스토어 제공 범위와 판매자센터 안내를 따른다. DearDay 자체 PG 영수증 발급을 전제로 하지 않는다.

### 12.4 문의내역
- 목록: 문의유형/제목/등록일/답변상태(답변대기/답변완료).
- 상세: 문의 원문/등록일/관리자 답변/답변일.
- `새 문의하기` 제공.
- 문의 등록 후 고객/관리자 모두 원문 수정·삭제 불가.

### 12.5 계정 / 내 정보
- 이름/휴대전화번호/이메일, 네이버 로그인 방식, 가입일, DearDay에서 별도 수집한 정보가 있으면 해당 정보 표시.
- 로그아웃 / 회원탈퇴.
- 소셜 로그인 중심이므로 DearDay 자체 비밀번호 변경 메뉴는 MVP에 두지 않는다.

## 13. RSVP (2026-10-23 확정)
- 하객 로그인 없이 제출한다. **이름·참석 여부 필수**, 참석 인원·연락처·전달 메시지 선택.
- 수집 목적은 주최자에게 참석 여부를 전달하고 참석 인원을 관리하기 위함이며 마케팅에 활용하지 않는다. 제출 화면에 수집 항목·목적·보유기간 및 개인정보 안내를 표시한다.
- 제출 완료 후 **응답별 추측하기 어려운 고유 수정 링크**를 제공하고 복사할 수 있게 한다. 수정 링크 보유자는 해당 응답의 참석 여부·인원·연락처·메시지를 수정할 수 있으므로 공유 주의를 안내한다.
- 수정은 기존 응답 ID를 갱신하며 중복 집계하지 않는다. 동일 이름으로 여러 건 제출은 허용한다(동명이인 가능). 이름/연락처만으로 자동 병합·차단·삭제하지 않는다.
- 주최자는 중복 의심 응답을 직접 확인·삭제할 수 있으며 삭제된 응답은 통계·엑셀 다운로드에서 제외한다.
- **행사 시작 시각(KST)에 신규 제출과 기존 응답 수정을 모두 마감**한다. 마감 안내 문구를 표시한다. 소유자는 RSVP 기능 ON/OFF 가능.
- 마감 이후에도 초대장 삭제 전까지 소유자는 기존 응답을 조회하고 엑셀로 다운로드할 수 있다. MVP 방명록 엑셀 다운로드는 제공하지 않는다.
- RSVP 개인정보는 행사일 +30일 자동삭제, 조기 삭제, 회원탈퇴 시 초대장과 함께 삭제한다. 주최자가 다운로드한 엑셀은 DearDay 서버의 자동삭제 범위 밖이므로 주최자에게 안전한 관리·파기를 안내한다.
- RSVP 목록·수정 링크·다운로드 API는 초대장 소유권 및 응답 토큰 범위를 서버에서 검증한다.

## 14. 방명록 (2026-10-23 확정)
- 소유자가 방명록 기능을 ON/OFF 할 수 있고 기본값은 ON. OFF 시 공개 초대장에서 작성폼·목록을 숨기고 신규 작성을 차단하되 기존 데이터는 보존한다.
- 하객 로그인 없이 작성 가능. 이름(필수, 최대 20자), 메시지(필수, 최대 200자), 삭제 비밀번호(필수, 숫자 4자리). 텍스트만 허용한다.
- 삭제 비밀번호 원문은 저장하지 않고 안전한 해시 방식으로 저장한다. 삭제 시 비밀번호 검증과 요청 속도 제한을 적용한다.
- 작성자는 4자리 비밀번호로 본인 글을 삭제할 수 있다. 본인 글 수정 기능은 MVP 제외. 소유자는 부적절한 글을 비밀번호 없이 삭제할 수 있다. 삭제는 확인 절차 후 처리한다.
- **행사 시작 시각(KST)에 신규 작성 자동 마감**. 마감 후 기존 글 열람과 작성자·주최자의 삭제 기능은 초대장 삭제 전까지 유지한다.
- 작성 전 이름·메시지가 링크 접근자에게 공개됨을 안내한다. 광고·마케팅에 활용하지 않는다.
- 행사일 +30일 자동삭제, 주최자 조기 삭제, 회원탈퇴 시 관련 방명록을 삭제한다.
- 공개 작성/삭제 요청에 기본 rate limit을 적용하고 CAPTCHA는 필요 시 추가한다.

## 15. 공유

- MVP부터 링크 복사 + QR 코드 + 모바일 기본 공유(Web Share API 가능 환경) 제공.
- 카카오톡 전용 공유 API는 향후 기능으로 두되 구조 확장 가능하게 한다.
- 공유는 초대장 자체 기능으로 제공하며 공유 수단이 바뀌어도 URL은 동일하게 유지한다.

## 16. 결제 / 환불 / 외부 판매채널 (2026-10-23 현행화)

### 16.1 초기 상용화 결제 구조
- 초기 판매 채널은 **네이버 스마트스토어 단일**, DearDay 자체 PG는 출시 범위에서 제외한다.
- 초대장 무료 제작/저장/미리보기 후, 최초 발행에 이용권 1개를 사용한다. 이용권 상품은 1/5/10개 묶음으로 판매하며 가격은 출시 전 최종 확정한다.
- 네이버 공식 주문 API로 주문/상품/수량/결제/취소 여부와 구매 귀속을 검증한 후 이용권을 지급한다. 회원 이름·전화번호 일치만으로 지급하지 않는다.
- 이용권 지급·차감·회수·만료는 원장 기반으로 기록하고 중복 지급·이중 차감을 방지한다. 상세는 26장 참조.

### 16.2 환불·취소
- 취소·환불 접수/승인/거절/실제 결제 취소는 네이버 스마트스토어 판매자센터 및 해당 채널 정책을 따른다. DearDay에서 PG 취소 API를 직접 실행하지 않는다.
- 전부 미사용 주문은 법령 및 스마트스토어 정책에 따른 환불을 지원한다. 일부 사용한 할인 묶음은 단순 변심 부분 환불을 제공하지 않는 것을 원칙으로 하되 법정 예외가 우선한다.
- 발행 직전 디지털 서비스 제공 개시 및 청약철회 제한 가능성 등을 적법하게 고지하고 동의 이력을 보존한다. 발행·탈퇴·조기 삭제만으로 법정 환불 권리가 소멸하지 않는다.
- 환불 요청만으로 초대장을 임의 삭제하지 않는다. 확정된 취소·환불에 따라 미사용 이용권 회수 및 발행 초대장 상태를 별도 정책/법령에 따라 처리한다.

### 16.3 향후 판매채널 확장
- 자체 PG·카카오 등 타 채널 연동은 향후 별도 승인 후 검토한다. 초기 상용화에서는 구현하지 않는다.
- 향후 채널 추가 시에도 주문 검증·원장·초대장 발행 로직이 특정 결제 사업자에 종속되지 않게 한다.

### 16.4 구매 인증 및 운영
- 주문 확인 지연/오류는 확인 중·재시도로 처리하고 임의 이용권 지급을 금지한다.
- 판매자센터 주문/환불 상태와 DearDay 이용권 원장·발행 이력의 정합성을 점검한다.
- 실제 판매 허용 범위·주문 API 접근권한·구매자 정보 제공 범위는 출시 전 네이버 공식 정책으로 확인한다.

## 17. 사이트 내부 문의 / 고객지원

- 이용안내 → 문의하기 → 문의유형(결제/환불, 초대장 이용, 오류/장애, 기타) + 제목 + 내용 → 등록.
- 마이페이지 문의내역에서 확인.
- 관리자: 전체/답변대기/답변완료 → 상세 → 답변 등록.
- 문의 원문은 등록 후 수정/삭제 불가.
- **관리자 답변도 등록 후 수정/삭제 불가**. 잘못된 답변은 추가 답변으로 정정하고 기존 이력 유지.
- 답변 등록 시 고객 사이트 내부 알림 생성.
- MVP 실시간 채팅은 필수 아님.

## 18. 관리자

### 18.1 권한 구조
- `user / admin / super_admin`.
- MVP `super_admin`은 **1명만 유지**.
- 초기 1명을 DB에서 지정하고 이후 super_admin만 admin 추가/해제 가능.
- admin은 자기 권한 상승 불가.
- API/서버/RLS에서 실제 권한 검증.
- 권한 변경 Audit Log 기록.

### 18.2 대시보드
- 오늘 방문자/가입/제작시작/결제금액/발행/환불/미답변 문의.
- 전환 퍼널: 방문 → 제작시작 → 로그인/가입 → 제작 → 결제 → 발행.
- 환불실패/확인필요 결제/삭제실패/미답변 문의/숨김 관련 등 운영 확인 필요 영역.
- 숫자 클릭 시 해당 메뉴의 필터된 목록으로 이동.

### 18.3 회원 관리
- 목록: 이름/닉네임, 가입방식, 가입일, 초대장 수, 결제 수, 상태.
- 상세: 기본정보, 초대장, 결제/환불, 문의, 계정상태.
- 관리자는 이용정지/정지해제 가능하며 정지 사유 필수.
- 회원 이용정지와 초대장 숨김은 별도 상태로 관리한다.
- 회원 정지만으로 이미 발행된 초대장을 자동 숨김하지 않는다.
- 인증토큰 등 민감한 내부정보는 노출하지 않는다.

### 18.4 초대장 관리
- 전체 목록/상태/행사종류/소유자/템플릿/행사일/발행일/이용종료일/결제상태/미리보기.
- 관리자는 고객 콘텐츠를 직접 수정하지 않는다.
- 신고/약관 위반 등은 `숨김/숨김해제`로 조치하고 사유 필수.
- 관리자 강제삭제 기능은 두지 않는다.
- 숨김 해제 시 같은 URL/기존 데이터 유지.
- 조치 Audit Log 기록.

### 18.5 템플릿 관리
- 템플릿명/내부코드/카테고리/썸네일/미리보기/노출/추천/NEW/정렬/지원섹션/가격방식 관리.
- 내부코드는 자동생성 또는 개발자 지정, 관리자 조회 위주.
- 디자인 자체는 코드에서 개발.
- 삭제 대신 숨김.
- MVP 복제 기능 제외.

### 18.6 스마트스토어 주문 / 이용권·환불 관리
- 네이버 주문번호·상품주문번호, 회원, 상품/지급 수량, 주문·취소·환불 상태, 발행 이력과 동기화 오류 조회.
- 취소·환불 실행은 스마트스토어 판매자센터에서 처리하며 DearDay 관리자에서는 증빙·상태 동기화·예외 확인만 수행한다.
- 이용권 수동 지급·회수·정정은 초기 super_admin만 허용하고 사유·처리자·시각·전후 수량을 감사 로그로 남긴다. 상세는 26.5~26.6절.

### 18.7 보관 / 만료 관리
- 이용중/행사 시작 후 읽기 전용/삭제예정/삭제처리중/삭제완료/삭제실패 조회.
- 정상 자동처리는 관리자 승인 불필요.
- 삭제 실패만 관리자 확인.
- 유료/무료 보관 연장 기능은 제공하지 않는다. 장애 보상은 법령 및 별도 운영 승인 절차로 처리한다.

### 18.8 문의 관리
- 전체/답변대기/답변완료 필터.
- 원문 수정/삭제 불가.
- 관리자 답변도 수정/삭제 불가, 추가답변으로 정정.

### 18.9 서비스 설정
- 이용권 정상가/판매가/지급 수량 등 가격 설정은 super_admin 수정 가능.
- 행사일 +30일 자동삭제, 행사 시작 시각 편집·RSVP·방명록 마감 등 핵심 운영정책은 MVP에서 조회만 가능.

## 19. 보안 / 운영 예외처리

- 권한은 UI 숨김이 아니라 서버/API/RLS에서 검증한다.
- 주문·환불 상태 동기화/이용권 지급·회수/권한변경/초대장 숨김·삭제 등 중요 조치는 Audit Log.
- 과도한 요청/도배에는 기본 rate limit 적용.
- 주문 상태가 불명확하면 네이버 공식 주문 조회 결과를 재확인하며 임의 성공처리하지 않는다.
- 발행 상태가 불명확하면 서버의 실제 상태를 재확인한다.
- 상태 확인 전 중복결제/중복발행을 차단한다.
- 자동복구 불가능한 건만 관리자 확인 필요로 전환한다.
- 계획 점검 중에는 가능하면 결제/발행을 비활성화하고 안내한다.
- 제작/관리 기능 장애와 이미 발행된 공개 초대장 열람을 최대한 분리해 공개 초대장의 가용성을 우선한다.

## 20. 화면별 최종 기능정의

### 20.1 홈페이지
`상단 메뉴 → Hero → 행사 종류 선택 → 추천 템플릿 → DearDay가 시작된 이유 → 이용방법 → 최종 CTA → Footer`
- Hero: `[초대장 만들기] [템플릿 보기]`.
- 최종 CTA에서 다시 제작 진입 유도.
- Footer: 사업자정보, 고객센터, 이용약관, 개인정보처리방침 등.
- 비회원도 홈/템플릿/이용안내 탐색 가능.

### 20.2 템플릿 목록 / 미리보기
- 카테고리 필터: 전체/심플/모던/로맨틱/포토/클래식 등.
- 카드: 미리보기 이미지 + 템플릿명 + NEW/추천.
- 상세는 실제 모바일 초대장 형태의 긴 미리보기 + `[이 템플릿으로 만들기]`.
- 비회원도 목록/미리보기 가능.
- 동일가격이므로 카드마다 가격을 과도하게 반복하지 않고 공통 가격 안내 영역 사용.

### 20.3 제작 화면
- 한 페이지 + 섹션 접기/펼치기.
- 기본정보, 대표사진, 인사말, 가족/연락처, 갤러리, 마음 전하기, RSVP, 방명록 등 행사 종류에 맞게 구성.
- 저장/미리보기 중심, 결제는 미리보기의 `발행 준비하기`에서 진입.

### 20.4 미리보기
- 실제 하객 화면과 최대한 동일하게 표시.
- 결제 전에는 `DearDay Preview` 워터마크.
- 공개 URL은 아직 활성화하지 않는다.
- `[계속 수정하기] [발행 준비하기]`.
- 미리보기는 결제 전 횟수 제한 없이 무료.

### 20.5 이용권 확인 → 최종 발행
- 발행 안내: 이용권 잔액, 최초 발행 시 1개 차감, 초대장 보관기간(행사일 +30일), 환불·디지털 서비스 개시 고지.
- 이용권 부족 시 스마트스토어 구매 링크 제공, 구매 후 공식 주문 검증으로 이용권 지급.
- 사용자가 최종 발행을 확인하면 이용권 1개 원자적 차감 및 URL 활성화 → `[초대장 보기] [공유하기]`.

## 21. 개발 우선순위 — 최종 확정

초기 상용화는 네이버 스마트스토어 이용권 판매·공식 주문 검증을 사용한다. 자체 PG는 초기 출시 범위에서 제외한다.

### 1단계 — 공통 UI 뼈대 + 핵심 제작 기반
- 홈, 상단 메뉴, 버튼, 카드, 폰트, 여백, 모바일 기본 레이아웃 등 DearDay 공통 디자인 시스템을 먼저 잡는다.
- 이 단계의 화면 디자인은 출시 수준의 완성본이 아니라 약 70~80% 수준의 기본 UI를 목표로 한다.
- 로그인 → 행사종류 → 템플릿 → 제작/저장 → 미리보기 → 수정의 핵심 흐름을 구축한다.

### 2단계 — 실제 판매용 템플릿 2~3개 + 핵심 제작 기능 검증
- 임시 샘플만으로 개발하지 않고 실제 판매에 사용할 웨딩 템플릿 2~3개를 먼저 코드 컴포넌트로 구현한다.
- 실제 템플릿으로 사진 비율, 섹션 ON/OFF, 편집 데이터 연결, 미리보기, 모바일 반응형을 검증한다.
- 템플릿 변경 시 기존 입력 내용/사진/RSVP/방명록 데이터가 유지되는 구조를 검증한다.
- 결제 전 미리보기 `DearDay Preview` 워터마크를 적용한다.

### 3단계 — 발행/공유 흐름을 개발용 이용권으로 검증
- 개발용 관리자 지급 이용권으로 최초 발행 1개 차감과 URL 활성화를 먼저 검증한다.
- `이용권 잔액 → 발행 동의 → 최초 발행 원자적 차감 → URL 활성화 → 공유/QR` 전체 흐름을 구현한다.
- 스마트스토어 실제 주문 연동은 후속 단계에서 연결한다.

### 4단계 — 하객 기능
`RSVP → 수정 링크 → 하객관리 → 엑셀 다운로드 → 방명록`

### 5단계 — 마이페이지 / 보관 / 알림 + 관리자
- `내 초대장 → 행사 시작 시각 편집 마감 → 행사일 +30일 자동삭제 → D-7/D-1 내부 알림`.
- 관리자: 대시보드 → 회원 → 초대장 → 템플릿 → 문의 → 결제관리 → 보관/만료 → 권한/Audit Log.
- 관리자 화면은 기능성과 운영 효율을 우선하고 과도한 시각 디자인 작업은 하지 않는다.

### 6단계 — 판매용 템플릿 확대 + 전체 고객 UI 최종 마감
- 실제 판매용 템플릿 수를 확대한다.
- 홈/템플릿 목록/제작/미리보기/공개 초대장/마이페이지 등 고객이 보는 주요 화면을 출시 수준으로 최종 디자인한다.
- PC/모바일 반응형, 폰트, 간격, 이미지 품질, 세부 인터랙션/애니메이션 등을 최종 조정한다.
- 디자인 리소스는 관리자 화면보다 고객이 직접 보는 화면에 우선 배분한다.

### 7단계 — 스마트스토어 주문·이용권 연동
`스마트스토어 공식 주문 검증 → 이용권 지급 → 최초 발행 시 원자적 1개 차감 → 취소/환불 상태 동기화 → 중복 지급 방지`

### 8단계 — 안정화 / 출시 준비
`전체 시나리오 테스트 → 모바일/PC → RLS/보안 → 개인정보/약관 → 성능 → 스마트스토어 주문/환불 연동 검증 → 출시`

## 24. 템플릿 Renderer 현재 진행 순서 (2026-09-21)

- 관리자 템플릿 Config C1~C5 저장/복원은 운영 TC까지 완료했다.
- C6-1 Config normalization 기반과 C6-2 pinned Version 기반 공개 Renderer 연결을 구현했다.
- C6-2 공개 렌더링은 이벤트에 저장된 `template_version_id`를 기준으로 하며 현재 판매 Version을 자동 추적하지 않는다.
- 현재 개발용 템플릿은 판매 Version이 없고 Draft만 있어, Draft Config를 공개 발행본으로 시각 검증하기 어렵다.
- 이를 해결하기 위해 관리자 **Draft Live Preview를 다음 작업으로 선행**한다. Preview는 실제 `InvitationRenderer`를 재사용하고 현재 Draft Config/Asset을 표시해야 한다.
- 관리자 Preview는 디자인 검증 도구이며 MVP에서 Drag/Resize 편집기를 만들지 않는다. 설정은 기존 Config 입력 UI에서 수정하고 Preview로 확인한다.
- 공개 초대장과 관리자 Preview의 Version 경계는 분리한다: 공개는 pinned Version, 관리자 Preview는 명시적으로 선택된 편집 Draft.
- 이후 순서는 `Draft Live Preview → C6-2 실화면 TC → C6-3 Decoration+Sections → C6-4 Effects/Safe Area → C6 통합 회귀 → T4 버전/판매상태 관리`로 한다.
- 실제 BGM 재생/음원 관리 기능은 현재 범위가 아니며, BGM Config는 확장 기반만 유지한다.

## 25. 출시 후 확장 — 초대장 데이터 기반 자동 영상 제작

- **우선순위:** DearDay 모바일 초대장 핵심 기능 완성 및 상용 출시 이후의 2차 확장 기능으로 개발한다. 현재 MVP/출시 범위에는 포함하지 않는다.
- 초대장 제작 과정에서 이미 저장된 **이름, 행사일시, 장소, 초대/인사 문구, 업로드 사진 등 기존 데이터를 재사용**하여 고객이 같은 정보를 다시 입력하거나 사진을 다시 업로드하지 않고 영상을 만들 수 있게 한다.
- 기본 사용자 흐름은 `초대장 완성 → 내 초대장으로 영상 만들기 → 기존 데이터 자동 불러오기 → 영상 템플릿 선택 → 사진 순서/사용 사진 확인 → BGM 선택 → 미리보기 → 결제 → MP4 생성`을 목표로 한다.
- 1차 영상 MVP는 자유로운 타임라인 편집기가 아니라 **고정 영상 템플릿 기반 자동 제작**으로 구현한다. Canva/CapCut 수준의 자유 편집 기능은 범위에 포함하지 않는다.
- 영상 템플릿은 사진 슬롯, 이름/날짜/문구 슬롯, 장면 길이, 전환/애니메이션, 엔딩 등의 구조를 미리 정의하고 고객 데이터만 자동 매핑하는 방식을 우선한다.
- 초기에는 영상 템플릿 약 2~3개로 렌더링 품질/사용성/수요를 검증한 뒤 확대한다.
- 하나의 공통 영상 렌더링 엔진을 기반으로 행사별 템플릿을 확장한다. 예: **결혼식 식전영상, 돌잔치 성장영상, 칠순·팔순 감사영상, 생일/기념일 축하영상, 모임·동창회 추억영상, 기타 행사영상**.
- 영상 생성은 생성형 AI 전체 영상 제작을 기본 방식으로 하지 않는다. 결과의 일관성과 비용을 위해 템플릿 렌더링을 기본으로 하고, 향후 AI 모션포토/짧은 애니메이션 클립 등은 선택형 부가기능으로 검토한다.
- 기술 검토 시 현재 DearDay의 Next.js/React 구조와 연계 가능한 영상 렌더링 방식(예: Remotion 계열)을 우선 검토하되 특정 라이브러리에 미리 종속시키지 않는다.
- 서버 렌더링은 장시간 작업 및 동시 요청을 고려하여 웹 요청과 분리된 **비동기 렌더링 작업/큐 구조**를 검토한다. Vercel 요청 함수에서 장시간 MP4 렌더링을 직접 처리하는 구조는 비용·제한을 확인한 후 결정한다.
- 생성된 영상은 해상도/길이/파일 크기 정책을 정의하고 저장소 비용을 고려하여 다운로드 가능 기간과 자동삭제 정책을 별도로 둔다.
- BGM은 음원 저작권/라이선스를 확인하여 상업적 영상 제작 및 고객의 행사장 재생/공유에 사용할 수 있는 음원만 제공한다.
- 영상 상품의 결제도 DearDay 공통 주문/결제 모델을 재사용하고, 스마트스토어/Npay 등 당시 운영 중인 결제채널과 연결할 수 있게 한다.
- 초대장 원본 사진/정보와 영상 생성용 파생파일의 소유권·삭제주기를 연결하여 초대장 데이터 삭제 시 불필요한 렌더링 중간파일이 남지 않도록 한다.
- 실제 개발 착수 전 렌더링 비용, 저장비용, 동시처리량, 영상 음원 라이선스, 결제/환불 정책을 다시 산정하고 영상 상품의 가격/보관정책을 확정한다.



### 16.5 초기 상용화 판매·결제 채널 확정 (2026-10-08)
- **초기 판매는 네이버 스마트스토어 단일 채널, 결제는 스마트스토어의 Npay 등 해당 채널 제공 방식**으로 진행한다. DearDay 자체 PG 결제 및 카카오 등 타 판매 채널은 초기 개발/출시 범위에서 제외한다. 이후 확장을 위해 내부 주문/결제 상태와 채널 어댑터는 분리한다.
- 별도 구매 도메인의 DearDay 웹사이트는 홍보·템플릿 탐색·무료 제작·저장·워터마크 미리보기·구매 확인·최종 발행을 담당한다. 자체 웹사이트에서 결제하려는 고객은 **네이버 스마트스토어의 해당 상품 상세/구매 페이지**로 이동한다.
- 웹사이트 결제/워터마크 제거 버튼은 적용 자격이 확인되면 **네이버 판매자 마케팅 링크**를 사용한다. 일반 상품 URL 이동만으로 수수료 우대를 보장하지 않으며, 링크 발급·귀속 조건·상품별 적용 여부·수수료는 운영 시점 공식 정책으로 확인한다.
- 흐름: `네이버 로그인 → DearDay 초대장 무료 제작·워터마크 미리보기 → 결제/워터마크 제거 → 스마트스토어 상품 페이지 이동 → Npay 결제 → DearDay 복귀·구매 확인 → 네이버 공식 주문 API 서버 검증 → 내부 PAID/미발행 → 워터마크 제거된 최종 확인 → 사용자 명시적 발행 → URL 활성화`.
- 네이버 스마트스토어에서 먼저 구매하고 DearDay에 진입하는 고객도 구매 확인 후 동일 권리를 부여할 수 있어야 한다.
- 주문 확인 지연·취소·환불·중복 사용은 별도 상태로 관리한다. 네이버 로그인과 구매 계정이 같아도 자동 결제확정하지 않는다. 한 거래의 재사용/이용권 차감은 멱등성 및 구매상품 권한으로 보호한다.
- **출시 전 확인 사항:** 디지털 초대장 제작 이용권의 스마트스토어 상품 등록·판매 정책, 외부 웹사이트 제작·결제 유도 허용 범위, 네이버 커머스 API 주문 접근 권한 및 구매자 정보 제공 범위, 판매자 마케팅 링크 수수료 적용 요건, 취소/환불 운영 절차.
- 본 절은 초기 출시 채널 선택에 대해 16.1/16.3의 '자체 PG 기본' 표현보다 우선한다. 실제 PG 도입은 별도 후속 의사결정으로 둔다.


## 26. 스마트스토어 이용권(크레딧) 판매·발행·관리 확정 요구사항 (2026-10-13)

> 본 절은 2026-10-13 협의한 초기 상용화 이용권 정책의 최신 기준이다. 기존 10장/16장/18장/20장/21장의 초대장별 직접 결제·자체 PG·자체 환불 실행·결제완료 후 바로 발행 가능 등의 표현과 충돌하면 본 절 및 3.4/16.5의 네이버 단일 로그인·스마트스토어 단일 판매 정책을 우선한다. **요구사항 확정이지 기능 구현 완료를 의미하지 않는다.**

### 26.1 상품·판매 채널·가격
- 초기 판매 채널은 **네이버 스마트스토어 단일**, DearDay 자체 PG 결제는 출시 범위에서 제외한다.
- 초대장 제작/저장/워터마크 미리보기는 무료이고, **초대장 1건 최초 발행에 이용권 1개**가 필요하다.
- 판매 상품 및 **초기 제안 가격(출시 전 최종 확정)**:
  - 1개: **8,900원**, 할인 없음.
  - 5개: **39,900원**, 정가 44,500원 대비 4,600원 할인(약 10.34%), 개당 7,980원.
  - 10개: **69,900원**, 정가 89,000원 대비 19,100원 할인(약 21.46%), 개당 6,990원.
- 상품별 판매가·정상가·지급 수량·판매 상태·스마트스토어 상품 링크는 관리자 설정으로 관리하고 코드에 하드코딩하지 않는다. 실제 주문 당시 가격·상품·수량은 스냅샷으로 보존한다.
- **구매한 이용권(1/5/10개)의 유효기간은 구매일로부터 5년**이다. 묶음 일부 사용은 잔여분 만료일을 갱신하지 않는다. 이용권 유효기간과 발행 초대장 공개기간은 별개다. 법정 환불 권리는 유효기간과 별도로 판단한다. 관리자·프로모션 무상 지급분의 유효기간은 지급 조건에 따르며 별도 고지한다.
- 스마트스토어에서 외부 사이트용 디지털 이용권 판매가 허용되는지, 주문 API 접근권한·상품 유형·취소/환불 정책을 **연동 개발 전에 공식 확인**한다.

### 26.2 고객 구매·발행 흐름
- 신규 고객은 **네이버 로그인만** 사용한다. 기존 관리자 네이버 계정 유지, 카카오 로그인은 고객 UI에서 제거하되 기존 데이터/인증 의존성 검증 후 코드 정리한다. **카카오톡 공유 기능은 그대로 유지**한다.
- `초대장 무료 제작 → 저장/미리보기 → 발행하기 → 이용권 잔액 확인`.
- 이용권이 **0개**이면 초대장 데이터를 유지하고 '이용권 1개(8,900원) 필요' 등 구매 안내 및 **스마트스토어 상품 구매 링크**를 보여준다. 강제 자동 이동은 하지 않는다.
- 스마트스토어 결제 후 고객이 DearDay에 복귀하여 주문 확인을 진행하거나, 지원 가능한 공식 API 동기화 경로로 주문을 확인한다.
- **서버에서 공식 네이버 주문 API의 주문번호/상품주문번호·결제 상태·상품·수량·취소 여부를 검증한 뒤** 구매 상품에 해당하는 이용권 1/5/10개를 지급한다. 이름·전화번호·이메일 일치 또는 네이버 로그인 사실만으로 이용권을 지급하지 않는다.
- 주문과 DearDay 회원의 안전한 귀속/소유 검증 방법은 API에서 실제 제공하는 식별자·데이터 범위를 확인한 뒤 확정한다. 주문 조회 지연·조회 실패는 '확인 중/재시도'로 표시하고 임의 지급하지 않는다.
- 이용권이 1개 이상이면 발행 전 필수값 검증 및 환불/디지털 서비스 제공 개시 안내를 거쳐, **최초 발행 성공과 동시에 이용권 1개 차감 + URL 활성화**한다.
- 같은 초대장의 발행 후 내용 수정, 템플릿 변경, 재공개(정책상 허용되는 경우)는 이용권을 추가 차감하지 않는다. 다른 신규 초대장 최초 발행에는 각각 1개가 필요하다.

### 26.3 구매·환불 및 발행 동의
- **미발행 상태**에서는 법령·스마트스토어 정책에 따른 취소/환불을 지원한다.
- **발행 직전** 디지털 서비스 제공 개시, 청약철회 제한 가능성, 서비스 장애 등 법정 환불 예외를 명확히 고지하고 별도 동의/확인 기록을 저장한다(문구 버전·회원·초대장·일시 등).
- 발행 후 단순 변심 환불은 법령상 청약철회 제한 요건과 네이버 정책을 충족하는 경우에만 거절할 수 있다. **고지/체크만으로 모든 환불이 자동 거절되는 것은 아니다.**
- 취소·환불 접수/승인·거절/결제 취소 실행은 **스마트스토어 판매자센터 중심으로 관리**한다. DearDay에 자체 PG 환불 실행 기능을 중복 구현하지 않는다.
- DearDay 관리자에서는 해당 주문의 **발행 여부·발행일시·연결 초대장·동의 이력·취소/환불 상태**를 확인한다.
- **환불 요청 접수만으로 초대장을 삭제/중지하지 않는다.** 실제 환불 확정 시 해당 주문의 미사용 이용권 회수 및 발행 초대장의 공개 중지 여부를 법령·스마트스토어 정책에 따라 처리한다. 종전 유예·보관 연장 규정은 적용하지 않는다. 서비스 제공 오류 등 법정 환불 예외를 고려한다.
- 구매확정은 초대장 발행과 별개이며, 판매자 측 API로 임의 구매확정할 수 있다고 가정하지 않는다. 스마트스토어의 실제 구매확정·배송없음 처리 정책을 확인한다.
- **일부 사용한 5/10개 할인 묶음상품은 단순 변심에 따른 잔여 이용권 부분 환불을 제공하지 않는다.** 다만 법령상 청약철회·환불 권리, 서비스 하자 및 스마트스토어 필수 정책이 우선하며 예외 요청은 관리자 확인 대상으로 처리한다. **전부 미사용 묶음상품**은 법령·스마트스토어 정책에 따라 환불 신청 가능하다.

### 26.4 사용자 마이페이지 — 내 이용권
- **현재 사용 가능한 이용권 수**, 구매/관리자 지급/프로모션별 지급 내역, 누적 사용·회수·만료 내역, 만료 예정 수량을 조회한다.
- **이용권 보유/지급 내역**과 **이용권 사용 내역**을 구분해서 제공하며 기간·유형별 필터를 지원한다.
- 사용 내역에는 사용일시, 이용권 수량, 대상 초대장(제목/ID), 발행일시를 표시한다. 구매 내역에는 상품명·수량·주문 식별자·처리 상태를 표시한다.
- 구매 및 환불 관련 상세/증빙은 가능한 범위에서 스마트스토어 주문·판매자 안내로 연결한다. 네이버가 제공하지 않는 결제 영수증을 DearDay가 자체 발급한다고 가정하지 않는다.
- 사용 가능한 이용권이 0개면 스마트스토어 구매 링크를 노출한다.

### 26.5 관리자 — 이용권·주문·발행 관리
- 관리자 메뉴: **대시보드 / 스마트스토어 주문 / 이용권·발행 관리 / 템플릿 관리 / 회원·문의 관리 / 운영 설정·통계**. 기존 관리자 페이지에 확장한다.
- 대시보드: 기간별 검증 주문 수·금액(조회 가능한 범위), 최초 발행 수, 미사용 이용권, 환불/연동 오류 확인 필요 건수, 최근 추이. 관리자 수동 지급을 실제 매출에 합산하지 않는다.
- 주문 목록: 네이버 주문번호·상품주문번호, 회원, 상품/지급 수량, 결제·취소·환불 상태, 연결 초대장, 동기화 일시/오류, 발행 여부 및 상세 이력.
- 이용권 목록: 회원별 현재 잔액, 누적 지급·사용·회수·만료, 지급 출처, 지급 묶음별 잔여 수량·만료일, 발행 초대장/URL 연결.
- **관리자 수동 지급**: 회원 선택, 수량(1/5/10 또는 직접입력), 사유(테스트/이벤트/보상/기타), 메모, 유효기간 선택. 스마트스토어 주문이나 매출은 생성하지 않는다.
- **관리자 수동 회수/정정**: 미사용 잔액 범위 내에서만, 사유 필수, 처리 전 확인. 이미 소비한 이용권은 임의로 음수 잔액 처리하지 않는다.
- 지급/회수 등 잔액 변경 권한은 서버/API/RLS에서 검증한다. 권한별 허용 범위는 관리자 역할 정책에 맞추되 초기에는 super_admin만 수동 변경하도록 한다.
- 회원/주문번호/초대장/일자/변경 유형/처리자 기준 검색·필터 및 CSV 다운로드 지원.
- 스마트스토어의 실제 환불 승인/거절은 판매자센터에서 처리하고 DearDay는 상태·발행 증빙 및 동기화 오류를 관리한다.

### 26.6 거래 원장·감사 로그·정합성
- 잔액 숫자만 직접 증감하지 않고 **불변 거래 원장(ledger)**을 기록하는 단일 서버 거래 경로를 통해 지급·차감·회수·만료·정정한다.
- 원장 필드 예: 거래 ID, 회원 ID, 증감 유형, +/-수량, 변경 전후 잔액, 지급 출처(`smartstore/admin/promotion`), 주문/상품주문 식별자, 지급 묶음 ID, 초대장 ID, 처리자 ID, 사유·메모, 처리 시각, 멱등성 키.
- 과거 원장 기록은 임의 수정/삭제하지 않는다. 오류는 **역거래/보정 거래**를 새로 기록하여 이력을 남긴다.
- 주문번호·상품주문번호 및 거래 유형에 맞는 유일성 제약으로 **동일 구매의 중복 지급 방지**. API 재시도·중복 콜백에도 동일 결과를 보장한다.
- **최초 발행 시 이용권 차감 + 초대장 발행 상태/URL 활성화는 원자적 DB 트랜잭션**으로 처리한다. 동시 클릭·다중 탭·재시도에서 이중 차감 또는 무차감 발행을 막는다.
- 구매/환불 상태 변경과 원장 동기화는 재시도 가능하고 추적 가능한 작업으로 구성하며, 외부 API 오류나 DB 실패 시 '확인 필요'로 기록한다.
- 관리자 지급/회수·주문 귀속 변경·환불 후 공개 상태 변경 등 중요 조치는 **별도 관리자 감사 로그**에 관리자·시각·대상·사유·변경 전후 상태를 남긴다.
- 권장 논리 데이터 모델: `credit_products`(상품), `credit_orders`(외부 주문/상태), `credit_wallets`(잔액), `credit_grants`(지급 묶음/만료), `credit_ledger`(불변 거래 원장), `admin_audit_logs`(관리자 조치). 실제 테이블명/기존 스키마 재사용 여부는 구현 전 GAP 점검 후 확정한다.
- 거래 기록은 법령상 보존 의무, 개인정보 최소 수집·접근 제어·탈퇴 시 분리 보관 원칙을 준수한다.

### 26.7 구현 우선순위·검증
1. 상품·이용권 DB/원장·관리자 수동 지급/회수 및 마이페이지 보유/사용 내역.
2. 최초 발행 1개 차감·재발행 무차감·0개 구매 안내·원자적 트랜잭션.

4. 취소/환불 상태 동기화·발행 동의 기록·관리자 확인 필요 큐.
5. 대시보드 집계·CSV·운영 모니터링·전체 회귀/보안 테스트.
- 필수 TC: 1/5/10개 구매 지급, 관리자 지급·회수, 사용/잔액 내역, 최초 발행 차감, 같은 초대장 수정/재발행 무차감, 동시 발행, 주문 중복 조회, 구매 확인 지연, 환불 요청/확정, 부분 사용 묶음 환불, 만료, 원장/감사 로그, 권한·RLS 검증.

### 27.1 회원 및 개인정보
- 회원가입/로그인은 네이버 단일. 회원 유지 시 네이버 고유 식별자, 이름, 휴대전화번호, 이메일을 서비스 제공 목적 범위에서 보유하고, 회원탈퇴 시 법정 보존분을 제외하고 삭제한다.
- 활성 초대장이나 이용권 보유 여부와 관계없이 회원탈퇴는 언제든 허용한다. 탈퇴 전 데이터 삭제·이용권 권리 종료·환불 경로를 안내하고 최종 확인한다. 탈퇴 즉시 초대장 URL 공개 중단 및 관련 데이터 삭제를 진행한다.
- 구매 이용권 유효기간은 구매일로부터 5년. 일부 사용한 할인 묶음의 잔여 이용권에 대한 단순 변심 부분 환불은 제공하지 않되 법정 권리·스마트스토어 필수 정책이 우선한다. 탈퇴 후에도 법정 환불 권리는 유지한다.
- 개인정보 처리업무 위탁 및 국외 이전 고지, 실제 사업자정보·개인정보 보호책임자·법정 거래기록 보존기간은 출시 전 실제 계약/운영 정보와 법령에 따라 확정한다. 확인 전 임의 기재하지 않는다.

### 27.2 초대장 공개·편집·삭제
- 발행된 초대장은 **링크를 아는 누구나 로그인 없이 열람**할 수 있고 카카오 공유·링크 복사·QR코드로 전달 가능하다. 재전달받은 사람도 열람할 수 있음을 주최자에게 안내한다. 편집/관리 권한은 소유자에게만 부여한다.
- 개별 공개 초대장에는 `noindex`(필요 시 검색엔진 응답 헤더 병행)를 적용하고 사이트맵에서 제외한다. 서비스 소개·템플릿 등 일반 공개 페이지는 검색 노출 허용. `noindex`는 접근통제가 아니며 검색 결과에서 완전·즉시 제거를 보장하지 않는다.
- 행사 시작 **전**에는 행사일·시간·사진·문구·템플릿 등 편집 가능. 행사 시작 시각(KST)부터 초대장 내용 전체를 **읽기 전용**으로 전환한다. 하객 관리·삭제는 계속 허용한다.
- 행사 시작 전 행사일 변경 시 새 행사일 +30일로 삭제 예정일 재계산, RSVP·방명록 마감 시각 변경. 추가 이용권 차감 없이 기존 URL/QR 유지.
- 행사일 **+30일**에 공개 종료와 관련 데이터 자동삭제. 유예·유료 연장·복구 없음. 주최자 조기 삭제와 회원탈퇴 시에도 공개 즉시 중단 및 관련 데이터 삭제.
- 마이페이지에 삭제 예정일을 상시 표시하고 D-7/D-1 서비스 내 알림을 제공한다. 초기 외부 이메일·문자 발송은 하지 않는다.

### 27.3 RSVP·방명록·사진
- RSVP 필수: 이름, 참석 여부. 선택: 참석 인원, 연락처, 메시지. 목적은 참석 관리로 제한하고 광고·마케팅에 활용하지 않는다. 개인별 보안 수정 링크로 행사 시작 전까지 수정 가능. 동일 이름 중복 제출은 허용하며 소유자가 중복 의심 응답을 직접 정리한다.
- RSVP 신규 제출·수정과 방명록 신규 작성은 **행사 시작 시각(KST)에 마감**한다. 기존 RSVP 열람/엑셀 다운로드 및 기존 방명록 열람·작성자/주최자 삭제는 초대장 삭제 전까지 허용한다.
- 방명록 이름·메시지는 공개 링크 방문자에게 보이며 작성 전 고지한다. 삭제 비밀번호 4자리는 해시 저장, 작성자 본인 글 삭제 및 소유자 관리 삭제 가능.
- 사진·갤러리는 초대장 제작·공개 목적에 한해 사용하고 별도 동의 없이 광고·홍보에 활용하지 않는다. 사진 업로드 권한·초상권 확인을 주최자에게 안내한다. 어린이 사진 포함 가능성을 고려한다.
- RSVP·방명록·사진은 초대장 삭제와 함께 파기하며, 별도로 내려받은 RSVP 엑셀은 주최자 측 보관·파기 책임과 별도 안내가 필요하다.

### 27.4 인프라 확인 사실과 적용 상태
- Supabase 프로젝트 데이터베이스 리전: **Northeast Asia (Seoul), `ap-northeast-2`** (관리자 화면 확인).
- Vercel Functions 설정 리전: **Seoul, `icn1`** (설정 저장 성공 확인). **기존 배포에는 아직 적용되지 않았으며 새 배포 시 적용**된다. 사용자 승인 없이 운영 재배포하지 않는다.
- 데이터베이스 및 함수 실행 리전이 서울이라고 해서 로그·인증·운영 지원·하위 처리업체의 국외 이전이 없다고 단정하지 않는다. 개인정보처리방침 작성 전 실제 처리업무·수탁자·국외 이전 여부를 확인한다.

### 27.5 출시 전 검증·미확정 항목
- **정책 확정과 실제 기능 구현은 구분**한다. RSVP 엑셀 다운로드는 기존 요구사항에 있으나 `dev` 코드의 버튼/API 실제 동작은 별도 검증한다. MVP 방명록 전체 다운로드는 제공하지 않는 기존 기준을 유지한다(정책 ㉒ 선택은 미확정).
- 스마트스토어 디지털 이용권 판매 가능 여부, 공식 주문 검증·취소/환불 처리 정책, 묶음상품 환불 고지의 법적 적합성 확인.
- 개인정보처리방침 필수 기재사항(처리자/수탁자, 국외 이전, 파기·보존, 이용자 권리, 보호책임자)과 실제 가입 동의 화면·동의 기록 검증.
- 초대장 행사일 +30일 날짜 경계, 자동삭제 배치·재시도, 저장소 파일 삭제, 탈퇴 시 삭제 실패 복구 절차, 검색엔진 색인 차단 및 서버 권한 검증.
- 초기 가격(1개 8,900원, 5개 39,900원, 10개 69,900원)은 **출시 전 최종 확정** 상태 유지.

### 27.6 개발·배포 원칙
- 개발은 `dev` 브랜치에서만 진행하고 로컬 테스트 후 사용자가 **`dev-main 병합 배포 진행`**을 명시적으로 지시한 경우에만 `main` 병합·운영 배포한다.
- 이 문서는 요구사항 업데이트 결과물이며 서비스 약관·개인정보처리방침·실제 앱 코드는 별도 단계에서 수정한다.
